# 规划器实测（离线评测工具）

G4a 设计稿要定一件事：线上助手的「规划、写分析、反思、临时统计」四项交给本地 Qwen 做，它能不能做到开发者同意的通过标准，用什么请求设置做到。本工具用内网本地模型服务把这四项各跑一遍，量准确率、稳定性与耗时。结果决定设计稿里模型与代码各管哪些事。

- **不是模块代码**：`src/` 不引用它，不随 wheel 发布。
- **不连库，不用真实业务数据**。发给模型的只有三样：
  - 由 `docs/2_landed` 生成的提示词（术语表、话题清单、分析维度）；
  - 测试案例集与设计探针里的问句，外加本工具补的变体；
  - 合成的事实（写分析、反思用）和程序生成的 300 行假问题单（临时统计用），单号都是 99 年的假号。

## 红线

- **只允许连内网本地模型服务**（OpenAI 兼容接口），禁止填外部模型 API。不加 `--confirm-local` 不会发请求。这个参数只是提醒，脚本判断不了地址是不是内网，**运行前要人工核对 `FI_LLM_BASE_URL`**。
- **凭据只放本机 `.env`**（已在 `.gitignore`），不要贴进对话，不要写进任何入库文件。
- 由开发者在能连模型服务的内网机器上运行。编程助手不运行它，只看下文「输出」里标为可以发回的文件。
- 输出写在 `runtime/planner_spike/` 下（`runtime/` 不入库）；`--out` 指到 `runtime/` 以外时脚本拒绝运行。

## 准备

复用话题标注那套 `.env` 变量，只读这三个：

```dotenv
FI_LLM_BASE_URL=http://<主机>:<端口>/v1   # 与平台 ctx.llm 同一个推理服务
FI_LLM_API_KEY=<key>
FI_LLM_MODEL=<服务上的模型名>
```

`FI_LLM_CONCURRENCY`、`FI_LLM_TIMEOUT`、`FI_LLM_DISABLE_THINKING` 是话题标注用的，本工具不读。并发与超时用命令行参数，默认并发 2、超时 120 秒（同线上 `LLMClient`）。思考开不开由下面的「组」决定。

## 四组请求设置

线上 `ctx.llm.chat()` 只能传 `temperature`、`max_tokens`、`response_format`、`tools`，**没法按次关思考**。Qwen3.8-27B 默认开思考（模型卡写的 `reasoning_effort` 默认 xhigh）。话题标注那次关了思考，说明不了线上默认请求的表现，所以分四组对比：

| 组 | 请求 | 线上现在能不能这样发 |
|---|---|---|
| 现状 | temperature 0，JSON 模式，不传 max_tokens，别的都不传 | 能，这就是线上会发出的请求 |
| 关思考 | 现状 + `chat_template_kwargs: {"enable_thinking": false}` | 不能，要平台加参数 |
| 思考low | 现状 + `reasoning_effort: "low"` | 不能，要平台加参数 |
| 推荐采样 | 关思考 + 模型卡推荐的非思考采样（temperature 0.7、top_p 0.8、top_k 20、presence_penalty 1.5） | 不能 |
| 现状+预匹配 | 请求同「现状」，只在本轮问题后面附一段「问句里能对上的名称与号码」（`prematch.py`），系统提示不变 | 能，模块自己拼进用户消息 |
| 现状+校验 | 请求同「现状」，计划格式合格后再过设计稿 §5.3 第 13、15 条校验（`resolve.query_checks`：日期依据与问句里的事件词一致；问句里的问题编号、机型名进了计划），不过就打回重写一次；重写后仍不过照用重写的 | 能 |
| 现状+预匹配+校验 | 上面两项都加 | 能 |

通过与否**以「现状」组为准**。只有别的组达标时，说明要向平台提「按次传思考开关」的需求，设计稿按那一组的设置写，并注明依赖平台版本。

「现状+预匹配」组用来回答一个问题：规划之前先由代码找出问句里能核对的号码与名字、写成提示交给模型，值不值得做。号码按总述「按编号查单」的认号表只看写法；名字在合成主数据 `mockdata.py`（人员 15,091、供应商 978、机型 500 等，条数与真实库同一量级，名字都是编的）里整串匹配，物料名称不查。提示只说「这个词在库里是什么」，不建议用哪种查法。

另有一条不调模型的代码规则「号码直通」（`resolve.number_shortcut`）：问句只有号码，加上号的种类和「查一下」「是哪张单」这类套话时，不调规划，直接按号查单。汇总里单列它命中了哪些问句、直通后对不对。

## 四项实测

| 项 | 做什么 | 怎么判 |
|---|---|---|
| 规划 | 问句 → 计划 JSON（技能、参数、步骤间引用）。提示词见 `prompts.planner_system()`，约 1.6 万字；对照集 `cases/plan_cases.json` 208 条（c4） | 计划先过格式校验，不合格把错误发回让模型改一次。再经 `resolve.py` 模拟线上代码在执行前做的确定性处理（规则与编号同设计稿 §5.3：同一个意思统一成一种写法、话题范围对照话题清单判断、名字改到库里对得上的一类、同一统计拆成的几步合成一步、有追问时只追问、检索文字里去掉同一步的条件值；另有几条看本轮问句原话：写成时间的状态改回条件、「各款」按机型包含、去掉问句没点名的栏目、安全问题拆成等级与话题两路。日期依据与事件词不一致不改写，由「+校验」组打回；不打回的组在汇总里报「按现规则会拦下」的运行数），然后与期望逐类比对：技能、域、时间原话、日期依据、条件、分组与指标、号码与单号、详情内容、文字查找、列与导出、依赖、沿用与替换。值按归一后比较（大小写、全角、空格、常见同义词），不比措辞。汇总另给「模型原样」的全对率作对照 |
| 写分析 | 给定问题、已展示的表格与合成事实，写表格下面那段分析。流式调用，同线上 `chat_stream`。`cases/narrative_cases.json` 20 条 | 逐句找数字（含「三十七张」这类汉字数；「这两类」这类指代不算），不在事实、问句、表格里出现的数算编造；点名的问题编号也要在事实、问句或表格里。另查有没有露出英文字段名。出汇总时按当前规则重算 |
| 反思 | 某一步结果有信号（查空、名字对上多个、质疑），程序列出允许的动作并标好每个动作「有结果 / 没有结果」，模型选一个。`cases/reflect_cases.json` 15 条 | 选的动作在期望里算对 |
| 临时统计 | 给列说明、3 行样例与题目，模型写沙箱脚本，在本机 `forge_sandbox` 里按线上资源档（60 秒、1024MB）跑。10 题，见 `stats_tasks.py` | 结果与参考脚本的结果比，数字容差 0.051。脚本报错时把报错发回让模型改一次 |

反思的期望动作按设计讨论里提议的策略写（只放宽默认补上的条件、名字对上多个时不猜）。查空放宽、质疑复核这两类口径开发者还没定，定了以后改 `reflect_cases.json` 再跑这一项即可。

## 运行

都在仓库根目录执行：

```powershell
# 1. 自检：不连模型，几十秒
uv run python scripts/planner_spike/spike.py --self-check

# 2. 冒烟：每组 3 条规划、1 条写分析，共 16 次调用
uv run python scripts/planner_spike/spike.py --smoke --confirm-local

# 3. 全量：低峰时段跑
uv run python scripts/planner_spike/spike.py --run --confirm-local
```

- **第 1 步**：最后一行应为「自检通过」。它检验的是打分本身：
  - 用期望冒充模型，四项必须全对；
  - 把期望计划改坏一处（换技能、改条件值、丢引用、该问不问……），必须判错；
  - 只改写法（时间原话加空格、取值换大小写与全角、无依赖的步骤换顺序……），必须判对；
  - 「改一次」那条路也走一遍。

  不通过就先停下，把输出发回。
- **第 2 步**：看 `smoke/冒烟.md`：
  - 每组请求是否被拒（HTTP 400 说明服务不认那组参数，全量时用 `--groups` 去掉）；
  - 「现状」组有没有思考内容、思考多少字；
  - 每次耗时；
  - 文末按冒烟耗时估算的全量用时。

  `run_info.json` 里有 `/models` 的返回。服务上同时有 `Qwen3-Fast` 与 `qwen3.8-27b` 等多个模型名。`Qwen3-Fast` 背后是 qwen3.8-27b（业务方 2026-10-27 确认），但两个名字走的部署不同：p0、p1 两次实测里 `Qwen3-Fast` 都更快，温度 0 下同一问句多次计划不一致的问句却多得多（p0 17 条比 4 条，p1 14 条比 4 条）。**`FI_LLM_MODEL` 要填平台 `ctx.llm` 实际用的那个名字**，量的才是线上的表现。
- **第 3 步**：默认共 2,246 项：
  - 规划 1,976 次：「现状」组 208 条 × 5 次；其余三组各跑标为 core 的 104 条，每条 3 次；
  - 写分析、反思、临时统计各在「现状」「关思考」两组跑 3 次，共 270 项。

  比较附不附预匹配提示（c4 起）。「现状+预匹配」放第一组，跑全部问句；「现状」放第二组，只跑 core 的 104 条（含新加的 25 条 M），每条也跑 5 次。共 1,560 次调用，按 p2 的耗时约半小时：

  ```powershell
  uv run python scripts/planner_spike/spike.py --run --confirm-local --parts plan --groups 现状+预匹配,现状 --sub-repeats 5 --out runtime/planner_spike/<日期>-p2-预匹配
  ```

  汇总里「只看各组都跑了的问句」一表是两组的直接对比；「预匹配提示」一节列出提示了什么、哪些提示期望里没用到。

  看打回后模型改不改得过来（「+校验」组），只跑 core 即可。把「现状+校验」放第一组时它会跑全部 208 条；只想跑会被拦下的那几类，用 `--limit` 不合适，直接全跑，约 1,040 次调用：

  ```powershell
  uv run python scripts/planner_spike/spike.py --run --confirm-local --parts plan --groups 现状+校验 --out runtime/planner_spike/<日期>-p2-校验
  ```

  预匹配的 A/B 有了结论后，若决定采纳，再跑一次「现状+预匹配+校验」作为下一版的基线。

  如果冒烟显示「现状」组每次要几十秒，先只跑规划：

  ```powershell
  uv run python scripts/planner_spike/spike.py --run --confirm-local --parts plan --groups 现状,关思考
  ```

- **中断了可以续跑**：同一天再运行同一条命令，已完成的跳过，调用出错的重跑。换一天运行要用 `--out runtime/planner_spike/<原目录名>` 指回原目录。某一项出了工具自己的错时，只跳过这一项并打 ⚠ 行，其余照跑，再运行一次会补跑。
- **换模型要换目录**：临时换模型可在同一个 PowerShell 窗口里先执行 `$env:FI_LLM_MODEL = "<模型名>"`（优先于 `.env`），再加 `--out runtime/planner_spike/<新目录名>`。目录里已有别的模型或提示词版本的结果时，脚本拒绝运行，免得新旧结果混在一起。
- **临时统计的沙箱同时只跑 2 个**：Windows 上同时跑十几个沙箱子进程时，偶有子进程直接崩掉（exit=3221227274），与脚本内容无关。参考结果在调模型之前先逐题算好；遇到这类崩溃会自动重试两次。
- **只重出汇总**：`--report --out <目录>`，按已有的 `raw.jsonl` 重算，不调模型。
- **其他参数**：
  - `--limit N`：每项只取前 N 条，试跑用；
  - `--repeats`：第一组每条跑几次，默认 5；
  - `--sub-repeats`：其余各组每条 core 跑几次，默认 3；
  - `--aux-repeats`：写分析、反思、临时统计每条跑几次，默认 3；
  - `--aux-groups`：这三项跑哪几组；
  - `--concurrency`、`--timeout`：并发与超时。

  耗时按并发 2 量，相当于两个人同时提问；调高并发会让耗时变差。
- 在 PowerShell 里把输出接到管道（`| Select-Object …`）时中文会乱码，先执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`。直接运行不受影响。

## 输出

默认目录 `runtime/planner_spike/<日期>-<提示词版本>/`：

| 文件 | 内容 | 能否发回 |
|---|---|---|
| `汇总.md` | 各项、各组对照通过标准的结果；耗时 P50 / P90 / P99；token；思考调用次数与字数；按问法分的全对率 | 可以 |
| `错例.csv` | 每次没全对的运行：错在哪一类、问句、期望、模型给的计划或句子 | 可以 |
| `分析段样例.md` | 每条写分析取第一次运行的原文，编造的数字句用 ⚠ 标出 | 可以，请顺手看几条：数字都对但说错对象的情形，脚本查不出来 |
| `smoke/冒烟.md` | 冒烟每次调用的状态、耗时、token、思考字数，以及全量用时估算 | 可以 |
| `run_info.json` | `/models` 返回、模型名、并发、超时 | 可以 |
| `raw.jsonl` | 每次运行的完整记录，含模型原文与思考内容的前 3,000 字 | 内容都是合成的，可以发回，但文件大；先留本地，需要时再要 |

## 通过标准（开发者 2026-10-26 同意）

| 项 | 指标 | 门槛 |
|---|---|---|
| 规划 | 计划 JSON 合格（含改一次） | ≥ 99% |
| 规划 | 选对技能 | ≥ 95% |
| 规划 | 关键参数正确，取最差的一类 | ≥ 90% |
| 规划 | 必须追问的漏问 | ≤ 2% |
| 规划 | 不该追问的多问 | ≤ 5% |
| 规划 | 多段问句拆分与依赖正确 | ≥ 85% |
| 规划 | 同一问句多次计划一致 | ≥ 95% |
| 规划 | 单次调用耗时 P90 | ≤ 10 秒 |
| 写分析 | 含数字的句子里，数字都出自事实 | ≥ 98% |
| 反思 | 选对动作 | ≥ 90% |
| 临时统计 | 一次跑对 / 改一次后跑对 | ≥ 70% / ≥ 85% |

- 漏问的样本少：必须追问的只有 11 条（模型该问 6 条、缺时间的汇总 5 条），「现状」组共 55 次运行，错 2 次（3.6%）就不达标。看到漏问先看 `错例.csv` 里是哪几条。
- 缺时间的汇总统计（对照集标 `"clarify": "rule"`）只要求模型不自己补时间：代码会在执行前检查时间缺失。模型补了时间才算漏问。
- 要查库才知道该不该追问的（重名、多家工厂，标 `"db"`），模型追问了算多问。

## 没达标时的退路

| 没达标的 | 先试 | 再不行 |
|---|---|---|
| JSON 合格 | 看错例是哪类格式错，改提示词（`PROMPT_VERSION` 加一，旧结果不混用） | 向平台提结构化输出（guided JSON）参数 |
| 选技能、某类参数 | 改提示词、补示例；易错的一类改由代码判（号码种类、状态词） | 规划拆成两次调用：先选技能，再按技能填参数 |
| 漏问、多问 | 改提示词 | 追问全部改由代码规则判 |
| 一致性 | 看是否思考导致；比较「关思考」组 | 收窄自由填写的字段 |
| 耗时 | 比较「关思考」「思考low」组；请运维确认推理服务开了前缀缓存（提示词前 1.45 万字每次相同） | 缩短提示词，按问法分流后只带相关段落 |
| 写分析 | 改提示词 | 数字句由代码模板生成，模型只写不带数字的句子；或逐句核对，含编造数字的句子删掉 |
| 反思 | 改提示词 | 改成代码里的固定策略，模型只写说明 |
| 临时统计 | 补口径函数与样例 | 不开放临时统计，只留固定的统计技能 |

## 对照集怎么写

`cases/plan_cases.json` 每条：

| 键 | 说明 |
|---|---|
| `id`、`q` | 编号与问句。CN、BR、OS、XC 来自测试案例集（XC-034 三域都无权时不调规划，不收），P 来自设计探针，V 是本工具补的变体，M 是「不整齐输入」（只有号码、几种号码混在一起、不带类别词的名字、跨类同名、名字与现象写在一起），全部标 core |
| `core` | `true` 的除第一组外其余各组也跑 |
| `clarify` | `model` 模型该追问；`rule` 缺时间的汇总统计（见上）；`db` 要查库才知道（模型不该问）；不写为不该问 |
| `history`、`previous_plan` | 多轮：最近几轮问答与上一轮计划 |
| `perms` | 本轮可查的域与 CAR，如 `{"domains": ["国内"], "car": false}`，只作说明：p2 起规划器不看权限，同一句话无论谁问计划都一样 |
| `expect` | 可接受的计划，几种写法都算对时列几个；每个是步骤数组，或 `{"steps": [...], "alternatives_nonempty": true}`（还要求模型写出其他理解） |

期望里的每一步只写要检查的键，没写的不查，但三条例外：
- 条件类技能（list_issues、aggregate、text_search、custom_stats）没写 `domains`、`time`、`filters` 时，表示**必须没有**，模型多写算错；
- 不想查这三个时写 `"any"`；
- 允许出现、但不要求出现的条件写进 `filters_optional`。

| 键 | 写法 |
|---|---|
| `skill` | 技能名；几种都行时写数组 |
| `domains` | 域数组；三个域写全等于不写。`domains_from` 查来源（`user` / `previous`） |
| `time` | 每项 `said`（原话，可写数组列几种说法）或 `said_has`（包含这些字），可加 `basis`（默认「建单」）与 `from` |
| `filters` | 每项 `field`（可写数组）、`op`（不写为「是 / 属于 / 包含」一类），取值四选一：`value`（数组表示多个值）、`value_any`（几种写法任一）、`value_has`（包含这些字）、`value_ref`（如 `"s1.top1"`）；可加 `from` |
| `group_by` / `group_by_has` | 分组维度，完全相同 / 至少包含 |
| `metrics_has`、`ranking`、`top`、`compare` | 指标至少包含、要排名、名次数、时段对比（写 `{"kind": "时段"}`，两个时段写在 `time` 里；p2 起没有对象对比，「A 和 B 哪个多」写成筛选加分组） |
| `sort`、`limit` | 清单排序（`{"by": "不良率", "order": "降序"}`）与张数 |
| `numbers`、`issue`、`issue_from` | 号码数组；单号原样，或 `{"ref": "s1.issues"}` |
| `aspects_has` | 详情要看的内容；某项写数组表示几种任一 |
| `mode`、`terms`、`logic`、`topic_has`、`topic_scope`、`phenomenon_has`、`approach_has`、`fields_has`、`ask`、`text_has` | 文字查找。`topic_scope` 比的是 `resolve.py` 按话题清单判出的结果（p1 起模型不填）；`text_has` 在话题、关键词、做法（`approach`）、现象四栏合起来找；`text_not_has` 要求这四栏里都不出现这些词（条件值不该混进要找的文字） |
| `columns_has`、`export` | 点名要的列、要导出 |
| `within`、`when`、`refs_has` | 步骤间依赖：`"s1"`、`"s1.increased"`、引用数组 |
| `chart`、`kind`、`reason` | 换图的图型、introduce 的类别、clarify 的原因 |

改了对照集先跑 `--self-check`：期望写错（如引用指到不存在的步骤）会在这一步暴露。

**请抽查约三成期望**，尤其是多轮、多步和「X 的问题」拆两步的几条。期望是编程助手按 `2_landed` 与测试案例集写的，写错了会把对的计划判错。

## 局限

- 对照集的问句大多来自测试案例集，问法比真实用户整齐，线上的准确率只会更低。
- 写分析只查得出编造的数字，查不出「数字对、对象说错」，要人看 `分析段样例.md`。
- 反思与临时统计的条数少（15 条、10 题），只能看量级。
- 耗时是在本工具的并发下量的，线上高峰时会更慢。
