# AI 润色实测（离线评测工具）

设计稿（决策 2026-11-09「AI 润色技术设计」）有几个数要靠实测定：原文长度上限、单次超时、`max_tokens` 系数，以及程序检查的门槛能不能达到。本工具用内网本地模型服务，把合成样例照线上的请求跑一遍，量检查通过率与耗时。结果回填设计稿 §4、§10、§12.3。

- **不是模块代码**：`src/` 不引用它，不随 wheel 发布。
- **做法 A**（开发者 2026-11-09 同意）：润色的规则读取、参数、富文本拆拼、提示与程序检查暂放在 `polish_core.py`，G4b 移进 `src/factory_issue_module/polish/`，本工具改成转接，规则只留一份。两边不一致时以设计稿为准。
- **不连库，不用真实业务数据**。发给模型的只有：
  - 由 `docs/2_landed/domestic/ai_polish.md` 生成的提示（栏目名称与说明）；
  - `docs/testcases/polish/cases.json` 的合成样例（p2 共 34 条：27 条调模型，7 条不调模型就该报错）；
  - 本工具拼的长度阶梯：几组编写的词（线别、部件、缺陷、原因、处理）轮换拼成原因分析，每句的批次号与数量都不同，拼成 500、1000、2000、3000、4000、6000 字。句子不能重复：重复的段落会被模型并掉，输出变短，长度检查必然不过（长度阶梯 `l1` 就是这样，2026-11-10 冒烟 LD-1000）。
  - 样例里的单号是不存在的 99 年号，带了也不查库。

## 红线

- **只允许连内网本地模型服务**（OpenAI 兼容接口），禁止填外部模型 API。不加 `--confirm-local` 不会发请求。这个参数只是提醒，脚本判断不了地址是不是内网，**运行前要人工核对 `FI_LLM_BASE_URL`**。
- **凭据只放本机 `.env`**（已在 `.gitignore`），不要贴进对话，不要写进任何入库文件。
- 由开发者在能连模型服务的内网机器上运行。编程助手不运行它，只看下文「发回哪些文件」里的文件。
- 输出写在 `runtime/polish_spike/` 下（`runtime/` 不入库）；`--out` 指到 `runtime/` 以外时脚本拒绝运行。

## 准备

1. 拉取最新代码后在仓库根目录 `uv sync`。
2. 仓库根目录的 `.env` 写这三个变量（与规划器实测 `scripts/planner_spike/` 同一套，已有就不用改）：

   ```dotenv
   FI_LLM_BASE_URL=http://<主机>:<端口>/v1   # 与平台 ctx.llm 同一个推理服务
   FI_LLM_API_KEY=<key>
   FI_LLM_MODEL=<服务上的模型名>             # 填平台 ctx.llm 实际用的那个（G4a 定的是 Qwen3-Fast）
   ```

请求与线上 `ctx.llm.chat` 发出的相同：temperature 0、JSON 模式、按原文长度给 `max_tokens`，system 经平台的 `PolicyLLM` 并入红线段。不另设请求组：线上只能这样发。

## 运行

都在仓库根目录执行（PowerShell）：

```powershell
# 1. 自检：不连模型，几秒。核对样例的判错、富文本拆拼往返、程序检查（含 11 个反例）、提示形状与长度阶梯
uv run python scripts/polish_spike/spike.py --self-check

# 2. 冒烟：PL-01、PL-04、PL-16 各一次，加 1000 字一档一次；顺带估算全量要多久
uv run python scripts/polish_spike/spike.py --smoke --confirm-local

# 3. 全量：样例各 3 次（报错类各 1 次），长度阶梯每档 5 次。中断后再执行同一条命令会接着跑
uv run python scripts/polish_spike/spike.py --run --confirm-local

# 只按已有结果重出汇总（不发请求）
uv run python scripts/polish_spike/spike.py --report
```

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--repeats` | 3 | 每条样例跑几次 |
| `--ladder-repeats` | 5 | 长度阶梯每档跑几次 |
| `--parts` | `cases,ladder` | 只跑样例写 `cases`，只跑阶梯写 `ladder` |
| `--only` | 空 | 只跑这几条，如 `PL-01,PL-19,LD-3000` |
| `--concurrency` | 2 | 并发数，与规划器实测相同 |
| `--timeout` | 120 | 单次请求超时（秒），同线上 `LLMClient` |
| `--out` | `runtime/polish_spike/<日期>-r1` | 换了模型、提示版本或样例版本要换目录，脚本会拦 |

全量约 120 次调用（加上修一次的），按冒烟估出的时间为准；冒烟的 `冒烟.md` 末尾有估算。

## 怎么判

每次调用的结果先过程序检查（设计 §9）：格式、占位标记、多出的事实、缺少的事实、长度、开头的说明。第一次不过，带上不过的原因修一次（同线上），仍不过算失败。

| 指标 | 门槛 | 用来定什么 |
|---|---|---|
| 一次通过检查 | ≥ 80% | 不到就改提示（`polish_core.PROMPT_VERSION` 改成 `r2`）再测 |
| 修一次后通过检查 | ≥ 95% | 同上 |
| 通过检查且样例要求都满足 | 全部 | 样例的 `answer_preserves` 等；不满足说明检查漏了，要补检查 |
| 不调模型的样例判对 | 全部 | 不对是代码问题，不是模型问题 |
| 因 `max_tokens` 截断 | 0 | 不为 0 就调大 `polish_core.max_tokens` 的系数 |
| 原文长度上限 | 修一次的总耗时 P90 ≤ 60 秒、通过率 ≥ 90% 的最长一档 | 回填 `2_landed` 的「原文长度上限」与设计稿 §10 |
| 单次超时 | 该档单次最长 × 1.5 | 回填设计稿 §4 的 `CALL_TIMEOUT` |

程序检查认不出人名、工位、原因措施的意思有没有被改。「抽看.md」列出 30 条通过了检查的结果，请逐条看一遍，在每条的「改掉了意思」后面写「否」或写出改掉的地方。

## 发回哪些文件

输出目录 `runtime/polish_spike/<日期>-r1/` 里，内容都是合成的，下面三个可以发回：

| 文件 | 内容 |
|---|---|
| `汇总.md` | 结论表、各检查项不过的次数、长度阶梯的耗时、各样例的结果 |
| `错例.csv` | 没过检查的每一次调用：哪几项不过、多出与缺少了什么、输出开头 |
| `抽看.md` | 看过并标注后的那份 |

`raw.jsonl`（全部原始记录）与 `run_info.json` 留在本机，要排查时再发。冒烟的结果在 `smoke/冒烟.md`，有报错时发回。
