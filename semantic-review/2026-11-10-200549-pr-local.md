## High-level view

`parse` 先按标题取出四个小节，再在各节里找表头逐字对上的那张表，然后逐行校验。表格层面的问题（缺分隔行、列数不对）沿用 `landed.tables` 的说法；表头对不上、缺小节、值不合法等，由本模块自己写提示，把该怎么写也告诉管理员。全角数字、上标、代码块里的表、单元格里的 `\|` 都能正确处理或拒收。

漏洞出在「取小节」这一步。`landed.section` 只取第一个同名标题，取到同级或更高级的下一个标题为止。所以四节以外的文字不管写在哪里都没人看。管理员在文件末尾再补一节 `### 共用要求`，或在共用要求里写一个 `## 注意` 小标题，保存时都能通过，规则却不生效。这正是 `validate_config` 本该在保存时拦下的那类错误。

实测工具改调 `src` 后行为不变。对内置默认，新旧两份解析得到的栏目、顺序、说明与要求逐项相同。34 条样例经 `prepare`、`user`、`system` 生成的提示也逐字相同。所以 r2 的实测结果仍然有效，不需要重跑 `--parts cases`。

设计 §10 与代码基本一致，只差栏目代码的字母大小写：设计写的是「小写字母开头的字母、数字、下划线」，代码只认小写字母。

### 小节边界：四节之外的文字没有人管

`_section` 用 `landed.section(text, "### 共用要求")` 取正文：只取第一个同名标题，取到下一个同级或更高级标题为止。对这一个文件来说，后果是管理员写下的、语法也没错的内容可能根本不生效，而保存能通过。实测：

```
内置默认 + 末尾再加「### 共用要求\n\n用词正式。」  → 通过，common = ''
内置默认 + 末尾再加一节「### 设置」写 100           → 通过，max_input = 3000
「### 共用要求\n\n## 注意\n\n正式」                → 通过，common = ''（「正式」被丢掉）
```

第三种情况很容易遇到：管理员在共用要求里分几条写、给每条加个 `##` 小标题，结果一个字都不进提示。要兼容「## 润色规则（初始版本）」开头和整份 `ai_polish.md` 上传（目前这两种都能通过），不能简单地拒收所有其他标题。建议至少做到两点：四个标题各自只许出现一次；从 `### 设置` 起，四节正文里出现的 `#`–`###` 标题拒收，并说明原因（「共用要求里只能写正文，小标题请用 #### 以下」之类）。其他 Markdown 槽位（`topic_terms.md` 等）也是取第一个同名节，那是已有代码，不在这一片的范围。

### 管理员会看到的报错

全角数字「３０００」、上标「3²」、空文件、只有空白、表在代码块里、`###设置`（漏了空格），都得到清楚的中文报错。单元格里的 `\|` 会还原成 `|`；行尾写成 `不限\|` 时报「现在是『不限|』」，也看得懂。只有超长数字这一条漏出原生异常：

```
[RAW] ValueError: Exceeds the limit (4300 digits) for integer string conversion: value has 5000 digits; use sys.set_int_max_str_digits() to increase the limit
```

保存照样会被拒，只是 Console 上显示的是这段英文。`_positive` 的注释说专门避开了 `int()` 的原生错误，这个口子是同一类问题。运行时 `load` 有兜底，所以只影响上传时的提示。

沿用 `landed.tables` 的那两种报错可以看懂，但不够顺：`「栏目」一节里 有一张表缺表头分隔行：'| 栏目代码 | … |'`，中间多了空格，还带着 Python 的引号。列数不对时（`写 A|B` 没转义）只说「第 7 行有 6 列，表头是 5 列」，没提示改成 `\|`。

另有一处非阻塞的观察：半角的「(没有)」和「无」不算「没有」，会作为额外要求原样进提示。这与设计列出的写法一致，管理员却很容易打成半角。如果不想多认几种写法，可以在 2_landed 那一节的说明里点明要用全角括号。

### 各栏要求的小标题与代码块

`_requirements` 逐行用 `^####\s+` 判断小标题，没有经过 `landed._content_lines` 的代码块判断。管理员在某栏要求里用代码块举例、里面写了 `#### 预防对策` 时，结果是 `measures.requirements == "```"`，`prevention.requirements == "```\n编号"`，两栏的要求都被弄乱，且不报错。这种输入少见，但修起来只是一次循环里的判断。

### 实测工具：r2 结果仍有效

把 HEAD 的 `polish_core.py` 放到临时目录，与当前版本对照：两者对内置默认解析出的 `max_input`、`common` 相同，六个栏目的顺序与 `code/name/about/rich/default_max/requirements` 也相同。34 条样例的 `prepare` 结果（错误码与原因）、`user()` 与 `system()` 逐字相同，没有差异。`Rules.fields` 由 dict 改成 tuple，工具里的三处用法（`parse_request` 的 `rules.field(...)`，`self_check` 的代码集合与计数）都已跟着改。新解析比旧的严，但只多了拒收的情形，内置默认又能通过，所以不违反规矩第 3 条。

### 单测覆盖

§10 表每一行都有拒收例，`load` 的四种回退路径（没上传、没有 config、存储报错、存下的旧版解析失败）连同日志事件名也都测到了。
