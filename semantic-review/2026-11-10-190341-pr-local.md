# AI 润色 P0：任务声明、入口分派与参数校验

这次改动给模块加上了 `domestic_polish` 任务的骨架。manifest 声明了 `TaskSpec` 和第 8 个配置槽位 `polish_rules.md`；`handle()` 开头按 `ext_param.task` 分派；新包 `polish/` 只做 §5 的参数校验，校验过了暂时答 `POLISH_FAILED`。四个错误代码与文案放在 `turn/errors.py`，有单测逐字对照 `ai_polish_api.md`。按任务单的许可，`config/polish_rules.py` 先挂了一个占位解析：它认四个小节和两张表头，并把内容读成 `PolishRules`。core 与 platform 的下界升到 0.3.9，锁文件只改了这两行。

**Verdict**: APPROVED

## High-level view

分派只认任务码，判断方式与平台的 `forge_platform.ext_param.task_of` 相同：去掉首尾空白，非字符串当空串。所以 `/v2/tasks` 和 `/v2/chat` 对同一个 `ext_param` 的判断一致。不带 `ext_param` 或带别的任务码时，`run_turn` 收到的仍是原来那个 request，pacing 和 `live` 的处理也没变。唯一新增的行为是认不出的任务码记一条 `factory_issue_unknown_task` 日志，这条日志是设计 §3 要求的。查询流程里没有任何地方读 `ext_param`。规矩第 6 条成立。

润色分支只读 `ctx.config`（`config_files.load`），不调 `describe()`，不碰工作区和会话历史，不发 SQL，也不经过 `pacing.paced`。单测守住了 describe、工作区、SQL 和 orchestrator 这几样。pacing 和会话历史只能靠读代码确认，因为单测在 `live=False` 下跑，也没有拦 `ctx.session`。

§5 参数表六行都实现了，逻辑与实测工具的 `parse_request` 一致，前四行和 context 那一行都有单测。`issue_no_ignored` 与 context 丢弃的计数只核对了 `PolishRequest` 的字段，日志本身是否发出没有测。五Why 那一项的容错比设计写得宽，设计与代码要对齐。

错误代码与文案和 `ai_polish_api.md` 开流后那张表逐字相同，单测拿整张表与 `POLISH_MESSAGES` 比对。错误事件都是 `fatal=True`，文案只出自 `turn/errors.py`。P0 用户能看到的只有这四句话，不涉及表名、字段名。

`polish/` 的 import 守卫通过：没有 import plan、present、skills、stats、`turn.orchestrator`。但 `polish/` 实际还依赖 `declarations`，设计 §1.2 的依赖清单没列。规则槽位和 `landed.polish_rules_section` 提前到 P0 做了，任务单写明了这一点，设计 §15 的 P1 行没跟着改。

### 分派与平台的任务码判断保持一致

```
handle(request)
  ├─ polish.is_polish ── task_of(request) == "domestic_polish" ──► polish.run（事件直出，live=False 时丢 progress）
  ├─ task_of 非空 ── log factory_issue_unknown_task ──┐
  └─ 其余 ────────────────────────────────────────────┴─► orchestrator.run_turn → pacing（与改前相同）
```

`task_of` 先 strip 再比较。平台的 `/v2/tasks` 也是先 strip 再调 `find_task`，所以 `" domestic_polish "` 在两个入口上都会进润色，`/v2/chat` 与 `/v2/tasks` 不会出现一边润色、另一边走查询的情况。

### `polish.run` 名字遮蔽（confirmed）

`polish/__init__.py` 里的 `from factory_issue_module.polish.run import ext_param, run` 把包属性 `run` 从子模块换成了函数。本机验证结果：`import factory_issue_module.polish.run as m` 和 `from factory_issue_module.polish import run` 拿到的都是 `function`，只有 `sys.modules[...]` 里才是模块。P3 的完成标准要求「把 `CALL_TIMEOUT`、`HEARTBEAT` 调小」，到时最自然的写法 `monkeypatch.setattr(polish_run_module, "CALL_TIMEOUT", 0.1)` 会改到函数对象上，常量其实没变，于是超时用例只能干等 110 秒或者假通过。P0 现在就是改名的最低成本点。

### §5 参数解析

`issue_no` 不是字符串时，记的 warning 也用 `factory_issue_polish_bad_param` 这个事件名。设计 §5 就是这样写的，只是以后按这个事件名统计「参数有误」的次数时，要先把 `reason=issue_no_ignored` 筛掉。

5Why 的过滤条件是 `all(isinstance(x.get(k, ""), str) …)`：缺键时默认值是 `""`，判断通过，于是 `{}` 会留成 `{"question": "", "answer": ""}`。到 P3/P4，这样的项会以「问：（空）答：（待答复）」的形式进提示。这段写法和实测工具一模一样，r2 没碰到；但设计 §5 的表和 `POLISH_EXT_SCHEMA` 的描述都说这种项应该丢掉。照规矩第 3 条，逻辑不必改，设计要跟着写清楚。

### 规则槽位的占位解析

占位解析不检查初始六种栏目在不在、原文格式改没改，也不查栏目代码重复（`field()` 取第一个）。现在的版本只会答 `POLISH_FAILED`，所以没有实际影响。以后 P1 加严校验后，P0 期间传上去的不合格文件会在 `load` 时回退到内置默认，并记一条 `factory_issue_config_fallback`。另外，`_limit` 和「原文长度上限」用 `isdigit()` 判断后再 `int()`：遇到「²」这类字符，`isdigit()` 为真、`int()` 却抛原生 `ValueError`，这个异常绕过了 `ConfigFormatError` 的中文报错（confirmed，P1 修）。
