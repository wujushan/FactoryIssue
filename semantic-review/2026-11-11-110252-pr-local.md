# 对话框里说「润色」时引导到问题单页面（AI 润色 G4b P5）

`run_turn` 在判空之后、判「三域都无权」之前加了一个代码分支：问句里含「润色」两个字，就答固定的引导语 `errors.POLISH_IN_CHAT`，有可查的域时附能力介绍的 3 个按钮（`greeting.buttons`），然后返回。这一轮不规划、不取数、不调模型（答后建议那次也不调）、不写工作区。判断与答法放在 `turn/greeting.py`，与寒暄、能力介绍放在一起。`DESCRIPTION`、`KEYWORDS`、`intents`、规划提示、能力介绍都没有改。设计 §13.3 补了实现说明，任务单更新了 P4、P5 两行。

Watch for：「只要含润色两个字」的误伤面在设计里没写成取舍（possible，影响小，见下文）；三域都无权那条单测没断言「不调模型、不取数」（confirmed，非阻塞）。

**Verdict**: APPROVED

## High-level view

分支位置符合设计 §13.3。`access is None` 时，函数在判空之前就答 `ACCESS_UNAVAILABLE` 并返回。空问句先由 `is_blank` 接住，所以「？？？」照旧答没看懂。新分支在 `access.none` 之前，所以三域都无权的用户问润色得到的是引导语，而不是「请先申请」。这时 `buttons` 返回空列表，也就不发 `suggestions` 事件。按钮沿用 `buttons` 的 `{id,name,label,query}` 对象，形状与能力介绍一致。

不带「润色」的轮次与 HEAD 逐字一致。改动只是在现有分支之间插入一个纯子串判断，命中就返回。没命中时，后面的代码、规划提示和 manifest 素材都没动。规划对照集与 116 条 golden 里都没有「润色」（已 grep 核对），所以不用重跑规划对照集，这个判断成立。「改写」「优化措辞」照旧走规划，有单测覆盖。

误伤面很小。本域是 POS 终端的制程质量问题，「润色」不是缺陷用语。`2_landed`（术语表、问题类型说法、主题说法）除润色文档外没有这个词，golden 与规划对照集里也没有。真实问句里能想到的命中有三类：用户问 AI 润色功能本身（如「AI润色按钮点了没反应」），这时引导语方向对，但帮不了排障；缺陷描述里偶然出现这个字串，例如「浸润色差」，属于构词巧合；模型生成的答后建议里带了这个词，点了会被引导而不按存下的计划执行。三类的后果都是一句引导语加三个按钮，用户换个说法就能继续，不会出错数、也不越权。§13.3 只写了「含「AI润色怎么用」这类问用法的」，建议补一句取舍：按子串判断、接受极少数查数据问句被误引导，不另做语义判断。

### 分支顺序与相邻路径

```
gate.resolve ──None──▶ ACCESS_UNAVAILABLE（fatal）
     │
is_blank ──是──▶ 没看懂 + 按钮（无权时无按钮）
     │
asks_to_polish ──是──▶ POLISH_IN_CHAT + 按钮（无权时无按钮）   ← 新
     │
access.none ──▶ 寒暄则能力介绍，否则请先申请
     │
读历史、工作区、规划……
```

「AI润色怎么用」同时命中 `is_greeting` 的「怎么用」。新分支在前，所以答的是引导语，不是能力介绍，与 §2.3、§13.3 一致。这一轮不动工作区：上一轮留下的 `pending_clarify`、`suggest`、`last` 原样保留，下一轮照旧能直填或接上一轮的计划。寒暄路径也是这样。

`asks_to_polish` 对原始问句做子串判断，不做 `_bare` 规整。所以「潤色」（繁体）、「润 色」（中间有空格）、英文 polish 都不会命中，会照旧走规划。漏判的后果只是走现有路径。

### 测试覆盖

`tests/test_polish_chat.py` 覆盖了这些情形：四种含润色的说法（含只有「润色」两个字、问用法），断言事件序列、按钮与 `greeting.buttons` 相同、不调模型、不发 SQL、不写工作区；三域都无权时不给按钮；`access is None` 时先答 ACCESS_UNAVAILABLE；空问句先答没看懂；「改写」「优化措辞」调了一次规划。护栏加了两条场景。本机重跑这两个文件 25 条全过。

没有测到的：三域都无权时的不调模型、不取数（见 Issues 第 2 条）；上一轮留下 `pending_clarify` 时说润色，下一轮仍能直填。后者与寒暄路径相同，可以不补。
