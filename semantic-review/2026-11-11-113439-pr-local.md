1. **润色轮超时会中断整次回归**：`DEFAULT_TIMEOUT` 180 秒小于设计 §4 的最坏耗时（约 4 分钟）。`httpx.ReadTimeout` 没有按单条用例处理，会让 `run()` 停掉剩下的用例。建议在 `run_case` 里把 `httpx.TimeoutException` 记成本条失败，或者跑润色样例时放宽超时（例如 300 秒）。在测试环境用 `--jobs 4` 跑之前改。

### 一轮润色的耗时与回归脚本的超时

`/test/chat` 等整轮跑完才返回 JSON，所以 httpx 的读超时就是一轮的总时长上限。一轮润色最坏是第 ⑥ 步两次各 110 秒的调用加上 10 秒的查库，约 230 秒，设计 §4 自己也写「最坏约 4 分钟」。§12.3 的实测在两条长文同时生成时出现过 85、113、120 秒的慢调用，而 `--jobs 4` 正好会制造这种并发。超时异常在 `run_case` 里不被捕获，经 `future.result()` 传到 `run()`，`run()` 把 `stop` 置位、取消剩下的用例后再抛出；`main()` 只处理 `KeyboardInterrupt`，结果是打出一段 traceback。已打印的结果还在，但后面的用例都不跑了，汇总行也没有。golden 单轮很少超过 180 秒，以前碰不到这个问题；P6 让脚本开始跑润色样例，才把它暴露出来（likely：机制已确认，触发要等模型变慢）。

### `error_code` 与 `no_error` 的组合

```python
want_code = expect.get("error_code")
if expect.get("no_error", not want_code) and body.get("error"): ...
if want_code: ... if got_code != want_code: failures.append(...)
```

本机按各种写法跑过一遍：只写 `error_code`，或同时写 `no_error: false`，代码对上就过，代码不同、没报错都判失败，失败信息里同时有实际值与预期值。只写 `no_error: false`、不写 `error_code` 的旧写法不变，报不报错都不判。`error_code: ""` 当作没写。`no_error: true` 加 `error_code` 时，代码对上也会报「模块报错」，在 `load_cases` 里也没有提示。守卫的 `case["expect"].get("no_error") is False` 让润色样例写不出这种组合，其他用例集只靠作者自己注意（confirmed，非阻塞）。

### 数字断言的负向实测与未测链路

把照抄结果中标签外文字里的数字全删掉，每条带数字的 `answer_preserves` 都报缺失，只有 PL-03 的 `"2"` 例外（见 Issues 第 3 条）。

Not tested：`qa_test` 经 `/test/chat` 带 `ext_param` 的完整链路。本机只验了 `POST /v2/tasks`，`/test/chat` 要等测试环境的 api-key 才能跑。文档说 `/test/chat` 的 `error` 是 `{code, message, fatal}`、`answer` 只含 delta，脚本按这个写法实现，但还没有实际跑过；第一次在测试环境跑时注意 `error.code` 是不是模块原样发出的代码。
