## High-level view

rich.py 和 check.py 是从 HEAD 版 polish_core 搬过来的。18 个函数去掉 docstring 与类型注解后比 AST，16 个完全相同。剩下两个的差别是：`assemble` 里的 `"表"` 换成了常量 `TABLE_KIND`；`check` 的栏目名改由参数 `field_name` 传入，上限从 `prep.limit` 取，转接层传入的值与原先相同。另跑了 20,000 条随机请求，比较两版的 prepare、提示、检查与修改说明，没有任何差异。

实测工具的参数解析改成调用 `params.parse` 后，继承了 P0 的一条规则：问与答都为空的 5Why 项要丢掉。HEAD 版工具保留这种项，提示「已有的 5Why」里会多一项「问：''，答：（待答复）」，`dropped` 也会少算一项。r2 样例里没有这种项，所以 r2 结果仍然有效。但任务单 P2 行「提示全部相同」的说法只对样例成立。

设计稿 §9 有两处写法与代码不一致。P2 往 §6.1 补了两条实测工具的既有行为，这两处没有一起补。一处是分条序号，设计稿写「结果里每行开头、范围 1 到行数」，代码是原文和结果都去掉每行开头的 1–2 位序号，不看行数。另一处是第 7 项，设计稿写「原文没有汉字时」，代码要求原文没有汉字并且有英文字母。

单测基本覆盖了 §12.1 列的场景。有两处只测了拆，没测拼和检查：未闭合标签的往返，以及第二套标记 `⟦图1⟧`。我在临时目录里试过，这两条路径现在都是对的，缺的只是断言。

### 设计稿 §9 与代码的两处差异

P2 往 §6.1 补了两条实测工具的既有行为：表格的占位后面不另起一行，判汉字只认基本区。§9 里还有两处同类差异没有补。

第一处是分条序号。设计稿写「结果里每行开头的 `1.`、`2、`、`（1）`、`①` 这类序号不算多出的数字，范围是 1 到结果的行数」。`facts()` 实际做的是：对原文和结果都用 `_NUMBERING` 去掉每行开头的 `\d{1,2}` 序号，不看行数。实测：

```
原文 "<p>治具松动</p>"，结果 "99. 治具松动"  →  ok=True
```

原文那一侧也去掉序号，意味着原文自带的「1、」「2、」被模型删掉时，第 4 项不会报缺少。这多半是有意的：允许模型重新编号。序号后面紧跟数字时（`10、20台`）`(?!\d)` 不让去掉，所以真实的数量不会被漏判。这一点实测过，「10、20台不良」去掉 10 时第 4 项报了缺少。问题只在设计稿的描述，应改成代码的实际行为。

第二处是第 7 项。§9 表格写「原文没有汉字时，结果里也没有汉字」。代码的条件是 `english_only(原文)`，也就是没有汉字并且有 ASCII 字母。原文只有数字和符号时不做第 7 项：

```
原文 "12345 / 678"，结果 "一二三四五"  →  failed = ['4 缺少']（没有 '7 语言'）
```

§1.2 已经写了 `english_only` 由提示的「原文语言」和第 7 项共用，§9 表格这一格应写成同一个条件。

### §12.1 富文本、检查两条的覆盖

富文本那条要求的外链与 base64 图片、表格（含嵌套）、链接、`&nbsp;`、列表、判空、判长（含 base64 不计入、`ignore_cap`）、K（富文本与纯文字两种算法、K ≤ 0）都有断言，而且确实在测各自声称的内容。例如 `test_numbers_compare_by_value_and_fullwidth` 如果去掉全角转半角，`１２` 会以原样的全角数字进集合，测试会失败，所以它确实测到了转换。

「未闭合标签的拆与拼往返」只测了一半：参数化用例断言了 `text` 和 `tokens[0]`，没有调 `assemble`。「占位换写法」也只测到拆，没有一条用例让 `check` 或 `assemble` 处理 `⟦图1⟧`。如果以后有人在 `check` 里把 `mark_re(split.style)` 误写成固定的 `BRACKET`，现有单测发现不了。我在临时目录里试过，这两条路径现在的结果都对：未闭合 table 能拼回原文；第二套标记的检查通过，图片按原样拼回。

检查那条要求 §9 每项都有通过与不通过的例子，外加汉字数字、`01` 与 `1`、分条序号、英文为主的原文，这些都有。第 5 项的短原文用例 22 字过、23 字不过，正好卡在「原文加 20 字」的边界上。比例的两个端点（正好一半、正好两倍）没有专门的用例，§12.1 也没有要求。
