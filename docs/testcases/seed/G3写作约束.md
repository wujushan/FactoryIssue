# G3 写作约束：业务行为 vs 实现形状

> 用途：G3 写 golden 用例、人工手册、参考 SQL 时的统一约束，避免把「实现长什么样」写成验收标准。
> 适用：制程问题查询助手（FACTORY_ISSUE）G3 全部产物；评审时逐条对照。
> 版本：v1.3（2026-10-26）；2026-10-28 随案例集 v1.0 冻结。此后变更需在缺口报告里留记录。

## 一、三条总则

1. **只写业务行为，不写实现形状。** 写「必须覆盖什么、口径是什么、不得出现什么」，不写「几次调用、走哪个工具、事件怎么发」。`2_landed` 已定的呈现（总述「回答怎么组织」「什么时候配图」：分段顺序、分几张表、配不配图与图型、前 10 名、导出阈值）是业务行为，可以写。
2. **预期按口径写，不按快照写。** 不写「某天 137 条」；需要精确值时，用参考 SQL 现取并注明取数日期。
3. **一条只考一个变量。** 多意图拆成子意图分别写预期，失败时能定位到哪一段。

## 二、必须写（业务硬约束）

这些来自 `docs/2_landed/`，是验收的硬标准，写不进案例就是漏测：

| 类别 | 必须写清 |
|---|---|
| 域与权限 | 点明域只查该域；没点明三域分别查，所以单域页的问句必须点明该域（或用带前缀的单号）；无权域写「无权限，未计入」，不说成「没有数据」 |
| 时间 | 默认按建单时间；问停线/重启/结案/发现时按对应日期（「停过线的单」按停线日期）；起止日期；某日期没填的单不计入并写明张数；汇总统计没给时间要先追问，问句里要么给时间、要么预期写追问 |
| 口径 | 问题类型、状态、责任归属部门、不良率、汇总不良率、结案周期、停线中、问题等级、系列、机型、PN、料号、「其他」三分法 |
| 清单 | 默认 6 列（问题编号/机型/问题类型/不良率/不良数量/问题描述）；用户点名了列就按点名 |
| 跨域 | 按域分表；先各域小计再合计；三域枚举不合成一张 |
| 文字检索 | 关键词「和/或」、话题三组（问题本身涉及/处理中提到/可能相关≤10）、类似问题不保证完整、点名了字段只在该字段找 |
| 统计 | 结尾必附「统计口径」；一单多值维度各计一次并写明 |
| 呈现 | 业务列名；不出现表名/字段名/数据源别名/自增 ID；枚举翻人话；空值写「未填」；业务标识给全 |
| 交互 | 必要澄清项；只读边界（不填单、不改状态、不审批、不上传）；寒暄报三域能力 |
| 语义 | 必须给应命中集或明确标「待基线」；没基线只能验行为，不能验「找得准不准」 |

## 三、不许写（实现形状）

| 不许写 | 反例 | 换成 |
|---|---|---|
| 表数/表标题（业务另有规定的除外） | 「必须返回 3 张表，每域一张」 | 「三个域的结果都要出现；某域无数据要写明 0 张」 |
| 列顺序 | 「列顺序必须是 A、B、C」 | 「列里必须包含 A、B、C」 |
| 图表类型（`2_landed` 初步分析维度指定了图型的除外） | 「必须是饼图」 | 「若配图，类型在 [pie,bar]」（分布类按 2_landed 对应图型） |
| 与 `2_landed` 默认值不同的 N | 「必须给 Top 5」 | 按总述「回答怎么组织」写「先点名第一，再给前 10 名，并列的都列出」；10 是默认值，注明管理员可改 |
| 与 `2_landed` 默认值不同的导出阈值 | 「超过 50 条就导出」 | 按总述写「某域超过 100 张导出、表格给最近 20 张」；注明管理员可改 |
| 工具/函数/调用次数 | 「必须先调 retrieval 再调 stats，共 3 次」 | 「取数路径：结构化 + 语义；两段结果都要出现」 |
| SQL 形态 | 「必须是 SELECT … LEFT JOIN …」 | 参考 SQL 单独写，案例里只写口径 |
| 事件序列/流式顺序 | 「必须先 progress 再 table」 | 「最终产物里有表/图」 |
| 模型/温度/token/耗时 | 「响应必须 <3 秒」 | 不写（平台侧指标，不进业务验收） |
| LLM 措辞 | 「开头必须是『根据您的问题』」 | 只做包含/排除断言（如「统计口径」必在） |
| 数据快照 | 「2026 上半年共 221 条」 | 「按口径现算；合计=分项之和」 |
| 未定设计 | 「多意图合并成一张表」「澄清一律先问」 | 写进「待定清单」，交 G4a |

## 四、每条案例的标准结构

```
编号 / 级别 / 结果形态 / 取数路径 / 验证方式
问句（用户原话，不夹账号、上下文说明）
前置（会话上下文、账号类型、种子复核，取工作簿「前置」列）
期望行为（按 2_landed 的口径，一段话）
数据断言（表列、行数下限、数值关系、图表点数）
呈现断言（必含词、禁含串、最小长度、链接）
不写什么（这条明确不锚的实现细节）
失败分层（路由 / 取数 / 数字 / 呈现）
```

示例（CN-001）：

- 问句：`2026 年 6 月国内 A920PRO 的软件制程问题都有哪些？`
- 期望行为：建单时间 6/1–6/30；机型完整匹配 A920PRO；类型=软件问题；只算未删除；默认 6 列、按建单时间倒序。
- 数据断言：首表列包含「问题编号」「机型」「问题类型」「不良率」「不良数量」「问题描述」；不含 `ID`、`IsDelete`；至少 1 行。
- 呈现断言：正文含张数与「统计口径」；不含 `dbo.`、表名、字段名。
- 不写：表必须 1 张、列顺序、SQL 形态。
- 失败分层：没路由到本模块→路由；`query_count=0`→取数；单号集合不对→口径；表里出现字段名→呈现。

## 五、按验证方式写

| 验证方式 | G3 写什么 | 不写什么 |
|---|---|---|
| A 真实数据 | golden + 人工手册；可做数据断言 | 快照数字 |
| B 单测夹具 | 人工手册只写行为；在 G4b pytest 里用 fake ctx + 构造数据 | golden 用例、数据断言 |
| D 待设计（目前为 0） | 人工手册只写业务行为 | 呈现断言（表数/图型/顺序/Top N） |
| E 权限账号 | 人工手册写账号、步骤、预期范围 | golden、数据断言 |
| 占位符未替换 | 标「待替换」 | 具体单号/数值断言 |
| 人工判据（如「措施只来自原记录」） | 人工手册：对照 trace 原文逐条看 | golden 断言 |

## 六、多意图与依赖怎么写

写三样：**子意图、作用域、失败分层**。

示例（XC-021）：

- 子意图：I1＝今年 A8900 的清单；I2＝其中停过线的张数。
- 作用域：I2 继承 I1 的时间与机型，只追加「停过线」；I1 为空时 I2 答 0 并说明。
- 断言：I1 张数与 I2 张数都出现；I2 ≤ I1；说明「I2 是 I1 的子集」。分段、各带小标题、按提问顺序，是总述「回答怎么组织」已定的呈现，可以写。
- 不写：先调哪个工具、工作区里存条件还是存单号。

禁止写法：「必须先查清单再查停线」「必须先调检索再调统计」。

## 七、语义检索怎么写

- **话题**：写三组、所用说法、应命中集（或「待基线」）；断言三组张数与分组归属。
- **类似问题**：断言「不保证完整」、结果≤10、按相近程度、带回原因与措施；不锚具体名次与分数。
- **关键词**：写「和」还是「或」；断言命中的词都在；剥图后再匹配。
- **点名字段**：写字段范围、按词找全 + 按意思补充；断言补充项标注。
- **10 字门槛**：只约束按意思找，不约束按词找；两条要分开写。
- **不写**：相似度分数、具体排序名次、embedding 模型名。

## 八、参考 SQL 怎么写

**写**：参数化（时间/机型/工厂/类型等占位）、只读、按 `source` 分实例、跨实例在应用层关联、聚合尽量下推、日期参数化、附「对应断言」与取数日期。

**不写**：`SELECT *`、写死某天数据、跨实例 JOIN、把某次 LLM 生成的 SQL 当参考、带业务数据行的结果集。

跨实例示例：国内工厂在 `erp`，问题单在 `info`，参考 SQL 只写单实例部分，工厂名称在应用层关联。

## 九、断言词表怎么用

- **golden**：`module` / `no_error` / `min_queries` / `tables`（列、行数下限、禁列）/ `charts`（分组 2 组及以上必须配图，类型按 `2_landed`「什么时候配图」）/ `clarify` / `answer_contains` / `answer_not_contains`。长度、点数这类阈值 `2_landed` 没有，不写。
- **人工手册**：在 trace 里看 SQL 条件与结果集、权限范围、链接可点、导出文件表头与全量行数。
- **优先关系断言**：合计=分项、分域小计=总、筛选后行数≤筛选前、换个问法结果一致；绝对数字只在有参考 SQL 时用。
- **列名唯一来源**：`2_landed/db_description/` 的「用户可见显示名」+ `glossary.md`；不得即兴翻译。

## 十、评审八问

1. 这条考哪个变量？一句话说不出来就是没想清。
2. 预期能不能从 `2_landed` 推出来？推不出来就是缺口径。
3. 有没有写表数/图型/顺序/调用次数？有就删。
4. 数字是按口径还是按快照？快照就改成关系断言。
5. 验证方式是 A/B/D/E 哪一种？B/D/E 有没有误写成 golden？
6. 失败时能不能定位到路由/取数/数字/呈现？
7. 呈现断言是不是只用了业务名、禁含串是否覆盖表名字段名？
8. 与已有案例是不是重复？差异有没有写进备注？

## 十一、变更与冻结

- v1.0 冻结后，新增案例走追加；修改要写原因与影响面，并在缺口报告留记录。
- 待定项已定（决策 2026-10-26「回答组织方式默认值」），呈现断言按 `2_landed` 写；不得反过来用案例倒逼设计。
- 应命中集复核后由 v0 升 v1；未复核的话题在案例里保持「待基线」。种子案例集只提供候选，不作为预期的依据。
- 种子的要求与 `2_landed` 不一致、或 `2_landed` 没写时，按 `2_landed` 写，并把分歧列进 `docs/open-questions.md`。
- 数据基线、账号、单号映射变化时，同步更新案例的「验证方式」列。
