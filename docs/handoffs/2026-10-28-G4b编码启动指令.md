# G4b 编码启动指令

把本文件整份当作任务。你负责制程问题查询助手（模块编码 `FACTORY_ISSUE`）的 G4b：照设计稿写代码。G1–G3 已关闭，G4a 设计稿已评审通过。

G4b 分 8 片（S0–S7），要多次会话做完。分片、每片的范围与完成标准、进度都在 `docs/handoffs/2026-10-27-G4b编码任务单.md`（下称「任务单」）。本文件只管怎么起步和守哪些规矩，不重复任务单。

## 要交付什么

- 本次会话：做任务单「进度」里第一片还没完成的（新开时是 S0），做完按任务单「每片的收尾」自查，更新任务单「进度」，停下来交开发者评审。一次会话只做一片，除非开发者让你接着做。
- 依据只有一份：`docs/decisions/2026-10-27-模块技术设计.md`（下称「设计」）。代码偏离设计时，在同一次改动里改设计；与业务口径冲突时先改 `docs/2_landed/`，必要时列进 `docs/open-questions.md` 问开发者。

## 规矩

- **口径以 `docs/2_landed/` 为准**，代码里不抄第二份：显示名、术语、示例问题、说法清单、部门简称、地区说法都在导入时从 `2_landed` 解析（设计 §2.3）。
- **SDK 不臆造**。签名以 `docs/dev/02-sdk-reference.md` 与 `.venv/Lib/site-packages/forge_*` 的源码为准。拿不准的写不连库的脚本实测（放 `$env:TEMP`），结论写回设计并注明版本。导入 `forge_platform.bus` 一类模块时用 `uv run --with greenlet python <脚本>`。
- **不连库，不碰真实数据**。单测只用假数据（设计 §15 的假 `ctx`，假数据照 `docs/testcases/seed/单测夹具清单.md`）。要在内网验的，写成脚本或列出 golden 用例 id，交开发者执行，只回计数与断言结果。
- **红线照 AGENTS.md「硬约束」与「答案呈现规范」**，设计 §15 的护栏测试从 S0 起每片都跑：不露表名字段名、`handle()` 不算数、不用 `ctx.data.query(` / `.raw(`、按钮是对象、只有一条 system。
- **测试包不带 mart 声明**：S6 之前不声明 `forge_mart_factory_issue` 别名、`vectorize`、`jobs()`（设计 §2）。
- **只读的目录**：`docs/1_user_input/`（可读，不改、不引用其中文件路径）、`docs/dev/`（平台文档快照）、`docs/testcases/`（G3 已冻为 v1.0，要改先问开发者）。`docs/reviews/` 可能有评审者新追加的内容，动之前先 `git diff` 看。
- **不提交、不打 tag**。开发者说「整理提交」时再提交，`docs/1_user_input/` 下的新文件与 `docs/decisions/2026-10-26-G1初版之后口径变更原文汇编.md` 不提交。
- 发现 SDK 缺能力或文档错误：按 AGENTS.md「平台 SDK 协作原则」写 `docs/platform-feedback/`，不在业务仓静默绕开。

## 第一步：开工前核对，有问题先停下来问

1. `git status` 与 `git log --oneline -5`：确认分支是 `fi-g4b`、工作区里没有别人未提交的改动。
2. `uv sync` 后看 `paxsz-forge-core` / `-data` / `-platform` 的版本是否仍是 0.3.7 / 0.3.2 / 0.3.7（任务单「开工前提」最后一项）。变了就先读 `docs/dev/` 里相应的变更，列出设计里依赖那条行为的几节，交开发者定要不要改设计，再开工。
3. `docs/open-questions.md`「待确认」为 0 项（否则 guard 会拦 `src/`）。
4. `uv run ruff check src tests`、`uv run pytest` 先跑一遍，记下基线（2026-10-28 为 9 个通过、4 个跳过）。
5. `src/factory_issue_module/module.py` 现在是模板骨架，S0 照设计 §1.4、§2 重建；`tests/` 里已有的契约测试与 `test_qa_assertions.py` 是模板与 G3 的，保留并保持通过。
