## 1. 一句话

用户每问本助手一个问题，平台就带着这个用户的 token 调一次 `GetPrivilegesByCode?Code=FACTORY_ISSUE`。请按用户申请了哪几个域（国内、巴西、海外）和是否申请了 CAR 报告，在 `Data` 里返回一份「默认拒绝、只列已申请的表」的权限对象；表名、位置、写法照第 4、5 节逐字写，各种组合的完整返回见第 6 节。

本文只讲这个接口返回什么。助手树（`GetAgentMenu2`）与前端调用不在本文范围。

## 2. 平台怎么调、怎么读返回

**调用**：用户的问题路由到本助手之后、本助手开始处理之前，平台调一次（同一轮内不重复调）：

```http
GET {INFO 地址}/api/AIAgentAuth/GetPrivilegesByCode?Code=FACTORY_ISSUE
Authorization: Bearer <该用户的 INFO token>
```

平台默认等 10 秒，超时按失败处理。返回的权限只对这一个用户、这一轮生效，下一轮重新拉。

**返回的外壳**：

```json
{ "Status": true, "Code": 200, "Message": "", "Data": { ...权限对象... } }
```

**平台怎么判读**：

| 返回 | 平台的处理 | 用户看到 |
|---|---|---|
| HTTP 不是 200、超时、不是 JSON | 本轮拒绝 | 提示稍后再试 |
| `Status` 不是 `true`（也认字符串 `"true"`），或 `Code` 不是 `200`（也认 `"200"`） | 本轮拒绝 | 同上 |
| `Data` 为 `{}` 或 `null` | 当成「本助手不做数据管控」，**全部放开** | 三个域和 CAR 报告全能看。**本助手禁止这样返回** |
| `Data` 是对象，但 `dataScope` 是单个对象（v1.0 旧写法） | 本轮拒绝 | 提示稍后再试 |
| `Data` 是 v1.3 权限对象 | 按它判断每张表能不能查 | 见第 6 节 |

`Message` 只在失败时进日志，成功时写什么都行。`dataScope` 里 `type` 为 `KB` 的项平台会丢掉，本助手不用知识库，不必写。

## 3. 业务规则

- 三个域（国内、巴西、海外）分别申请，申请通过才能看。国内的 CAR 报告（纠正预防措施报告）另外单独申请。**没配置就看不到**。
- 因此权限对象一律用**默认拒绝**：`defaultEffect` 写 `DENY`，只列出该给「允许」的表，没申请的不列。漏列一张表的后果是那张表查不到，不会放开。
- 级别 `level.code` 总是写 `A`。本助手有权的域内可看全部数据，不按部门、个人再切。
- 除流程待办任务表的一条固定规则外，不下发任何行级、列级规则。
- 一个域都没申请的用户，不应把本助手授权给他。万一这类用户还是调到了这个接口，也**不要返回空权限**（空 = 全部放开，见第 2 节），按 6.9 返回。
- 本助手每轮开头先看三张主表和 CAR 报告表能不能查，据此决定查哪些域。用户问到没申请的域，回答里写「无权限，未计入」，不会说成「没有数据」。

## 4. 权限对象怎么写

### 4.1 顶层

```json
{
  "version": "1.3",
  "defaultEffect": "DENY",
  "level": { "code": "A", "description": "可访问全部数据库数据" },
  "dataScope": [ ...每张最外层表一项... ]
}
```

`level.description` 可不写。`dataScope` 不能为空数组：带级别 A 却一张表都不列，等于全部放开。

### 4.2 三种表项

**① 主表**（带本域子表）。主表自己显式写「不限行、不屏蔽列」；子表挂在 `sub_tables` 里，写 `inherit_parent: true` 和关联列，省略 `row`：

```json
{ "type": "DB", "table": {
    "name": "info.CoreINFO.dbo.ZCTracking_ProblemList", "mode": "ALLOW",
    "row": { "mode": "DENY", "logic": "OR", "rules": [] },
    "column": { "mode": "DENY", "rules": [] }, "cell": {},
    "sub_tables": [
      { "name": "info.CoreINFO.dbo.ZCTracking_ProblemSteplog", "mode": "ALLOW", "inherit_parent": true,
        "relation": { "mappings": [ { "parent_field": "ID", "child_field": "ProblemId" } ] },
        "column": { "mode": "DENY", "rules": [] }, "cell": {}, "sub_tables": [] }
    ] } }
```

**② 最外层的普通表**（查表、共用主数据、CAR 报告表、文字查找表）：

```json
{ "type": "DB", "table": {
    "name": "info.info.dbo.Employee", "mode": "ALLOW",
    "row": { "mode": "DENY", "logic": "OR", "rules": [] },
    "column": { "mode": "DENY", "rules": [] }, "cell": {}, "sub_tables": [] } }
```

**③ 流程待办任务表**。这张表全公司共用，只放行本助手用到的两类国内制程问题待办（效果确认、预防对策确认）。这条规则对所有申请了国内的用户都一样：

```json
{ "type": "DB", "table": {
    "name": "info.info.dbo.tbTask", "mode": "ALLOW",
    "row": { "mode": "ALLOW", "logic": "OR", "rules": [
        { "logic": "AND", "conditions": [
            { "field": "ftable", "operator": "IN",
              "value": ["ZCTracking_ProblemSoftware3", "ZCTracking_PreventionConfirm"] } ] } ] },
    "column": { "mode": "DENY", "rules": [] }, "cell": {}, "sub_tables": [] } }
```

规则里的字段名逐字写 `ftable`（全小写）。写成别的名字，取待办任务时整条查询会被拒。

### 4.3 必须逐字遵守的几点

1. **表名是四段**：`实例.库.架构.表`。INFO 实例写 `info`，ERP 实例写 `erp`，本助手产物库写 `mart`。库、架构、表名的**大小写**照第 5 节逐字写。大小写不对，那张表就匹配不上，按「没列」处理，也就是拒绝。
2. **同一张表只能出现一次**。重复出现时整份权限作废，用户每一轮都得到「暂时无法确认您的查看权限」。几个域共用的表因此只能放最外层。
3. **每张列出的表都写 `mode`**。不写时按默认效果，也就是拒绝。
4. 主表和最外层表都写 `row`、`column`，值照上面的样子；`row` 或 `column` 写了却不带 `mode` 会出错（见第 7 节）。
5. **关联列逐字是物理列名**：国内 `ID` → `ProblemId`，巴西 `ID` → `ProblemID`，海外 `Id` → `ProblemId`。平台把它直接拼进查询，不做任何映射。
6. 子表放在本域主表的 `sub_tables` 里，不要放到最外层。

## 7. 常见写错与后果

以下各条都按平台的实际解析与取数判定核对过（不连库），对回答的影响按本助手的处理方式写出。「整份作废」指这份权限无法使用，用户每一轮都得到「暂时无法确认您的查看权限，请稍后再试」。

| 写法 | 后果 | 严重程度 |
|---|---|---|
| `Data` 返回 `{}` 或 `null` | 当成不做管控，三个域和 CAR 报告全部放开 | 越权 |
| `dataScope` 为空数组或不写 | 同上，全部放开 | 越权 |
| `defaultEffect` 写成 `ALLOW`，却只列了已申请的表 | 没列的表全部放开：没申请的域、CAR 报告都能看 | 越权 |
| 一个域都没申请的用户，返回「默认拒绝 + 不列任何表」 | 等于「dataScope 为空」，全部放开。正确写法见 6.9 | 越权 |
| `type` 写成小写 `db` 或别的值 | 整份作废 | 用不了 |
| `dataScope` 写成单个对象（v1.0 旧写法） | 本轮拒绝 | 用不了 |
| 表名不足四段，或某一段为空（如 `.forge_mart_factory_issue.public.domestic_issue_text`） | 整份作废 | 用不了 |
| 同一张表出现两次（如人员表在两个域下各列一次） | 整份作废 | 用不了 |
| 子表缺 `relation` 或 `mappings` 为空 | 整份作废 | 用不了 |
| 库名、架构名或表名大小写不对（如 `info.coreinfo.dbo.ZCTracking_ProblemList`） | 那张表匹配不上，当成没列，即拒绝。主表写错 = 整个域看不到 | 查不到 |
| 主表写到了别的库（如 `info.info.dbo.ZCTracking_ProblemList`） | 同上 | 查不到 |
| 列出的表没写 `mode` | 按默认效果拒绝这张表 | 查不到 |
| `row` 写了但没写 `mode` | 这张表一行都查不到；写在主表上时，整个域查不到任何单 | 查不到 |
| `column` 写了但没写 `mode` | 这张表一查就报错，回答里那一部分写「暂时没查到」 | 报错 |
| `column.rules` 里列了任何字段 | 本助手没有列级管控的对应关系，查这张表就报错 | 报错 |
| 主表或其他表上带了行规则（如按部门） | 本助手没有这些字段的对应关系，查这张表就报错 | 报错 |
| 待办任务表规则的字段不是逐字 `ftable`（如 `fTable`） | 取待办任务时报错，国内单的处理进度给不全 | 报错 |
| 待办任务表规则里的业务表名与 4.2 ③ 不一致 | 本助手取不到它要的两类待办，国内单的当前状态和当前责任人会不准 | 结果不对 |
| 漏列某张该给允许的表（如人员表、待办任务表） | 用到这张表的查询被拒；本助手以拒绝为准，相关的域在回答里会被当成「无权限，未计入」 | 查不到 |
| 漏列某个域的文字查找表（3 张缺任何一张） | 这个域按关键词、按意思找单时回答「暂不可用」，其余查询照常 | 部分功能不可用 |
| 关联列只差大小写（如 `id` → `ProblemId`） | 库不区分列名大小写时能用，否则取数报错。请照第 4.3 节逐字写 | 可能报错 |
| 待办任务表不带那条固定规则 | 结果不变（本助手取数时自己也带同样条件），但不符合规格 | 不符合规格 |
| 不写 `defaultEffect` | 平台按 `DENY` 处理，结果对，请仍写明 | 不符合规格 |
| `level` 不写或不是 `A` | 平台不检查这一项，结果不变；规格要求总是 `A` | 不符合规格 |
| 主表或最外层表不写 `row`、或不写 `column` | 目前当成不限行、不屏蔽列，结果对；按协议应写明，请照写 | 不符合规格 |
| 子表不写 `inherit_parent: true`，或放到了最外层 | 当前结果不变，但主表被拒时子表不会跟着被拒 | 不符合规格 |
| 实例段写成别的值（如 `INFO.CoreINFO.dbo.ZCTracking_ProblemList`） | 目前仍能匹配（平台只比后三段；产物库的表只比表名），请照写，以免平台以后改成按全名比 | 不符合规格 |
| 多列了本助手不用的表，或带了 `type: KB` 的项 | 忽略 | 无影响 |

## 8. 备选写法：默认允许

只有权限平台的生成规则**只能**用默认允许时才用这种写法。两种写法下本助手的行为相同，区别在配置出错时的后果：默认拒绝漏列一张是「查不到」，默认允许漏列一张是「放开」。

规则：

- `defaultEffect` 写 `ALLOW`，41 张表**全部列出**，不能省略任何一张。
- 该给允许的照第 4 节写。不该给允许的最外层表写 `"mode": "DENY"`（不用写 `row`、`column`）。
- 没申请的域，主表写 `DENY`，**子表照样挂在它下面**（`inherit_parent: true`），靠继承随主表一起被拒。只写主表、不挂子表的话，那几张子表就成了「没列 = 允许」。

### 9.2 步骤

1. **INFO 自测接口**：用甲、乙、丙的 token 各调一次，确认返回与 6.1、6.2、6.3 一致（顺序可以不同）：

   ```bash
   curl -s "{INFO 地址}/api/AIAgentAuth/GetPrivilegesByCode?Code=FACTORY_ISSUE" \
        -H "Authorization: Bearer <账号的 token>"
   ```

   丁不应该在助手入口看到本助手。万一调到这个接口，确认返回与 6.9 一致，不是空权限。

2. **把返回结果发给制程助手业务仓**：保存成 JSON 文件，文件名写上账号，比如 `甲.json`。业务仓用自查工具核对，结果会写明：本助手据此放开了哪些域、CAR 报告和按文字找单；41 张表每张实际是「可查」还是「拒绝」；与第 4、5 节的哪些写法不一致。
3. **在联调环境里提问**：用各账号在 INFO 前端问下表的问题，核对回答。

| 账号 | 问句 | 应看到 | 不应看到 |
|---|---|---|---|
| 甲 | 查一下上个月的国内、巴西、海外问题。 | 只给国内的单；开头写明巴西、海外「无权限，未计入」 | 巴西、海外的单或张数；把无权说成「没有数据」 |
| 甲 | 你好，你能帮我查什么？ | 三个域都介绍，巴西、海外注明「申请后可查」 | 只介绍国内 |
| 甲 | 一个 BR 开头的真实单号（如 BR2609001）现在到哪了？ | 只答「您没有该域的查看权限」 | 这张单存不存在 |
| 甲、乙 | 一张关联了 CAR 报告的国内物料问题单号 + 「的 CAR 报告根本原因是什么？」 | 乙：根本原因内容和 CAR 报告链接。甲：「该单关联了 CAR 报告，您没有查看权限，可点链接到报告页面查看」，附链接 | 甲看到报告里的任何内容 |

4. **对不上时**：请平台管理员在管理台的审计页找到这一轮，取出 `permissions.json`，或者在平台日志里找 `info_privileges_body` 那一行。这是平台实际收到的返回，同样发给业务仓核对。

### 9.3 业务仓的核对方法

本节写给制程助手业务仓的开发者。INFO 同学不用执行，只需把返回结果发过来。

```bash

# 生成任意组合的标准返回（--allow-variant 为第 8 节的默认允许写法）
uv run python scripts/privileges_check.py --print 国内,海外

# 核对本文档里的全部示例
uv run python scripts/privileges_check.py --examples docs/handoffs/2026-11-05-INFO权限联调说明.md
```

工具不连库：用平台的真实解析（`parse_privileges_payload`）和取数权限判定（`ScopedDataAccess`）逐张表试查，只记下生成的查询，不执行。退出码 0 表示没有错误且与 `--expect` 一致。结论分三档：「错误」（越权、查不到或报错）、「不符合规格」（现在结果对，但写法与约定不一致）、「提示」。
