# G4a 技术设计启动指令

把本文件整份当作任务。你负责制程问题查询助手（模块编码 `FACTORY_ISSUE`）的 G4a：写出模块技术设计稿。G1（业务口径）、G2（数据源与治理）都已关闭；G3（测试案例集）由另一路同时推进，你不碰它。

## 要交付什么

一份设计稿：`docs/decisions/YYYY-MM-DD-模块技术设计.md`（日期用开写当天），文首状态写「草案，未评审」。它是 G4b 写代码的唯一依据：G4b 偏离它就要回来改它。写完后会像 G2 一样做独立评审、修订、由开发者批准，所以要写成别人不读代码也能核对的样子。

不交付代码。`src/` 不写、不改（G4b 的事）；可以写不连库的验证脚本放 `$env:TEMP`，用来核对 SDK 行为。

## 规则

- **口径以 `docs/2_landed/` 为准。** 设计只写「怎么实现」，业务规则只引用、不复述（引用写成「见总述『XXX』」）。G2 已定的数据侧形态（用哪些源、mart 12 张表、向量声明、同步策略）只引用 G2 决策，不重写。同一件事只写一处；开发者对文档膨胀很敏感，写完按这一条自查。
- **SDK 不许臆造。** API 签名以 `docs/dev/02-sdk-reference.md` 和 `.venv/Lib/site-packages/forge_*` 的源码为准；设计里每个关键用法（取数、JOIN、聚合、检索参数、沙箱、导出、配置、工作区、事件）都要能指到文档或源码，拿不准的写不连库脚本实测，结论写进设计稿并注明版本（当前 core 0.3.7 / data 0.3.2 / platform 0.3.7）。本机项目环境缺 `greenlet`，导入 `forge_platform.bus` 一类模块时用 `uv run --with greenlet python <脚本>`。
- **不连库，不碰真实数据。** 需要数据事实时，照 `docs/probes/` 的惯例写探测说明交业务方执行（读记忆 `factoryissue-intranet-probe-conventions`），新探测段号用还没用过的字母（读记忆 `factoryissue-landed-citation-style`）。
- **发现业务口径有缺口或冲突**：不在设计里自定业务规则。列进 `docs/open-questions.md`（`- [ ]`，会重新打开 G1 闸门），在设计里标「待确认」，并告诉开发者。G3 那一路也可能改 `2_landed` 或 open-questions，动之前先 `git status` 看有没有别人的改动。
- **发现 SDK 缺能力或文档错误**：按 AGENTS.md「平台 SDK 协作原则」写 `docs/platform-feedback/` 反馈（读记忆 `platform-feedback-must-be-self-contained`），设计里写明平台实现前的临时做法。
- **只读的目录**：`docs/1_user_input/`（开发者投递区，可以读，不改、不引用其中文件路径）、`docs/testcases/`（G3 在改）、`docs/dev/`（平台文档快照）。
- **不提交。** 开发者说「整理提交」时再提交。

## 第一步：对账与关键取舍，先停下来问

读完后先不写全稿，交给开发者两样东西：

1. **带入项清单**：把散落各处、写明「G4a 定 / 留 G4a / 带入 G4a」的事项逐条收齐，每条写出处与一句话内容。来源至少有：README 的两段「带入后续阶段」；G2 决策（约 14 处）；决策 2026-10-18「域权限判断前置」「权限默认效果取允许」「没拉到权限时拒绝本轮」，2026-10-22「涉及某个话题的找法与呈现」，2026-10-23「G1 三次复核修订」「G1 四次复核修订」，2026-10-24「测试案例梳理补充口径」，2026-10-26「回答组织方式默认值」「待办任务表行规则只放行两类」「说法清单按全量标注修订」；两份 `docs/reviews/` 独立评审；`docs/testcases/seed/` 的缺口报告（D-10 检索前补全问句、D-15 设计探针逐条映射）、G3 写作约束、权限测试账号文档；`docs/probes/2026-10-24-话题应命中集探测说明.md`。最后在 `docs/`（不含 `1_user_input`、`dev`）和 `README.md` 里全文搜「G4a」核一遍有没有漏。
2. **关键取舍**：只列会影响整体结构、改起来贵的几项，每项给两三个方案、按正确性 / 本地 Qwen 的可靠度 / 可测性 / 改动成本比较，给出倾向。至少包括：
   - 问句怎么变成取数：模型直接组 `QuerySpec`，还是模型只抽参数（问法类型、域、时间、机型、工厂等）、由代码按问法模板组 spec。对照 AGENTS.md「设计取向」：数字、权限、路由处收紧，澄清、解读处放开。
   - 模块内怎么分问法：按条件查单、按编号查单、单张详情、汇总统计、关键词搜索、涉及某个话题、类似问题、点名字段、寒暄与能力介绍、多段问句，各走哪条路径，谁来判。
   - 三域怎么并行查、怎么合并，跨实例（国内工厂在 `erp`）怎么在应用层关联。
   - `src/` 的包结构怎么分（G4b 照它建文件）。

开发者确认取舍后，再写全稿。

## 全稿必须覆盖

按 G4a 模板，加上本模块特有的部分。每一节先写结论，再写依据。

1. **manifest 草案**（写成接近代码的形态）：`profiles`；`intents` / `keywords`（场景清单唯一信源是总述「常用查询场景」与各域示例，写成用户认得的说法）；`data_sources`（`info`、`erp`、`forge_mart_factory_issue`，各自 `tables` 与 `joins`，JOIN 边逐条列出关联列）；`field_mappings`；`vectorize`（照 G2「结论」，不改）；`config_files`；`clarify_dimensions`（总述「必要澄清项」）；`analysis_dimensions`（总述「初步分析维度」）；`glossary`（唯一信源 `glossary.md`，写清怎么同步、怎么防漂移）。
2. **`field_mappings` 逐列锚定**：目前唯一的行规则在待办任务表（业务表名 `IN` 两个值）。写清协议字段 → 物理列、表级还是源级映射、依据哪张表文件；mart 别名不填。用不连库脚本证明：有规则时编译出的 WHERE 对，缺映射时 fail-closed。
3. **每轮编排与事件序列**：权限前置（`describe()` 判三张主表、CAR 报告表、本域三张 mart 表，见 `privileges.md`「域闸门」）→ 寒暄 / 能力介绍（读前置判断结果，不用固定话术）→ 理解问句与多轮消解 → 澄清 → 取数 → 沙箱算数 → 呈现 → `suggestions` → 导出。每种问法给事件顺序。
4. **取数设计**：每种问法用哪些表、`select` 哪些列、怎么过滤与 JOIN、哪些聚合下推 SQL、哪些进沙箱。要核对并写进设计的约束：`fetch(spec)` 优先于裸 `where`；日期用 `$relative`；`CoreINFO.dbo.*` 与 `info.dbo.*` 同在 `info` 别名下能否声明 JOIN 边（三段名，脚本实测）；平台没把 `info` 默认库设为 `CoreINFO` 前不用 `TRY_CONVERT` / `STRING_SPLIT`；清单与统计不取叙述原文；平台行数上限超限即报错。
5. **文字查找**：把 G2「查询期怎么用」①–⑦ 落成具体调用（读哪张表、`restrict_ids` / `restrict_column` / `filters` / `group_by` 怎么传、按词匹配的 SQL 或代码、模型判断的输入输出、上限与降级、域闸门）。D-10：检索前怎么把问句补全成自足的说法。
6. **数字与沙箱**：每类统计的沙箱脚本输入输出形状；什么时候用 `return_frames=True`；图表 spec 怎么从沙箱产物出来；各分析维度的图表样式（`Event.chart` 的 `style`）。
7. **呈现**：照 `docs/dev/09` 自检；列名唯一取自 `db_description` 的「用户可见显示名」与 `glossary.md`；总述「回答怎么组织」「什么时候配图」「统计口径说明」怎么落到代码；Top N、导出阈值、表格条数做成配置；导出走 `ctx.files`。
8. **多轮与会话工作区**：`conversation_messages` 怎么用；`ctx.workspace` 存什么（上一轮的清单、焦点单、候选），过期时怎么办。
9. **配置文件**：收齐全部 `config_files`（至少：说法清单、分段规则含分组与处理步骤环节清单、判断与重排上限及阈值、部门简称、地区说法对照、Top N 与导出阈值），每份的文件名、格式、内置默认值从哪来、`validate_config()` 查什么、读不到时怎么办；怎么让管理员看到常用的临时说法。
10. **治理任务**：`sync_issue_text`、`rebuild_issue_text` 的步骤；指纹 SQL（`HASHBYTES`，覆盖哪些列）；按单分批读原文；剥图与清洗（`dirty_data.md`「富文本」）；处理步骤内容去人名前缀（G2 说要用测试环境样本定，你这里写方案和需要的探测）；分段与两张段表的写入；三张治理后表的 DDL；进度上报与统计行；失败与重跑。`JobContext` 只有 `embedder`、`etl`、`config`、进度回调，没有大模型。
11. **叙述原文的取数**：核对沙箱数据帧通道单次上限与单轮预算（G2「叙述原文的取数」），给出单张详情的取法；如需改走 mart 副本，列为待确认。
12. **错误与降级**：没拉到权限、表级拒绝、列不允许、取数超限、检索不可用（`ctx.retrieval is None`、mart 表无权、`RetrievalRestrictTooLarge`）、模型超时、配置写错，各回答什么。消息一律业务语言，不露表名字段名。
13. **测试设计**：单测夹具清单里每个分支在设计里由哪个函数承接、怎么用假 `ctx` 测；哪些行为只能 golden 或人工验；不写 G3 的案例内容。
14. **`db_description` 与 mart 表**：manifest 声明 `forge_mart_factory_issue` 后，AGENTS.md 要求 `db_description` 各表 `source` 的并集与 `data_sources` 一致，guard 也查 `source`；mart 表要不要、怎么补表文件（同构三域按表族写一个文件），`forge data check` 在治理表首轮建出之前会怎样。给出做法。
15. **带入项对账**：第一步那张清单，每条写「在第几节处理」或「待确认」。
16. **设计探针映射**（D-15）：20 条探针逐条指到设计稿的节。
17. **待确认与平台缺口**：需要开发者或业务方决定的事、新写的探测与平台反馈。
