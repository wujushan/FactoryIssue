## K1 处理步骤：环节编码与环节名称的对应（D23、G30）

页面按环节编码认环节，本仓现在按环节名称认。代码里有两处名称与编码不一一对应：
- 驳回效果确认、预防对策确认时，编码记为驳回，名称却写成「效果确认」「预防对策确认」。
- 工程确认的编码有两个名称：确认为「是」记「确认版本信息」，为「否」记「工程确认」。

本段列出全部「编码 × 名称」组合，核实这两处的条数，同时拿到驳回、任务转移、删除问题等环节的编码，并看「停线重启发起」是不是只出现在旧数据里。

```sql
SELECT st."Step"::int                   AS "环节编码",
       btrim(st."StepStr"::text)        AS "环节名称",
       count(*)                         AS "记录数",
       count(DISTINCT st."ProblemId")   AS "单数",
       min(st."AddDate")::date          AS "最早",
       max(st."AddDate")::date          AS "最晚"
FROM "ZCTracking_ProblemSteplog" st
JOIN "ZCTracking_ProblemList" m
  ON m."ID" = st."ProblemId" AND COALESCE(m."IsDelete"::int, 0) <> 1
GROUP BY 1, 2
ORDER BY 1, 2;
```

**结果怎么用**：
- 落盘的环节对照表按编码写。
- 同一编码有多个名称、同一名称有多个编码的，按 D23 的结论处理。
- 名称为「效果确认」「预防对策确认」、编码却是驳回的条数，就是按名称取「最新一次效果确认」时会认错的记录数。

## K2 处理结果在各问题类型上的分布（主表 `DesignConfirmResult`）

核实处理结果按问题类型由不同环节填写：硬件、软件、结构、制程优化在跟进人确认为「是」时有值，资料问题在资料确认为「是」时有值，物料问题在需要设计变更时有值，工厂制程没有。

```sql
SELECT m."ProblemType"::int                                    AS "问题类型码",
       COALESCE(m."DesignConfirmResult"::text, '空')            AS "处理结果码",
       count(*)                                                AS "单数",
       count(*) FILTER (WHERE m."RConfirm"::int = 1)           AS "跟进人确认为是",
       count(*) FILTER (WHERE m."ZLConfirmResult"::int = 1)    AS "资料确认为是",
       count(*) FILTER (WHERE m."IsDesignChange"::int = 1)     AS "需要设计变更"
FROM "ZCTracking_ProblemList" m
WHERE COALESCE(m."IsDelete"::int, 0) <> 1
GROUP BY 1, 2
ORDER BY 1, 2;
```

**结果怎么用**：
- 处理结果有值的单基本都满足对应条件时，落盘的「按类型放在不同环节下」成立。
- 不满足的单（如有处理结果、跟进人确认却不是「是」），按页面不显示处理结果，写进 `dirty_data.md`。
- 工厂制程（5）出现处理结果时同样写进 `dirty_data.md`。

## K3 停过线的单：问题类型 × 停线状态

页面代码里工厂制程（5）、制程优化（7）没有停线重启流程，改成这两类时停线待办会被关掉，但停线状态不改。这样的单可能一直停在「停线中」一类状态，按 G34 会被算成停线中。

```sql
SELECT m."ProblemType"::int                         AS "问题类型码",
       COALESCE(m."StopStatus"::text, '空')          AS "停线状态码",
       count(*)                                     AS "单数",
       count(*) FILTER (WHERE m."Status"::int = 32) AS "其中已完成"
FROM "ZCTracking_ProblemList" m
WHERE COALESCE(m."IsDelete"::int, 0) <> 1
  AND m."IsStop"::int = 1
GROUP BY 1, 2
ORDER BY 1, 2;
```

**结果怎么用**：问题类型 5、7 停在停线状态 1、4、5、6 的单有几张。为 0 时不用处理；不为 0 时另提待确认：这些单在管理页面上能不能按「停线中」筛到，以页面为准。

## K6 并行阶段的单还挂着哪些待办（D24）

本仓现在取并行阶段的环节与人时，取的是本单所有「业务表名以 `ZCTracking` 开头、状态为已接受」的待办。页面只看效果确认、预防对策确认这两类。本段看状态 30、36、37 的单除这两类以外还挂着什么待办，例如「待填写停线重启方案」。另数一下这些单里 IQC 状态有值的有几张：页面在并行阶段也显示 IQC 那一行，本仓不显示。

**外传前请过目**：本段会输出任务业务表名与任务标题「】」之后的文字。

```sql
WITH p AS (
    SELECT m."ID", m."Status"::int AS st, (m."IQCStatus" IS NOT NULL) AS has_iqc
    FROM "ZCTracking_ProblemList" m
    WHERE COALESCE(m."IsDelete"::int, 0) <> 1
      AND m."Status"::int IN (30, 36, 37)
)
SELECT p.st                                       AS "主表状态",
       btrim(t."ftable"::text)                    AS "任务业务表名",
       substring(t."fname"::text from '】(.*)$')   AS "任务标题后段",
       count(*)                                   AS "任务数",
       count(DISTINCT p."ID")                     AS "单数"
FROM p
JOIN "tbTask" t
  ON t."frecID"::text = p."ID"::text
 AND btrim(t."fstat"::text) = '已接受'
 AND t."ftable"::text LIKE 'ZCTracking%'
GROUP BY 1, 2, 3
UNION ALL
SELECT p.st, '（这些状态的全部单）', NULL, NULL, count(*) FROM p GROUP BY 1
UNION ALL
SELECT p.st, '（其中 IQC 状态有值）', NULL, NULL, count(*) FROM p WHERE p.has_iqc GROUP BY 1
ORDER BY 1, 2;
```

**结果怎么用**：
- 除效果确认、预防对策确认外还有别的待办的单，就是按现口径会多出一行环节的单。
- IQC 状态有值的单，就是按现口径会少一行 IQC 的单。
- 两者都为 0 时，D24 的 ③ 只是兜底。

## K9 挑几张已重启的国内单，到管理页面看「重启日期」（2026-10-22 补充，正式镜像库）

> **本段输出问题编号与日期，结果只在内网对照管理页面用，不要发回，也不要放进 `docs/1_user_input/`。** 只需按下方「结果怎么用」回告页面上看到了什么。

G44：详情页代码会把最新一条「停线重启」步骤（环节编码 29）登记的日期显示为「重启日期」，有备注时另显示「重启备注」。2026-10-22 的页面核对结论却是「页面不显示这个日期」，两者对不上，需要再到页面上看一次。

本段从已经重启（停线状态 2）的未删除国内单里挑三类，每类最多 3 张：
- **最近重启的**：按这一步的发生时间倒序。
- **有重启备注的**：页面应同时显示「重启备注」。
- **重启日期与这一步的发生时间相差超过 7 天的**：用来分清页面显示的是登记的日期，还是这一步的发生时间。

```sql
WITH last29 AS (
    SELECT DISTINCT ON (s."ProblemId")
           s."ProblemId",
           left(btrim(regexp_replace(COALESCE(s."Result"::text, ''), '<[^>]+>|&nbsp;', '', 'g')), 10) AS restart_v,
           btrim(regexp_replace(COALESCE(s."Opinon"::text, ''), '<[^>]+>|&nbsp;', '', 'g')) <> ''     AS has_memo,
           s."AddDate"                                                                               AS step_at
    FROM "ZCTracking_ProblemSteplog" s
    WHERE s."Step"::int = 29
    ORDER BY s."ProblemId", s."ID" DESC
),
c AS (
    SELECT m."Numbers"::text   AS no,
           m."StopDate"::date  AS stop_d,
           l.restart_v,
           l.has_memo,
           l.step_at,
           CASE WHEN l.restart_v ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'
                THEN abs(l.restart_v::date - l.step_at::date) END AS gap_days
    FROM "ZCTracking_ProblemList" m
    JOIN last29 l ON l."ProblemId" = m."ID"
    WHERE COALESCE(m."IsDelete"::int, 0) <> 1
      AND m."StopStatus"::int = 2
)
(SELECT '1 最近重启的' AS "类别", no AS "问题编号", stop_d AS "停线日期", restart_v AS "应显示的重启日期",
        CASE WHEN has_memo THEN '有' ELSE '无' END AS "有无重启备注", step_at::date AS "这一步的发生日期"
 FROM c ORDER BY step_at DESC LIMIT 3)
UNION ALL
(SELECT '2 有重启备注的', no, stop_d, restart_v, '有', step_at::date
 FROM c WHERE has_memo ORDER BY step_at DESC LIMIT 3)
UNION ALL
(SELECT '3 两个日期相差超过 7 天的', no, stop_d, restart_v,
        CASE WHEN has_memo THEN '有' ELSE '无' END, step_at::date
 FROM c WHERE gap_days > 7 ORDER BY step_at DESC LIMIT 3)
ORDER BY 1, 6 DESC;
```

**结果怎么用**：在管理页面打开这些单的详情，看「是否需要停产 / 停线状态 / 停产日期」那几行下面，回告三点即可，不必附单号：

1. 有没有「重启日期」一行。有的话，显示的日期等于本段的「应显示的重启日期」，还是等于「这一步的发生日期」。第 3 类的单能分清这两者。
2. 第 2 类的单，有没有「重启备注」一行。
3. 打开「操作记录」，「重启操作日志」一段里「停线重启」那一行的内容，是不是写着「……停线重启,重启时间：某日期」。

页面显示「重启日期」时，G44 按建议用这个日期；三类单都没有这一行时，退回 G44 的备用方案（不按重启时间筛、不算停线时长）。
