# G4a 模块技术设计独立评审指令

把本文件整份当作任务。你是独立评审者，不是设计稿的作者。

## 要回答的唯一问题

`docs/decisions/2026-10-27-模块技术设计.md`（下称「设计」）能不能标成评审通过，让 G4b 照 `docs/handoffs/2026-10-27-G4b编码任务单.md`（下称「任务单」）开工。

G4b 写代码只认设计（AGENTS.md「技术设计先行」）。有几类错单测照样能过，只能在设计这一步拦住：权限映射锚错列就是越权，缺映射就是拒查；数字的来源错了就是错数；表头露出字段名，用户就会看到。设计是同一位作者在 2026-10-27 一天里改了多轮写成的（B1–B9、G59–G64、T1–T8 都动过多处），前后说法不一致的风险比平时高。

## 评审对象

- 以开发者交给你时指明的提交为准。没有指明时读工作区现状，并在评审稿文首写明读的是哪个提交、另加了哪些未提交文件。
- 设计引用的规划器实测工具在 `scripts/planner_spike/`，实测结果在 `runtime/planner_spike/<目录>/`。`runtime/` 不入库，只在开发者本机上。

## 做法

- 只新增一份评审稿。不改设计、`docs/2_landed/`、`docs/open-questions.md`、README、任务单和代码，不提交。
- 不连库，不调模型服务（不跑 `spike.py --run`）。可以做的有两件：
  - 在 `$env:TEMP` 写不连库的脚本核对 SDK 行为。导入 `forge_platform.bus` 一类模块时用 `uv run --with greenlet python <脚本>`。
  - 跑 `uv run python scripts/planner_spike/spike.py --self-check`。它不连模型，输出写进 `runtime/planner_spike/selfcheck/`。
- 不打开 `docs/1_user_input/` 和 `runtime/topic_labeling/`，那里有业务原文。`runtime/planner_spike/` 可以读：问句来自对照集，事实与问题单都是合成的。
- 口径以现行 `docs/2_landed/` 为准。设计里的说法、`open-questions.md` 已关闭条目的摘要、决策记录里的旧句，都不能反过来当口径。
- 开发者已定的事（见下）不重审。你认为某项取舍的代价没写清楚，可以写一条「风险提示」。只有它违反 AGENTS.md「硬约束」的某一条时才升档，并写明是哪一条。

**开发者已定、不重审**（设计 §19「已定」与所列决策）：
- 受控代理：模型只写计划，不写 SQL（§1.3）。
- 沿用 Qwen3-Fast。
- 开放临时统计（§5.5）。
- 链接参数写死在代码里，命名混淆（§9.1）。
- 自然期间由代码换算成日期，不算越过数字红线（§6.1）。
- B1–B8；预匹配结果不附给规划器（§1.3）。
- G59–G64，以及名称对不上时给其他类选项（都已落 `2_landed`）。
- 换域时沿用上一轮条件。

## 什么算阻塞、重要、小

- **阻塞**：不改设计就开工，会造成下面任一种后果。
  - 越权，或该拒不拒、该查不查（权限映射、域闸门，或把「没权限 / 暂不可用」答成「没有这类单」）。
  - 违反 AGENTS.md 硬约束：数字由 `handle()` 或模型产出、绕开平台句柄、给用户露出表名字段名。
  - 与现行 `2_landed` 冲突，G4b 照做会给用户错的业务结果，而测试发现不了。
  - 依赖的 SDK 接口不存在或行为不同，改它要动整体结构。
  - 治理表结构写错，首轮跑数后要重建。
  - 发到测试环境的包会让平台起不来。
- **重要**：
  - G4b 照做会出错，但改动只限一处代码或一条规则。
  - 启动指令要求覆盖的某项缺失，或没有落点。
  - 设计前后矛盾，G4b 不知道该照哪一处。
  - 某条行为既没有单测也没有 golden 能验到。
- **小**：措辞问题、交叉引用指错、同一件事写了两处、状态与正文不一致。

## 必核清单

逐条给结论。对上了，在「已核对」里一两句带过。对不上，按上面三档各写一条，写明位置（节号，必要时加行号）、现状、依据（文件与位置）、建议。

1. **覆盖**：
   - 启动指令「全稿必须覆盖」17 项和 G4a 模板各栏，逐项找到落点。
   - §17 带入项对账：每条指到的节里确实写了。
   - §18 的 20 条探针：指到的节确实回答了那条探针。
2. **权限**（§3、§4.1、§14、§15 的 J-P 夹具），对照 `privileges.md`：
   - 行列规则是否只有待办任务表那一条；
   - 表级映射的写法是否与 `04` 一致；
   - mart 别名不填 `field_mappings` 的依据；
   - `describe()` 判出的可查域、CAR 权限、文字查找是否可用，与「域闸门」逐条对上；
   - 无权的情形都不会答成「没有」。

   §3 的三段实测可以用不连库脚本复核（`ScopedDataAccess` 加一个只记 SQL 的假连接器）。
3. **数字红线**：把会出现在用户面前的数逐类追到产出者（SQL 或沙箱），包括：
   - 清单与统计；
   - 分析段：§8.3 的核数能不能拦住各种写法的数；
   - 摘要（§9.2）、统计口径（§8.4）；
   - 反思的说明，以及放宽按钮上的张数（§5.4）；
   - 临时统计（§5.5）、追问选项。

   另一处：AGENTS.md 要求，能用已有列加 COUNT/SUM 等表达完的聚合优先下推 SQL；§6.3 写的是一律不下推 GROUP BY。判断设计给的理由是否成立。
4. **SDK 可溯源**：
   - 设计里出现的每个 SDK 名字（类、方法、参数、异常、事件、上限数值）都能在 `docs/dev/` 或源码里找到，行为与设计说的一致。
   - 模块自己的辅助函数（如 `fetch_all()`）不能写得像 SDK 接口。
5. **与 `2_landed` 一致、不复述**。设计复述业务规则的地方逐字核对：一致的也记一条「小：复述」，不一致的按后果定档。重点：
   - §5.3 第 7–11 条每一条会改口径的改写，在 `2_landed` 里都要有依据。
   - 第 7 条：名字在这一类对不上、另一类恰好对上一项时，自动改到另一类。核对它与下面几处是否冲突：总述「部门名称怎么对」，总述「必要澄清项」（含 2026-10-27 新增的「名称对不上」一行），各域「加工厂」里「对不上请用户核对、不猜」。

## 评审稿写到哪里、写成什么样

新建 `docs/reviews/YYYY-MM-DD-G4a模块技术设计独立评审.md`（日期用执行当天），不改本指令。结构：

1. **文首**：评审者不是作者；只读，只新增本稿；未连库、未调模型；读的是哪个提交、另加了哪些未提交文件。
2. **结论**：「通过，可以开 G4b」「修后再评」「不通过」三选一，用一段话说为什么。有阻塞就不能写通过。
3. **阻塞**、**重要**、**小**、**风险提示**：某档没有就写「无」。
4. **已核对**：必核清单里对上的项，各用一两句写依据。
5. **覆盖对账**：启动指令 17 项各落在哪一节；缺的，指向上面某一条。
6. **开工前要定住的清单**：每行标「已定住」，或标「还定不住」并指向上面某一条。
   - `field_mappings`；
   - manifest 各字段，以及 S6 之前不带 mart 声明；
   - 计划格式：改了要重跑对照集，约 1,000 次模型调用；
   - 五份配置文件的名字与格式；
   - 工作区各键的内容；
   - 治理表与分段表的结构（含 `seg_compact`）；
   - 各技能的事件顺序。

用简体中文。表名、字段名可以出现；不写真实业务原文和单号清单。
