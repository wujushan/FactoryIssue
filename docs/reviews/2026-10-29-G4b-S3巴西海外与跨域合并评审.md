## 结论

**先改再收口。** 巴西、海外和跨域合并的主干是按设计和业务口径落下来的：主表条件与沙箱派生的分工、未删除、巴西草稿与已终止仍在范围内、未结案不含这两类、费用按明细认定、测试值 0 不计入、海外不良率逐单列原文、同名合并的「—」和 0、一域一行加合计、对不上的域整段不计入、部分域无权不取那两域的表、J-D08 / J-D10 / J-D11 / J-D12 / J-P01，都对得上，而且有单测。`handle()` 这条链上没有用 `len`、`max`、`sorted`、`sum` 给用户报一个新算出来的数；用户看见的张数来自沙箱的 `found`、`facts`、`by_domain`。

不能按「不用再改」收口。有两处单测盖不住，用户会看到答错的追问，或把三种结案日期混成一个平均数。459 全绿说明现有夹具没走到这两处。

## 必须改

### M1 巴西、海外文档里的三句停线说法认不出，追问给的是流程状态

- **位置**：`domains/enums.py` 的状态说法表。`status_kind` 对不上时，`domains/brazil.py::status_items`（海外复用它）整段追问，选项是该域主表状态的前 4 个。
- **现状**：直接调用的结果是：
  - 「从未停线」「停线已重启」「停线后已恢复生产」→ 认不出。
  - 「没有停线」「停线重启」「已重启」「停线且未重启」「正在停线」→ 认得出。
  只问巴西「从未停线的单」时，追问是「这个状态对不上，巴西的状态有：待提交、待修改类别、待跟进、待设计更改」。点了「待提交」会去查草稿，和「是否停线为否」不是一回事。三域一起问时，三个域都对不上，返回的是国内那条追问（选项是未结案、已结案、停线中、已经重启），同样没有「从未停线」。
- **依据**：巴西「停线」表：从未停线 = 是否停线为「否」；停线已重启、停线后已恢复生产 = 是否停线为「是」且停线状态为「停线重启」。海外「停线」表：停线后已恢复生产 = 停线状态为「已经重启」。执行层已经能认「没有停线」「停线重启」「已重启」，差的是文档里的这三句原话。规划提示写了若干状态改写，没有这三句；任务单说这片没动规划层。模型照抄原话时，执行层要自己认得，不必为了这三句重跑对照集。
- **后果**：用户按业务文档里的说法问停线，本轮不出数，还可能点进草稿或「停线中」。
- **建议**：把这三句补进状态说法表，映射到现有判据（从未停线 → 没有停线；后两句 → 已经重启）。补三条单测：说法进去之后，巴西「从未停线」只留下是否停线为「否」的单，「停线已重启」只留下已标记停线重启的单；不要改规划提示。

### M2 三域一起问结案周期时，合计行把三种结案日期合成一个平均数

- **位置**：`stats/tasks/aggregate.py` 的 `ag_cross_overview`。各域一行用本域自己的天数；合计行把三域 `_done` 的单拼在一起，再算 `_close_days` 的平均和中位数。
- **现状**：国内、海外的结案时间是处理步骤里最新一条结案确认，巴西是最新一条处理过程上的结案日期。三域的 `TRAITS` 都含「结案周期」，所以合计格是一个数，不是「—」。不良率的合计格已经是「—」（国内分母是生产数量，巴西是影响数量，海外不汇总）。口径按域写了结案时间怎么取，没有写这个合计格是三种日期混在一起的平均。
- **依据**：总述「结案时间与结案周期」、设计 §6.4：要结案周期时各域各自一列值；合计行明确写成「—」的是不良率。总述没有定义一个跨域的结案天数。
- **后果**：问「三个域平均多久结案」，用户会把合计行那个数当成答案。它不是任一域的结案周期，也不是文档里的指标。各域自己那一行的数是对的。
- **建议**：合计行的「结案周期平均（天）」「结案周期中位数（天）」写「—」。各域的格子保留。停线时长可以留在合计行：巴西没有这项，格子已是「—」，合计只含国内和海外里两个日期都有的单，算法相同。补一条：三域一起要结案周期时，合计格是「—」，国内、巴西、海外三格仍是各自的天数。

## 应补

### A1 产品主数据没取到时，巴西、海外的机型整列变成「未识别机型」

按机型筛时，产品表取失败会走「这一部分暂时没查到」（S2 评审 A5 的那条，`MasterData.failed`）。不按机型筛、只列清单时，派生仍用空的产品表去对大机型 ID，对不上就写「未识别机型」，整段仍当成功。巴西、海外「大机型」：全部对不上才显示「未识别机型」，指的是 ID 在产品主数据里没有，不是这张表没取到。取失败时这一段答「这一部分暂时没查到」，不要把每张单的机型都写成未识别。

### A2 设计写了有两条公开测试向量的单测，仓库里没有

`present/_blk.py` 的分组变换，我用 FIPS-197 附录 C.3 和 SP 800-38A F.2.5 对过，两组都逐字节相同。PKCS7 在长度正好是 16 的倍数时会再补一整组，这是对的。设计 §9.1 写「单测用这两条向量核对」，`tests/` 里没有这两条，现有链接单测只检查「同一输入得到同一串大写十六进制」。把这两条公开向量补进单测。向量是公开的，两项业务值不要出现在测试、日志和本稿里。

### A3 巴西清单上的停线状态和分组用的不是同一套字

分组走 `_stop_label`：是否停线为「否」且停线状态为空时，组名是「从未停线」。清单列 `stop_status` 展示单上的原值，空写成「未填」。同一批单，表里是「未填」，按停线状态统计时是「从未停线」。海外这一列和分组都用「没有停线 / 停线中 / 已经重启」，两边一致。巴西清单在「否 + 空」时也写「从未停线」，或者分组改用单上原值、空写「未填」，并在口径里说明这个空就是从未停线。两处选一处，不要各写各的。

## 对得上的部分

这些对照过设计和两域口径，没有另立口径：

- 巴西未删除是状态不是「已删除」；待提交、已终止仍在范围内，未结案不含它们，概况口径写「巴西另列」。海外未删除是「是否删除为 0」。
- 巴西处理过程只取 `ID` 最大的一条：跟进人、跟进部门（跟进人现在的部门）、结案日期、扣款、是否设计更改都从这条来；还没有处理过程的单，跟进人和跟进部门是「未指定」，按部门统计时不计入。
- 巴西不良率 = 不良数量 × 100 ÷ 影响数量，影响数量为 0 时单上显示 0.00%，为空时「未填」。合计不良率仍排除不良数量为空、影响数量为 0 或空的单。海外单上原文保留 `%` / `‰`，比大小时 ‰ 除以 10，不参与合计；三域一起时海外那格和合计格都是「—」，并逐单列出原文。
- 费用：用户明说「是否涉及费用」时只比 1 和 2，测试值 0 不进结果（J-D12）。「涉及费用的单」按美元或雷亚尔合计大于 0，不看标记。问美元时，只产生雷亚尔的单数和雷亚尔合计写在开头（J-D08）。扣款单独一列，口径写明未计入费用。
- 加工厂：巴西整段相等、不分大小写、「TT 工厂」去掉「工厂」，逗号多值任一段命中。海外名称包含或相近，命中多家就追问；XC-010 的追问里写了国内、巴西没有这家。只在某一个域对得上的名字，其余域不计入、不追问。「TT」不是机型时，选项里有「TT：巴西的加工厂」。
- 问题类型同名才合并。「该域没有这个类型」是「—」，「有这个类型但这次是 0」是 0。等级 A+、A、B、C 没有单也列出，未填单独一行。处理环节、状态按域分表。清单开头是「合计 N 张：国内 a 张、巴西 b 张、海外 c 张」，三域清单只写一次分析。
- 点名的类型本域一个都没有时，整域不计入。国内「设计问题」、按统计日期、是否需要回复 8D、海外单上的国内工厂，都走这条，不再把该域全部单算进来。巴西没有当前责任人；海外系列不作条件。责任归属部门两边都按问题跟进部门解释并写明。巴西只说「责任人」按问题跟进人；海外只说「责任人」按当前责任人，清单上同时给出问题跟进人。已完成的海外单不按当前责任人计入。
- 海外详情区块写在 `os_blocks`：按走过的环节给，不套类型表；驳回后还没重新提交的那一块不给旧内容和主表原因、措施、对策。单测覆盖 J-D10、J-D11。详情正文接到回答上是 S4 的事。
- 子表关联列和声明一致：巴西 `ProblemID`，海外 `ProblemId`。文本日期只认 `YYYY-MM-DD`。物料 JSON 的键与表文件一致。海外加工厂取值清单带未删除条件。
- 数字红线：开头、口径、各域张数读的是沙箱字段。`execute.py` 里的 `len`、`sorted` 用来决定要不要分域写、给时间段排先后、拼帧，不另造给用户的张数。核数里原有的 `max` 仍只决定哪一句留下。
- 巴西链接：站点没配或两项值缺失时问题编号是纯文字；参数是大写十六进制，不做 URL 编码；异常日志只有异常类型。`brazil` 不写时与 `issue` 同一站点。两项值已在代码里，本稿不摘录。
- BR-001 去掉「状态」列，与总述「清单默认列」一致：问句按等级筛，等级列加上；没按状态筛，不要求状态列。开发者已同意，golden 和人工手册改了，参考 SQL 的查询列不动。这处不算缺陷。

任务单已经写明、这次不记成缺陷：问题描述摘要和导出在 S6 / S5；详情、按号、附件与 CAR 在 S4；比较两个时段这片按设计只出各组单数、增减和变化率。第一个预发布包里超过表格条数的清单仍只有前若干行，没有导出文件。
