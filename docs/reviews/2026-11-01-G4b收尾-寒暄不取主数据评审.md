## 核对过、成立的

- **号码直通的单调性**（决策第 2 条第 1 点）。`prematch._maybe_machine` 里，机型清单只在长相判断之外多加一条「对得上就拒」，长相像机型的 `_MACHINE_SHAPE` 有没有清单都拒。所以 `number_shortcut(q, None) is None` 能推出 `number_shortcut(q, machines) is None`。不带清单先判断不会漏掉直通，也不会多直通。
- **第一次模型调用用不到主数据**：`Planner.messages` 只用 `planner_system(manifest, topics)` 和 `planner_user(query, history, previous_plan, previous_outcome)`。
- **只有 introduce 时规整、校验与主数据无关**：`normalize.apply` 里只有第 7 条（`_regroup`）读 `classes`，而且只遍历 `filters`。`tagged_checks` 算完第 13 条后，遇到 `introduce`、`clarify` 就返回，不会走到读 `entities` 的第 15 条。第 11、5、2、18、17 条都不读主数据。另有一个例外，见 A2。
- **再次规整没有副作用**：`_normalize` 里的 `drop_ignored_keys` 是就地改、可重复做；`normalize.apply` 先 `deepcopy`。补上主数据之后再规整一次，结果和第一次就带主数据规整相同。
- **编排**：`_LazyMaster` 缓存结果，一轮最多取一次主数据。模型写的追问、写成 `introduce` 的两条路，都在 `lazy.get()` 之前返回：
  - 追问在规划器里已经补过主数据，这和决策「追问照旧取」一致。
  - `introduce` 一次也不取。

  直填、重放、执行三条路都要先经过 `lazy.get()`。`fill_no_effect` 重新规划时用的 `inputs` 不带主数据，调 `enrich` 拿到的是缓存。`shared.load` 内部接住异常、记进 `failed`，所以取主数据的位置挪进 `Planner.plan` 之后，异常怎么传出来没有变。
- **实测**（假 `ctx`，三域都可查，`runtime/probes/rv_greet_paths.py`）：

  | 问句 | 结果 | SQL | 业务取数 |
  |---|---|---|---|
  | XC-014、XC-015（写成 `introduce`） | 介绍 + 按钮 | 0 | 0 |
  | XC-009、XC-013（两种写法）、XC-038 | 追问 | 8（主数据） | 0 |
  | XC-012（走号码直通） | 追问 | 8（主数据） | 0 |

  决策里的「三域 8 条」与实测一致。XC-014、XC-015 本身就在对照集里，p2.2 整跑（`20261029-p2.2`）各 5 次都写成 `introduce`，所以线上这两条正常会走「不取」的那条路。
- **单测**：`test_jp04`、`test_introduce_out_of_scope` 收紧为 `h.queries == []`。新加的 6 条覆盖三域都可查时的两种 introduce、模型写追问时照旧取主数据，以及 `enrich` 的三种调用。改动前的代码在规划前无条件 `shared.load`，`account_jia`、`GREEN` 两种权限下 `h.queries` 都不会是空的，所以这 5 条断言放在改动前的代码上一定失败。这一点从逻辑上成立，我没有撤回代码重跑。

## 建议（都不挡提交）

### A1　人工手册 XC-009「trace 里有查问题单的 SQL→取数」照字面判会误报

规划前取的 8 条主数据 SQL 里，有两条查的就是问题单的表（实测 trace）：

- 国内机型取值清单：取自国内机型子表 `ZCTracking_ProductNames`。
- 海外加工厂取值清单：在海外主表 `OverseasProblemDetail` 上 `SELECT DISTINCT` 加工厂一列（`tests/fakes.py::is_factory_list` 就是为它开的例外）。

测试人员照 XC-009 那一行看 trace，会看到问题单的表名，判成「取数」失败。`docs/testcases/README.md` 新加的定义写了主数据「不算」，括号里写「工厂、部门、机型、供应商等取值清单」，字面上包括了这两条；但 XC-009 那一行没有指回这个定义，读 trace 的人也不容易把这两张表对到「取值清单」上。

另外，`no_tables` 断言的是「不出表」，「不查问题单」这件事 golden 本身验不到，只能看 trace。README 那句「golden 用 `no_tables` 断言」可以补半句说明这一点。

建议：

- README 的定义点名这两条：「国内机型取自机型子表，海外加工厂取自海外主表的去重一列」。
- XC-009 的失败分层改为「trace 里除了规划前那几条取值清单，还有查问题单的 SQL → 取数」。

### A2　「只有 introduce 时与主数据无关」前提是 introduce 步骤不带 `filters`

所有技能共用同一个 `StepParams`，所以模型写 `{"skill": "introduce", "params": {"kind": "能力", "filters": [...]}}` 也能通过格式校验。这时第 7 条的 `_regroup` 会按 `classes` 归类：

- 不带主数据时，`matched` 为空，计划仍是介绍。
- 带主数据时，可能改写成「名称对上多类」的追问。

两种结果不同，而那段防御分支只在「规整后不再只是介绍」时才补主数据，接不住这种情况。

后果不严重：不带主数据时照常答介绍，比为一句介绍追问名字更合理；而且模型给 introduce 写 `filters` 很少见。建议二选一：

- `introduce_only` 另外要求每步都没有 `filters`；
- 或者把注释、§4.2 第 6 步、§19 那句「规整出来一样」改为「introduce 不带条件时规整出来一样」。

### A3　第一次回复格式不合格、修一次后写成 introduce，仍会取主数据

只要第一次有格式错误，`light` 就是假，修一次之前先补主数据。修一次的提示并不用主数据，所以补主数据其实可以挪到解析出修后计划、确认它不只是介绍之后再做。

目前这样做是保守的，决策也只说了「模型第一次写的计划」，不算偏离。但出现这种情况时，XC-014、XC-015 会因为有 8 条 SQL 而失败。启动指令的「没验证到的」只写了「写成别的（如追问）会失败」，建议补一句「第一次格式不合格、修一次后才写成 introduce，也会有 8 条」，方便开发者看 trace 时对上原因。

### A4　编排和规划器对「这是介绍」的判据不同

- 编排：第一步是 `introduce` 就按介绍答。
- 规划器：要求 `introduce_only`，即每一步都是 `introduce`。

所以 `[introduce, list_issues]` 这种计划会先取主数据，最后照样只答介绍。现在不出错，只是多发了几条 SQL。可以在 `introduce_only` 的文档串里记一句，或者以后让两处用同一个判据。

## 小处

- 任务单「G4b 收尾」第一项已经勾成 `[x]`，但同一行写着「待评审，没有提交」。建议提交后再勾。
- 启动指令「没验证到的」引的是「对照集 c5 里非业务输入 90 次全对，问能力、只读请求在内」。那 90 次是 18 条通用输入（U-*），XC-014、XC-015 属于 c4。直接引更有力的证据更准确：p2.2 整跑里这两句各 5 次都写成 `introduce`。
- `test_enrich_called_once_for_other_plans_and_before_repair` 只断言了次数，没断言「在修一次之前」补主数据。顺序其实不影响正确性，测试名可以去掉「before_repair」，或者补一个顺序断言。
- `Planner.plan` 里那段「规整后不再只是介绍、或被打回」的防御分支，按注释的推理走不到，也没有单测。可以留着当保险，但最好有一条单测：用假的规整结果让它走一次，或者用 A2 那种带 `filters` 的 introduce。
- 顺带一提：golden 里 108 条数据用例都带 `min_queries: 1`，这些 SQL 仍然把主数据算在内。改动之后，它能抓住「写成 introduce」和「规划失败」这两种 0 条 SQL 的情况；「答成追问」由 `qa_test.py` 的澄清判定抓。README 的定义只讲了「不取数」，`min_queries` 的含义暂时不用改，G5 用 trace 对数时注意即可。
