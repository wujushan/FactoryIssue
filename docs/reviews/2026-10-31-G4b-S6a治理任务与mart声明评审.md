## 结论

**写进产物库的文字可以收口，统计行建议发包前补。** 三域文字表的列与各域「叙述文字」、总述「比对范围」对得上；清洗、去人名前缀、分析类环节、巴西只取最新一条处理过程、重启方案照存、指纹覆盖来源列、建表后核对列、写入语句能被 `pglast` 解析，都按设计落了。`forge vectorize ddl` 三张向量表的权限承载列都是「（无）」，`issue_id`、`field` 都在。`forge jobs list` 列出 5 个任务，两个治理任务和三个向量化任务的 cron 与 G2 一致。

`handle()` 这条链上没有用 `len`、`max`、`sorted`、`sum` 给用户报一个新算出来的数。治理任务里的 `len`、`sum` 只进统计行和进度。

不能按「进度句和统计行已经能做上线首轮核对」收口。去人名前缀只数了分析类环节；清洗前的字符数把同一环节没采用的旧步骤也算进去了；任务页最后一句缺了核对清单里的大半项。这三处不改文字本身，但首轮拿它们判断「剥图片剥了多少、姓名去得怎么样」会读错。

## 应补

### A1 去人名前缀的条数只统计了分析类环节

- **位置**：`jobs/steps.py` 的 `build`。姓名在所有环节的内容上都去掉了，计数写在 `if key not in wanted: continue` 之后。
- **现状**：文字表三列包含全部环节（填写问题、驳回、结案确认都在）。`name_prefix` 只累计配置里的分析类环节。单测把这个范围锁住了：`填写问题` 的内容从「测试甲提交了问题」收成「提交了问题」，`prefix` 里没有「填写问题」。
- **依据**：设计 §12 第 5 步：「统计行里照报每个环节去掉与没去掉的条数」。第 8 步的 `name_prefix` 是「环节 → [去掉, 没去掉]」。G2「上线首轮核对」和启动指令都要「各环节」这两列数。
- **后果**：首轮只能看到责任人确认、工厂制程分析、SQE 跟进这些分析类环节。填写问题、结案确认、驳回的内容同样进文字表，点名「处理步骤内容」时会拿去比对；这些环节姓名没去掉的比例，统计行里是 0 条，不是「没去掉」。
- **建议**：有内容的环节都计入，分析类以外的也计。若只想统计分析类，把设计 §12 那句改成「分析类环节」，并写明其余环节不进这组数。补一条：填写问题去掉了姓名，统计行里该环节是 [1, 0]。

### A2 任务页最后一句缺了核对清单的大半项

- **位置**：`jobs/text_sync.py` 的 `DomainStats.line`。结束时 `ctx.progress` 用的是这句。
- **现状**：进度句只有单数、整理数、删掉数、分段数、按意思找的段数、比对文字全空、没有按意思找的段、总秒数。清洗前后字符数、含内嵌图片的单数、各环节去人名前缀、清单外环节、分步耗时在结构化日志 `factory_issue_text_sync_stats` 里，不在这句里。
- **依据**：设计 §12 第 8 步：最后一次进度的 `message` 与这条日志都写出 G2「上线首轮核对」的各项，另加去人名前缀和清单外环节。启动指令写的是「日志或任务页最后一条进度」都能拿来核对。
- **后果**：只抄 Console 任务页那一句，对不上核对清单。日志是齐的（A1 的范围问题除外）。
- **建议**：最后一句带上字符数、含图单数、去人名前缀、清单外环节、分步耗时。字可以紧，只要核对的人不用再去翻日志。

### A3 清洗前字符数包含没写进文字表的旧步骤

- **位置**：`jobs/text_sync.py` 的 `build_issue`。处理步骤在 `steps.build` 之前，对每一行的结论、意见、内容都 `raw.take`。巴西处理过程只 `take` 最新一条。
- **现状**：`chars_raw` 含同一环节 ID 较小的那些行；`chars_clean` 只加最终三列的字数，旧行不在里面。旧行里的 `data:image` 也会把这张单算进 `with_inline_images`，哪怕留下来的文字里已经没有图片。
- **依据**：设计 §12 第 8 步：`chars_raw` / `chars_clean` 是清洗前后字符数。G2 用这对数看内嵌图片剥掉了多少。
- **后果**：首轮会觉得「清洗掉了很多字」。其中一部分是每个环节只留最新一条时丢掉的旧步骤，不是 HTML 和图片。国内处理步骤行数远多于「每单一条」，这个差会被放大。处理过程那边又只数最新一条，两个域的「清洗前」不是同一口径。
- **建议**：清洗前只数真正送进清洗、并且会写进文字表的那些值（步骤只数每个环节最新一条）。含图单数同样只看这些值。

## 对得上的部分

这些对照过设计和业务口径，没有另立口径：

- **列**。文字表族文件「成员差异」与三域「叙述文字」、总述「比对范围」逐项对过：国内含现象、问题描述、原因、改善建议、改善措施、预防对策、效果确认、生产确认备注、备注、原因分类说明、重启方案、处理步骤三列；巴西含现象、问题描述、备注、补料备注、最新一条处理过程的各叙述列、费用备注；海外含已选现象、问题描述、原因、改善建议、改善措施、预防对策、效果确认、备注、其他问题说明、处理步骤三列。5Why、可能原因、可能物料、CAR 报告、附件不在表里。列名 `f_` + 代号。`jobs/spec.py` 导入时与这张表逐列核对，多一列少一列模块加载失败。
- **未删除**。国内 `ISNULL(IsDelete, 0) = 0`（空算未删除，夹具里的 9903 进了表）；巴西 `Status <> -1`；海外 `IsDelete = 0`。已删除的单不进文字表，源上消失的单从三张表一起删。
- **清洗**。`strip_rich` 与详情的 `rich_display` 同一段代码：内嵌图片和外链图片都去掉，段落留成换行，不截断。详情仍把外链留成「[图片](地址)」。空值和 NaN 成空串。NUL 在写入前去掉。
- **去人名前缀**。内容以操作人姓名开头才去掉；后面是逗号、冒号、顿号或空白时连这一个分隔符去掉；姓名后直接接正文也去掉（责任人确认）；姓名不在开头不动；查不到人不去。与探测 W1 和国内「停线」无关的步骤规则一致。单测覆盖了这几种。
- **处理步骤**。每个环节 ID 最大的一条；文字表三列全部环节，按 ID 先后，每条「环节名称：」开头。结论只取工厂制程分析（国内编码 6，海外名称「工厂制程分析」）。分段表的「处理步骤」只取分析类环节；意见或结论在去掉空白后的内容里已出现则不加；同单相同条目只留一条。国内按编码认环节：编码 28 的驳回不会因为名称写成「预防对策确认」被当成预防对策确认（名称只用于展示）。海外按名称认。清单外的编码或名称进 `outside_steps`。环节清单的默认值与总述「比对范围」两份清单一致。
- **现象**。国内按已选现象的行 ID 先后、按现象去重，用「；」连接，整列不进按意思找的段表。巴西、海外按展平规则，编号小于 0 的手填才进按意思找的段表；标准现象仍进分段表。展平从详情挪到 `textnorm.phen_parts`，详情改调它。
- **巴西处理过程与费用**。文字只取 ID 最大的一条；指纹含全部处理过程行，旧行改字会触发重写。费用全部行按 ID 先后，有备注的写成「费用类型：备注」，空备注不写。
- **短文本**。剥净后不超过 10 个字（不算空白）不进按意思找的段表，分段表仍保留。处理步骤按条目正文判断，「OK」不进向量来源，仍留在分段表的处理步骤里。夹具里只有「OK」的 9903 有分段、没有按意思找的段。
- **分段**。分段表一栏目一段，不切；`seg_text` 带栏目名，`seg_norm`、`seg_compact` 不带。按意思找的段表按 `whole` / `field` / `field_split` 切，段编号 `<issue_id>:<代号>:<序号>`，两张表各自编号。`whole` 的栏目代号是 `whole`。默认 `field_split`：超过 500 字才切，相邻段重叠一句。用总述那种 30 字一句的长文跑过，句子都还在，重叠的是上一句。
- **指纹**。主表与子表在 SQL Server 侧用 `HASHBYTES('SHA2_256', …)`，首段及后续都转成 `NVARCHAR(MAX)`，用 `+` 和 `NCHAR(31)` 拼接，再在任务里用 sha256 按子表名和行 ID 合成。兼容级别 100 不用的函数（`TRY_CONVERT`、`STRING_SPLIT`、`CONCAT`、`STRING_AGG`、`CONCAT_WS`）不在这些 SQL 里。文字表每列在表族文件里写的来源列都进了指纹；现象主数据的现象文字不进，靠凌晨全量。分段规则不进指纹。操作人、环节编码、环节名称、费用类型、已选现象 ID 进组合指纹。
- **挑单与分批**。增量只写新增和指纹变了的单；全量写全部未删除的单。按原文字节数贪心组批，约 20 MB 或 200 张，单张更大的单独一批。读原文时已删除的单跳过。员工姓名按 ID 每 1,000 个一块取 `Employee.Name`。
- **写入**。每批一条数据修改型 CTE：文字表 upsert，两张段表先删「这批单里新段编号以外的段」再 upsert。删和插不碰同一行。按意思找的段表只在 `seg_text` 变化时更新。已删除的单一条语句从三张表删除。空段集合与非空都走 JSON 数组。SQL 里没有 `%`、没有带冒号的字面量。单测把 `:name` 换成 `$n` 后用 `pglast` 解析了写入、删除和建表语句。
- **建表与核对**。每轮 `CREATE TABLE IF NOT EXISTS`，然后经只读句柄读 `information_schema.columns`。缺列、多列、一列都读不到都在写入前失败，并提示改了列要删表后全量重建、读不到列时可能是只读账号没授权。向量表不在这里建。
- **失败与重跑**。每批一次 `execute`、自动提交。已写的批指纹已更新，下一轮增量不再写它们；没写的批下一轮会再写。02:30 增量与全量可能交错，设计写明不加锁。取数和写入放在 `asyncio.to_thread`。
- **配置**。分段规则读 `ctx.config`，读不到或解析失败用内置默认值。`FIELD_CODES` 改取分段表族文件，与原先写死的 8 个代号相同。`seg_min` 大于 `seg_max` 时保存配置会拒绝。
- **域闸门**。`describe()` 里本域文字表、分段表、向量表三张都可见，该域 `text_search` 才为真。清单的问题描述仍无条件写「暂不可用」（摘要在 S6b）。有 mart 权限时，能力介绍的第三个按钮变成「类似问题」，点了走 `NOT_READY`。这是启动指令写明的过渡，S6b 接上后去掉。
- **重启方案**。`f_restart` 和处理步骤三列照存停线重启、停线重启审核、责任人填写重启方案。查询期按实时停线状态排除，是 S6b 的事。国内「停线」已补上这句，开发者 2026-10-30 确认。
- **红线**。`jobs/` 只经 `ctx.etl`，没有 `ctx.data`、`ctx.llm`、读环境变量、自己连库。日志和进度只有计数、环节编码或环节名称、耗时，没有叙述原文。`stats/lib` 仍只被沙箱拼接引用；现象展平挪到 `textnorm` 后，详情脚本继续拼 `textnorm.py`。

## 不挡收口

- **硬切的长句相邻段不重叠。** 一句超过 500 字时切成 500 字一块。下一块若再重叠这一整块，就会超过 `seg_max`，代码因此不重叠。用 1,200 个「长」跑过：三段 500、500、200，拼回去正好 1,200，没有丢字。设计同时写了「不超过 500」和「重叠一句」，顶满 500 时只能守住字数上限。
- **最后一段可以短于 300 字。** 30 字一句的样例切成 481 字和 150 字，句子都在，重叠的是上一句。150 是剩余，没有下一句可用来补满。设计要求补满的是「当前段不到 300 且下一句放不下」。
- **详情里工厂制程分析仍写 `code == 6`。** 治理任务用 `enums.CN_STEP_FACTORY`（也是 6）。两边现在相同。以后只改常量的话，详情和文字表会各认一个编码。
- **工作区里还有一处与 S6a 无关的改动。** `docs/platform-feedback/2026-10-30-INFO网页前端把按钮的query当按钮文字.md` 补了两句：2026-10-30 发包后在网页上复核，改短的按钮显示正常。整理提交时可以跟治理任务分开，也可以写明是复核记录。

## 发包前已经对过、首轮仍要看的

这些不是代码缺陷。设计写明本机没有真库，作者也记了没在 PostgreSQL 和 SQL Server 上跑过。本次评审同样没连库。

- 写入语句只经过 `pglast`。真 PostgreSQL 上要看：一条 CTE 里未被主查询引用的数据修改是否都执行、空 JSON 数组的 `NOT IN` 是否删掉该单全部旧段、`ON CONFLICT … WHERE seg_text IS DISTINCT` 是否避免无谓重嵌、单张约 48 MB 的原文做成一个 JSON 参数是否写得进。
- 指纹 SQL 没在 SQL Server 上跑。`HASHBYTES` 返回的二进制要能稳定收成同一种十六进制；列名按代码里的大小写回来（`ProblemDesc`、`Opinon`、`ReStartScheme`）。对不上的话，增量会每轮把单全部重写，或整理进文字表的列是空的。
- 建表用的写账号和核对列用的读账号如果不是同一个，刚建的表在 `information_schema` 里读不到，任务会在写入前失败并报「读不到列」。这是设计里的失败方式，首轮若遇到，先给读账号授权再重跑。
- 上线顺序仍是：`rebuild_issue_text` → 三个 `vectorize:*` → 重启平台。向量表还没有时，本助手会被隔离，聊天进不来；任务要在隔离之前或由 jobs worker 跑起来，按 G2 第 4 项执行。
- 改了分段规则或环节清单，指纹不会变，必须手动跑一次全量重建。现象主数据的文字改了，同样要等凌晨全量或手动全量，增量不会重写。
- 首轮统计行回来后，按 G2「上线首轮核对」看单数、段数、比对文字全空、没有按意思找的段、去人名前缀、清单外环节。A1–A3 补上之前，去人名前缀只代表分析类环节，清洗前字符数含旧步骤。
