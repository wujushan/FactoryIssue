**【适配通知】业务页面的助手调用从对话接口中分离：新增 `/v2/tasks`**

**背景**

目前自动审核、填单页面的分析和润色建议等业务调用，和用户的对话问答用的是同一个接口 `/v2/chat`。这带来两个问题：

- 每审核一张单据、每打开一次填单页面，都会在用户的会话列表里留下一条会话；
- 后台统计分不清哪些是问答、哪些是业务调用。

平台新增了业务任务接口 `POST /v2/tasks`，专门承接这类调用。

**这次变化的原则**

- **请求和响应格式与 `/v2/chat` 完全相同**：请求体字段、SSE 流式事件、响应头、`conversation_id` 续聊、断线续接和停止生成都一样，现有的流式解析代码可以直接复用。
- **可以逐个页面切换，可以随时回退**：`/v2/chat` 的行为不变，没切换的页面照常工作。

**和 `/v2/chat` 的三处区别**

1. `target`（助手编码）**必填**，平台不做语义路由；
2. `ext_param.task`（任务码）**必填**，而且必须是该助手事先声明过的任务；
3. 这类调用**不出现在用户的会话列表里**，统计里单独算作「业务调用」。

按会话 ID 查历史、改名、删除、点赞点踩、分享，都和对话一样可用。

---

**一、业务仓需要做的**

1. **把 SDK 升级到 0.3.9**：`paxsz-forge-core>=0.3.9`。如果用本地 dev serve 联调，`paxsz-forge-platform` 也要 `>=0.3.9`。
2. **在 manifest 里声明任务**。只有声明过的任务码，才能被 `/v2/tasks` 调用：

   ```python
   from forge_core.module import TaskSpec

   tasks=[
       TaskSpec(
           code="review_contract",            # 任务码，即 ext_param.task
           name="合同自动审核",
           description="审核流程节点调用：对合同正文给出风险点与修改建议",
           query="待审核的合同正文",             # 说明 query 字段里放什么
       ),
   ]
   ```

3. **`handle()` 不用改**：两个接口送到模块的请求完全一样，原来按 `ext_param.task` 分派逻辑的代码照常工作。不要在模块里判断请求是从哪个接口进来的。
4. **在 `docs/2_landed` 写一份给 INFO 前端的对接说明**，内容包括：每个任务的 `target`、`task`、`query` 放什么、`ext_param` 里还有哪些参数及含义。
5. **（按需）任务要用超出当前用户权限的数据时**：比如审核时要参考同类单据的历史驳回原因，可以在**这个任务**上声明 `data_scope="system"`。效果和边界如下：
   - **效果**：这个任务通过 `/v2/tasks` 调用时，取数不再按当前用户的权限过滤。
   - **范围**：只对这个任务、只在 `/v2/tasks` 上生效。用 `/v2/chat` 调用同一个任务码不会放开；你的模块调用的其他模块也不会跟着放开。
   - **留痕**：每次调用都会记录。
   - **你的责任**：越权数据一旦交给模型，模型的输出就是唯一的防线，返回什么由业务仓负责。请按 docs/dev/04「任务级系统数据范围」的做法来写：
     - 优先把聚合结果交给模型，而不是越权的明细数据；
     - 明细要先脱敏；
     - 被处理的单据正文当作数据处理，防止其中夹带的提示词注入；
     - 引用来源只指向用户本人有权限看的数据。
   - **建议**：在 `docs/decisions/` 写明为什么需要越权、用到了哪些数据。

   不声明的话，默认按用户权限，和现在一样。

6. **测试**：`/test/chat` 不检查任务是否声明过。请另写一条单元测试，确认 `handle()` 里分派到的每个任务码都能用 `manifest.find_task(...)` 找到。

**二、INFO 前端需要做的**

1. **把业务页面的调用地址从 `/v2/chat` 换成 `/v2/tasks`**，请求体、请求头和流式解析都不用改。示例：

   ```json
   POST /v2/tasks
   Authorization: Bearer <处理者 / 审核者本人的 INFO token>

   {
     "query": "<待审核的合同正文>",
     "user_id": "<处理者 / 审核者工号>",
     "target": "CONTRACT_REVIEW",
     "ext_param": { "task": "review_contract", "contract_type": "采购" }
   }
   ```

2. **身份用触发这次任务的处理者或审核者本人的 token 和工号**，和现在一样，平台照常按他的权限判断能否使用该助手。
3. **`target` 和 `task` 在页面里写成常量**，具体取值见各业务仓的对接说明。主体正文（被审核或被润色的那段）放在 `query` 里，其他参数放进 `ext_param`。
4. **按钮显不显示**：可以读 `GET /v2/modules` 返回的每个助手的新字段 `tasks`，里面有这个任务码才显示按钮，避免用户点了才报错。
5. **需要对同一张单据追问时**，带上上一次响应头里的 `conversation_id` 即可，和对话一样。老会话被 `/v2/tasks` 续上以后仍会留在会话列表里，不会消失。
6. **错误处理**：以下错误都在流式输出开始前以 JSON 返回：

   | 状态码 | 错误码 | 含义 |
   |---|---|---|
   | 400 | `invalid_param` | 缺 `target` 或 `task` |
   | 401 | | token 无效 |
   | 403 | `NOT_AUTHORIZED_FOR_MODULE` | 用户无权使用该助手 |
   | 404 | `MODULE_NOT_REGISTERED` | 助手暂未上线 |
   | 400 | `UNKNOWN_TASK` | 任务码未声明；响应里的 `available_tasks` 列出了可用的任务码，方便排查拼写 |

7. **切换时机**：等对应的业务仓声明了任务、平台部署 0.3.9 之后再切。切换后，这类调用不会再出现在用户的会话列表里。已经产生的历史会话暂时保持原样，之后统一整理。

完整说明见《INFO 对接 v2 API 协议》§3.8 和 §4。
