## 关键元数据结论（供后续 SQL 参考）

1. **类型不一致是最大坑**：
   - `OverseasProblemDetail` 几乎全用 `varchar`（含日期 `FoundDate`/`StopDate` 是 varchar，`IsDelete` 是 bit）；`ZCTracking_*` 系列全用 `nvarchar` + 真正的 `datetime` + `IsDelete` 为 int。**两表不能直接 UNION，日期/删除标记类型都要转换。**
   - `ZCTracking_ProblemList.Rate` 是 `decimal(8,2)`，而 `OverseasProblemDetail.Rate` 是 `varchar(50)`。
2. **tbIQCreportOut 的数量列全是 varchar**（fcount/fcheckcount/fbadcount/fbadper 都是 varchar(50)），做数值聚合必须先 TRY_CONVERT，不能直接 SUM。
3. **CAR 关联**：`ZCTracking_ProblemList.CARID`(int) ↔ `tbIQCreportOut.fid`(int, 主键)，类型匹配可直接 JOIN。
4. **子表外键**：`ZCTracking_ProductNames.ProblemId`、`ZCTracking_ProblemSteplog.ProblemId`、`ZCTracking_ProblemOrders.ProblemId`、`ZCTracking_OtherOrder.ProblemId` 均为 int NOT NULL，指向主表 `ID`。
5. **排序规则统一**：CoreINFO 与 info 均为 `Chinese_PRC_CI_AS`，跨库 JOIN 无 collation 冲突。
6. **tbIQCreportOut 列间隔大**（fid 在 1，fcount 在 13，fstep2 在 30+），说明该表很宽，本助手只用到了 19 列。
