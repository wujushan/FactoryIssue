# docs/1_user_input —— 复杂输入的临时投递区（不是信源，**仅开发者可编辑**）

业务逻辑较复杂时（例如一次追加一批新功能，附带需求清单、样例 SQL、数据字典、存储过程、业务方书面答复等），
开发者把原始材料放进这里，供编程助手梳理后落盘到 `docs/2_landed/`。内容简单直白时不必经过本目录——
在对话里直接交代，编程助手直接改 `2_landed/`。

> **编辑权限**：本目录**仅开发者可编辑**。编程助手只读、不改、也不清理本目录（guard 硬拦）；
> 清理由开发者 `git rm`。

## 怎么放

- **按批次 / 主题建子目录**，一批材料对应一次梳理，例如 `<主题>/<日期>/`。
- 放：需求清单、样例 SQL、数据字典、存储过程、旧系统截图与说明、业务方答复 / 执行结果等原始材料。
- 不放：真实业务数据行（查询结果、导出、样本 dump）——外部编程助手不得接触真实数据，确需样例请脱敏并在文件头注明。

## 生命周期

1. **投递**：开发者放入某个子目录，交代编程助手梳理。
2. **梳理**：编程助手阅读、整理，有歧义的地方列进 `docs/open-questions.md` 向业务方确认（答复同样可以放回该子目录）。
   新材料在落盘前只是待梳理的输入：与 `2_landed/` 现有口径冲突时**以 `2_landed/` 为准**，冲突本身作为歧义确认后再改 `2_landed/`。
3. **落盘**：结论与有用信息**复制**进 `2_landed/`，需要留痕的决策写进 `docs/decisions/`。
4. **梳理完成后**：任何文档与代码都**不再引用**本批材料中的文件。它们不作日后追溯依据，可随时清理。

> ⚠️ 本目录的材料只作梳理期间的临时素材，仅供理解业务逻辑，**不是信源，也不是技术选型标准**。
> 业务口径一律以 `docs/2_landed/` 为准，技术决策一律走 `docs/decisions/`（带日期）。
