# 平台需求：为「默认拒绝」类助手提供声明式的权限兜底

| 项 | 内容 |
|---|---|
| 提出方 | 制程问题查询助手（模块编码 `FACTORY_ISSUE`）业务仓 |
| 日期 | 2026-10-18 |
| 类型 | SDK 能力缺口（需求）；另请确认一项接口约定 |
| 涉及版本 | `paxsz-forge-core` 0.3.4、`paxsz-forge-data` 0.3.0、`paxsz-forge-platform` 0.3.4 |
| 涉及代码 | `forge_data/access/scoped.py`：`_resolve_table_scope()`、`ScopedDataAccess.describe()`；`forge_platform/privileges.py`：`PrivilegeResolver`、`OPEN_PRIVILEGES`；`forge_platform/auth.py`：`build_test_access_tree()`；`forge_platform/bus.py`：`_build_scoped_data()` |
| 验证方式 | 读源码 + 本地脚本实测（不连数据库，脚本与输出见文末） |
| 期望答复 | 是否接受需求、开关形态与排期；以及第 5 节三点确认 |

## 1. 一句话

要求「申请通过才能访问」（默认拒绝）的助手，在三种「没拿到可用授权」的情形下都会被放开：权限级别缺失或不认可、级别 A 但一张表都没列、权限平台返回空权限。业务仓自己补不了：这三种情形在模块里看到的权限，和平台自己下发的「绿灯」权限长得一样。请平台在 manifest 上提供声明式开关，由框架只对**真实向 INFO 拉取的权限**执行拒绝。

## 2. 业务场景

- 制程问题查询助手查国内、巴西、海外三个域的制程问题单。业务方要求与原有管理系统一致：每个域分别申请，**申请通过才能看，没配置就看不到**。另有国内 CAR 报告单独申请。
- 设想的配置（与客诉助手真实下发同一写法）：`defaultEffect = DENY`、`level.code = "A"`；已申请域的主表 `mode = ALLOW`，其子表挂在主表下、`inherit_parent = true`；共用主数据放最外层；未申请的域、未申请的 CAR 报告表不列出。
- 助手在每轮开头、取数之前，用 `ctx.data.describe()` 看三张主表、CAR 报告表是否可见，据此决定查哪些域、怎么回答（例如「巴西、海外无权限，未计入」）。助手**不自己解析**权限协议，表级判断都交给框架。

## 3. 缺口：三种情形都会放开

协议原文（权限信息传递协议 v1.3 字段描述 §15.1、§15.2）：

> §15.1：`privileges` 缺失或为 `{}` → 允许访问当前业务范围内的全部数据库数据与知识库内容。
> §15.2 第 2 条：如果 `level` 缺失、`level.code` 缺失，或者 `level.code` 不符合业务逻辑内预定义的取值范围，则按 `defaultEffect` 决定数据库默认权限：`ALLOW` 表示数据库全部允许，`DENY` 表示数据库全部拒绝。
> §15.2 第 3 条：对 DB 权限，如果 `dataScope` 不存在、为空数组或不包含 DB 权限项，则无需针对表、行、列执行细粒度权限管控，按 `level` 字段决定数据库权限。

| 情形 | 协议要求 | SDK / 平台实际（实测） | 对默认拒绝助手的后果 |
|---|---|---|---|
| ① `privileges` 非空，`level` 缺失或取值不在助手认可范围 | 按 `defaultEffect`；`DENY` 即整库拒绝 | 框架不执行 `level`（`compiler.py` 注释：「level 属业务仓自定义、框架不落地」），照常按 `dataScope` 选表 | 协议要求整库拒绝，实际照常可查 |
| ② `privileges` 非空、`level = A`，`dataScope` 为空或没有 DB 项 | 按 `level`，A 即整库允许 | 全部表放行 | INFO 漏生成表清单即整库放开，不报错 |
| ③ INFO 对本助手返回空权限（`Data` 为 `{}` / `null`） | §15.1：全放开 | 平台视为「该助手无行列管控」；即使 `require_privileges=True` 也放行（`bus._build_scoped_data` 传入 `privileges_resolved=True`，抵消了 `require_privileges`） | 对需要限制的用户误返回空权限，三域与 CAR 全放开 |

①② 是协议本身就定义的放行（② 完全合规，① 是框架未实现 `level`），③ 是平台按设计放行。三者对普通助手都合理；对「默认拒绝」的助手，它们的业务含义都是「没拿到可用的授权」，应当拒绝本轮。

## 4. 为什么业务仓自己补不了

最直接的想法是让助手在 `handle()` 开头读 `ctx.agent_node.privileges`：不带级别、或没有表项就拒绝。实际做不得，原因有二：

**(a) 平台自己的「绿灯」权限与 ①② 长得一样。** 平台在以下场景下发 `{"defaultEffect": "ALLOW", "dataScope": []}`：

| 场景 | 出处 |
|---|---|
| `/test/*` 自动化测试通道 | `auth.build_test_access_tree()` |
| Admin 调试对话、`forge dev serve` | `privileges.py` 模块注释第 2 条（旁路授权树） |
| 管理员在 Console 关闭该助手的数据权限管控 | `privileges.OPEN_PRIVILEGES`（`source = toggle_off`） |

这份权限不带 `level`、`dataScope` 为空。助手按 ①② 自查，就会把这几个场景一并拒掉：golden 测试集跑不了，本地调试跑不起来，管控开关的「放开」也会失效。而模块拿不到 `ResolvedPrivileges.source` / `resolved`，分不出这份权限是平台绿灯还是 INFO 漏配。

**(b) ③ 在模块里同样无法识别。** 空权限到模块是 `privileges is None`；旁路授权树、未按需解析时也可能是 `None`。区分它们的 `resolved` 标记只传给了取数层，没有暴露给模块。

此外，即便能自查，也等于每个默认拒绝的助手各自读协议字段（`level.code`、`dataScope`），协议调整时每个助手都要跟着改。这类兜底是通用机制，不是某个助手的业务。

## 5. 期望

### 5.1 manifest 声明式开关（主需求）

```python
manifest = ModuleManifest(
    code="FACTORY_ISSUE",
    require_privileges=True,
    accepted_levels=["A"],       # ① level 缺失或不在列表内 → 拒绝本轮
    require_table_scope=True,    # ② privileges 非空但没有任何 DB 表项 → 拒绝本轮
    empty_privileges="deny",     # ③ INFO 返回空权限 → 拒绝本轮；默认 "allow" 保持现行为
)
```

字段名与形态请平台定。要点：

- **只对 `source = info_api`（平台真实向 INFO 拉到的权限）生效**。`/test`、调试对话、`forge dev serve` 的绿灯树和管控开关关闭（`toggle_off`）不受影响，这几处的设计意图保持不变。
- 默认值保持现行为，不声明的助手零影响。
- 命中时与「拉不到权限」同样处理：拒绝本轮、`handle()` 不执行；给用户的提示不暴露协议细节；审计 / `turn_permissions` 日志记明命中哪一条。
- 权限级别的**含义**仍由业务定义，框架只执行「认可哪些取值」这一机制。

### 5.2 请确认 `describe()` 可作为表级权限判断的依据

`docs/dev/02`、`04` 写明 `describe()` 只列当前用户够得着的表。它的主要用途是给助手或 LLM 组查询的目录，本助手借用它做每轮开头的域判断。实测与源码一致：`describe()` 与 `fetch()` 共用 `_resolve_table_scope()` 的表级判定。请确认并写进 `docs/dev/04`：

1. 「表级无权的表不出现在 `describe()` 结果里」是稳定约定，可据此做权限判断。或者提供一个专门的接口（如「本轮可访问的表」），本仓改用它。
2. 实测：子表 `inherit_parent = true` 而父表表级被拒时，子表也不出现（`inherit_chain_denied` 生效）。请确认这也是约定的一部分。
3. 文档写明 `describe()` 只反映表级权限：表允许、但行规则拒绝全部行（如 `row.mode = ALLOW` 且 `rules = []`）时，表仍然出现，查出来为空。行级权限依赖数据，无法提前判断；需要「无权」与「无数据」分得开的助手要知道这一点。

## 6. 影响范围

- 所有要求「默认拒绝」的助手：目前 ①②③ 都无法可靠兜住。
- 不声明新开关的助手：无影响。

## 7. 本仓在平台实现前的做法

- **不在助手里做 ①② 自查**，原因见第 4 节 (a)。
- 由 INFO 侧承诺兜住：对本助手总是下发 `level.code = "A"`、总是列出表清单、不返回空权限；本助手的管控开关不得关闭（写成运维约定）。
- 每轮开头的域判断照常用 `describe()`；取数调用处接住 `TableDenied` 作为兜底。
- 平台发版后，升级 `paxsz-forge-*` 依赖、执行 `uv sync`，在 manifest 上声明开关。

## 附：复现脚本与实测输出

在任一装了上述版本的业务仓执行 `uv run python probe.py`：

```python
from forge_core.module import DataSourceRef
from forge_core.permissions.agentnode import AgentNode
from forge_data.access.scoped import ScopedDataAccess

MAIN = "CoreINFO.dbo.ZCTracking_ProblemList"
SUB = "CoreINFO.dbo.ZCTracking_ProblemSteplog"
CAR = "info.dbo.tbIQCreportOut"
REL = {"mappings": [{"parent_field": "ID", "child_field": "ProblemId"}]}
ref = DataSourceRef(alias="info", kind="sqlserver", tables=[MAIN, SUB, CAR])

def case(title, priv, resolved=True):
    acc = ScopedDataAccess(registry=None, field_mappings={}, data_sources=[ref],
                           agent_node=AgentNode.model_validate({"agent": "FACTORY_ISSUE", "privileges": priv}),
                           require_privileges=True, privileges_resolved=resolved)
    try:
        print(f"[{title}] ->", [t.table for c in acc.describe() for t in c.tables])
    except Exception as exc:
        print(f"[{title}] ->", type(exc).__name__)

only_main = [{"type": "DB", "table": {"name": f"info.{MAIN}", "mode": "ALLOW"}}]
case("① level=D", {"version": "1.3", "defaultEffect": "DENY", "level": {"code": "D"}, "dataScope": only_main})
case("① 不带 level", {"version": "1.3", "defaultEffect": "DENY", "dataScope": only_main})
case("② level=A、dataScope 为空", {"version": "1.3", "defaultEffect": "DENY", "level": {"code": "A"}, "dataScope": []})
case("③ 空权限，平台已按需拉取", {})
case("③ 空权限，未按需拉取", {}, resolved=False)
case("平台绿灯 / 开关关闭", {"defaultEffect": "ALLOW", "dataScope": []})
case("父表 DENY、子表继承父表", {"version": "1.3", "defaultEffect": "ALLOW", "level": {"code": "A"},
     "dataScope": [{"type": "DB", "table": {"name": f"info.{MAIN}", "mode": "DENY",
                   "sub_tables": [{"name": f"info.{SUB}", "mode": "ALLOW", "inherit_parent": True, "relation": REL}]}}]})
case("表 ALLOW、行规则拒绝全部行", {"version": "1.3", "defaultEffect": "DENY", "level": {"code": "A"},
     "dataScope": [{"type": "DB", "table": {"name": f"info.{MAIN}", "mode": "ALLOW", "row": {"mode": "ALLOW", "rules": []}}}]})
```

2026-10-18 实测输出：

```text
[① level=D] -> ['CoreINFO.dbo.ZCTracking_ProblemList']
[① 不带 level] -> ['CoreINFO.dbo.ZCTracking_ProblemList']
[② level=A、dataScope 为空] -> ['CoreINFO.dbo.ZCTracking_ProblemList', 'CoreINFO.dbo.ZCTracking_ProblemSteplog', 'info.dbo.tbIQCreportOut']
[③ 空权限，平台已按需拉取] -> ['CoreINFO.dbo.ZCTracking_ProblemList', 'CoreINFO.dbo.ZCTracking_ProblemSteplog', 'info.dbo.tbIQCreportOut']
[③ 空权限，未按需拉取] -> PrivilegesRequiredError
[平台绿灯 / 开关关闭] -> ['CoreINFO.dbo.ZCTracking_ProblemList', 'CoreINFO.dbo.ZCTracking_ProblemSteplog', 'info.dbo.tbIQCreportOut']
[父表 DENY、子表继承父表] -> ['info.dbo.tbIQCreportOut']
[表 ALLOW、行规则拒绝全部行] -> ['CoreINFO.dbo.ZCTracking_ProblemList']
```

读法：
- ① 两行：`level` 被忽略，按 `dataScope` 照常放行国内主表。
- ② 与「平台绿灯」两行结果相同，模块无法区分。
- ③ 第一行：`require_privileges=True` 被 `privileges_resolved=True` 抵消，全放开。
- 「父表 DENY」一行：继承父表的子表随父表消失，未列出的 CAR 报告表按 `defaultEffect = ALLOW` 可见。
- 最后一行：表仍在目录里，但查询时行级 WHERE 为 `1 = 0`。
