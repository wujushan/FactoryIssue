## 一句话

`search(restrict_ids=...)` 按向量行 `id` 限定，声明式向量化又是「一行源记录出一个向量」。长文本要切块时，一条业务记录在向量表里有多行，模块手里的候选是业务记录编号、向量行 `id` 却是块编号，两者对不上；返回的前 `top_n` 条也可能被同一条记录的多个块占满。建议向量表多带一列「业务记录编号」，限定与去重都按它做，不切块的模块不受影响。

分段之后还连带两件事：用户点名某个字段时（「原因分析里提到非接的单」），检索没法只在该字段的段里找；三个域各一张向量表、分别检索后要合并，而重排分数不带回模块，合并只能按向量分数比。建议向量表再带一列「字段」并可按它限定，命中结果带回重排分数（见「按字段限定与跨表合并」一节）。

## 业务场景

- 「类似问题」：用户描述一个缺陷现象，助手找出历史上最相近的若干条业务记录（问题单）及其处理方式。用户同时给了机型、工厂、时间等条件时，模块先经 `ctx.data.fetch()` 在原始表上取出符合条件的记录编号，再用 `restrict_ids` 只在这些记录里找（这个参数已在 core 0.3.5 / data 0.3.1 发布，工作正常）。
- 每条记录的比对文字由问题描述、原因分析、改善措施等几段组成。正式数据画像：剥掉内嵌图片后，问题描述 97% 在 1,000 字以内（含格式）。长度远在 embedding 输入上限之内，但**切块的理由不是长度上限，是检索粒度**：用户常用很短的说法找单（「非接」「音频」），而这件事可能只是整段里的一句。整条记录压成一个向量时，这一句的分量被其余内容稀释，相关记录排不进向量召回的前列。
- 所以提出方决定：每条记录按字段分段（问题描述、原因分析、改善措施各一段），单个字段过长再按段落切，一段一个向量。三域约 3,000 条记录，约 1 万个向量。
- 这样一条业务记录在向量表里有 2–3 行甚至更多，正是本文要解决的情形。其他做文档、报告类检索的模块同样会遇到。

## SDK 当前行为

1. **`VectorizeSpec` 没有切块或业务记录编号相关字段**，回填 SQL 把 `id_column` 转文字直接当向量行 `id`（见文末输出 [1][2]）。要切块，只能由治理任务把源表落成「一块一行」的治理后表（块编号作 `id_column`，如 `2811#0`、`2811#1`），再声明向量化读它。这符合「表达力边界是单表 + 列拼接、复杂拼装靠治理」的既有定位。
2. **`restrict_ids` 只匹配向量行 `id`**：编译为 `id = ANY(%(restrict_ids)s::text[])`（输出 [4]）。传业务记录编号 `2811`，对块编号 `2811#0` 一条都不中，且不报错。
3. **命中结果没有业务记录编号**：`VectorHit` 只有 `id`、`text`、`score`、`metadata`（输出 [5]），声明式回填不写 `metadata`。模块要从块编号里自己解析出记录编号。
4. **结果不按记录去重**：`top_n = 10` 时，一条很长的记录的 6 个块可能同时排进前 10，用户看到的「最相近的 10 条」实际只有 5 条。

## 现在能用的做法（平台不改也能做，代价见右）

| 步骤 | 做法 | 代价 |
|---|---|---|
| 候选展开 | 治理后表带「业务记录编号」列；模块先经 `ctx.data.fetch()` 查这张表，把候选记录编号展开成块编号，再传 `restrict_ids` | 每次检索多一次取数；5,000 上限按块数算，候选记录多、块多时更早撞上限 |
| 结果归并 | 模块按块编号前缀归回记录，同一记录留得分最高的块 | 为凑够 10 条不同记录，`top_n` 要放大到「10 × 每条记录最多块数」，rerank 的文本量随之放大；仍可能不足 10 条 |
| 不带条件的检索 | 无法展开候选，只能放大 `top_n` 后归并 | 同上 |

可行，但每个要切块的模块都得把「展开 → 检索 → 归并」重写一遍，且归并依赖块编号的拼法约定，平台无从校验。

## 期望

**方案 1（倾向）：向量表带业务记录编号列，限定与去重按它做**

- `VectorizeSpec` 增加可选字段 `record_column`：治理后表里标识业务记录的列，**缺省等于 `id_column`**。平台建表时多建一列 `record_id`（text，btree 索引），回填时与权限承载列一样透传。
- `restrict_ids` 匹配 `record_id`。不切块时 `record_id = id`，行为与 0.3.1 完全相同，现有模块不用改。
  - 实现上 `PgVectorIndex` 已经把限定条件写在 `id_col` 上（`ScopedRetrieval.search` 也接受 `id_col`），新增一个「限定用列」即可复用现有的物化候选 + 精确排序逻辑。
- `search()` 增加可选参数（如 `distinct_records=True`）：同一 `record_id` 只留得分最高的块，返回 `top_n` 条**不同记录**。近邻阶段多取多少、rerank 前还是后去重，由平台定；契约是「返回 `top_n` 条不同记录，不足时是真的不够」。
- `VectorHit` 带上 `record_id`（新字段或放进 `metadata`），模块凭它回源取展示字段。
- 5,000 上限按记录编号个数计。
- 切块本身仍归治理任务（块大小、重叠、按段落切随业务定）；平台以后若内建切块，上述契约不变。

**方案 2：只加去重，不改限定**

`VectorizeSpec` 增加 `record_column` 并写进向量表，`search()` 只增加按它去重；限定仍按块 `id`，候选展开由模块做（上表第一行）。改动小一些，但模块侧仍要多一次取数，上限也仍按块数算。

## 按字段限定与跨表合并（分段带来的另外两项）

### 场景

上面的分段让每段带上所属字段（问题描述、现象、原因分析、改善措施）。本助手由此多出两种检索：

- **只在某个字段里找**：用户点名字段，如「原因分析里提到非接的单」「改善措施里写了更换物料的单」。只检索该字段的段，问题描述里顺带提到的不算。
- **三个域一起找**：国内、巴西、海外三个域各自授权（权限平台对三域的表分别给允许 / 拒绝），所以每个域一张向量表、按域授权。用户没点明域时，三个有权的域各检索一次，再合并成一份「最相近的 10 张单」。

### 现在能用的做法与问题

| 需求 | 现在的做法 | 问题 |
|---|---|---|
| 只在某个字段里找 | 治理后表带「字段」列；模块先经 `ctx.data.fetch()` 取出该字段的段编号，再传 `restrict_ids` | 每次多一次取数；`restrict_ids` 本来留给「机型、工厂、时间」这类条件用，现在还要承担字段限定，两者叠加后段数更容易接近 5,000 上限；模块要自己保证段编号与字段对得上 |
| 三个域一起找 | 三张表各检索、各重排一次，模块合并 | 重排只调整顺序，命中的 `score` 仍是向量相似度，重排分数不带回（复现二 [2]）。模块合并三张表的结果时只能比向量分数，重排对表与表之间的先后没有作用（复现二 [3]）。用「各表轮流取一张」之类的办法也只是绕开，不是按相关程度排 |

`search()` 没有按字段或其他列限定的参数（复现二 [1]）；三域放进同一张表再按域过滤也不行，因为域权限是表级的，同表内无法按域授权。

### 期望

**一、向量表带「字段」列，`search()` 可按它限定**

- `VectorizeSpec` 增加可选字段 `field_column`：治理后表里标识字段的列。平台建表时多建一列（text，btree 索引），回填时照抄，与方案 1 的 `record_column` 同样处理。
- `search()` 增加可选参数 `fields=["reason"]`：编译成该列 `= ANY(...)`，与行级权限、`restrict_ids` 都是 AND。不传即不限定。
- 不声明 `field_column` 时，传 `fields` 报错，不静默忽略。

更通用的写法是 `VectorizeSpec` 声明一组可过滤列、`search()` 接受与 `QuerySpec.filter` 同形的条件；本助手只用得到「字段」这一列，哪种由平台定。

**二、命中带回重排分数**

- `VectorHit` 增加 `rerank_score`（没配重排或重排失败回退时为空），模块按它合并多张表的结果。不影响现有调用方。
- 同一个重排模型、同一个问句，各次调用的分数可以直接比较；配了重排时，模块合并只用重排分数。
- 第二个用途：**按分数阈值判断相关性**。本助手回答「有没有涉及非接」时，要从按词命中的单里分出「真涉及」与「只是提到」（如「NFC 测试正常」）、从说法有歧义的命中里去掉不相关的。现在只能逐张调大模型判断，几十张就要很久，结论还可能前后不一致。Qwen3-Reranker 是按「是 / 否满足查询」训练的，分数就是「是」的概率；模块把按词命中的段用 `restrict_ids` 交给检索、拿回分数，就能按阈值判断，比大模型快、结果稳定。若平台同时支持「查询侧任务说明」那份反馈里的说明参数，阈值判断会更准。
- 若平台更愿意在一次调用里检索多张表、合并后统一重排（各表各自施加行级权限），也满足本助手的需要，并且省去模块侧合并。

## 影响范围

- 只影响切块或分段向量化的模块，以及要合并多张向量表结果的模块；其他模块在各方案下行为都不变。
- 不做方案 1 / 2 的话，切块模块要么自己写展开与归并（上表），要么回到「全表召回再求交」——那正是 `restrict_ids` 刚消除的静默少召回。
- 不带回重排分数的话，凡是按权限分表、再合并检索结果的模块，合并后的先后都只反映向量相似度。

## 附：开发者文档示例的列名

`docs/dev/02`、`04` 的 `restrict_ids` 示例写的是 `ctx.data.fetch(spec)["issue_no"].tolist()`，注释是「向量行 id = 源表 id 列转 text，直接传」。按常见命名，`issue_no` 像是业务单号（如 `ZC2509012`），而向量行 `id` 来自 `id_column`（通常是主键）。照抄示例传了单号，结果是 0 条且不报错（`11` 排查表里已列这种症状）。建议示例改成 `id_column` 那一列，例如 `["issue_id"]`，并在注释里写「传 `manifest.vectorize` 的 `id_column`，不是业务单号」。

## 复现二：按字段限定与跨表合并

不连任何服务，环境同上：

```python
"""复现（0.3.1）：检索没有按字段限定的参数；分表检索后重排分数不带回，跨表合并只能比向量分数（不连任何服务）。"""

import asyncio
import inspect
from importlib.metadata import version

from forge_core.module import RetrievalPort
from forge_data.retrieval.index import VectorHit
from forge_data.retrieval.rerank import rerank_candidates

for pkg in ("paxsz-forge-core", "paxsz-forge-data"):
    print(f"{pkg} {version(pkg)}")

params = list(inspect.signature(RetrievalPort.search).parameters)
print("\n[1] RetrievalPort.search 参数:", params)
print("    有没有按字段限定的参数:", any(p in params for p in ("fields", "filter", "where")))


class FakeReranker:
    """按给定的分数表打分，模拟重排模型。"""

    def __init__(self, scores):
        self.scores = scores

    async def rerank(self, query, documents, *, top_n=None):
        ranked = sorted(enumerate(self.scores), key=lambda x: -x[1])
        return ranked[:top_n] if top_n else ranked


# 两张向量表（两个域）各自检索、各自重排
domestic = [VectorHit(id="2811:desc:0", text="问题描述：刷卡区感应无反应", score=0.52, metadata={}),
            VectorHit(id="2830:desc:0", text="问题描述：外壳刮伤", score=0.50, metadata={})]
brazil = [VectorHit(id="105:desc:0", text="问题描述：NFC 读卡距离不足", score=0.31, metadata={})]

d = asyncio.run(rerank_candidates(FakeReranker([0.40, 0.05]), "非接", domestic, text=lambda h: h.text))
b = asyncio.run(rerank_candidates(FakeReranker([0.95]), "非接", brazil, text=lambda h: h.text))
print("\n[2] 国内表重排后:", [(h.id, h.score) for h in d], "（重排分 0.40 / 0.05）")
print("    巴西表重排后:", [(h.id, h.score) for h in b], "（重排分 0.95）")
merged = sorted(d + b, key=lambda h: -h.score)
print("[3] 模块按手上的 score 合并:", [h.id for h in merged])
print("    按重排分本应是:", ["105:desc:0", "2811:desc:0", "2830:desc:0"])
```

实际输出（2026-10-20）：

```text
paxsz-forge-core 0.3.6
paxsz-forge-data 0.3.1

[1] RetrievalPort.search 参数: ['self', 'query', 'source', 'table', 'top_k', 'top_n', 'restrict_ids']
    有没有按字段限定的参数: False

[2] 国内表重排后: [('2811:desc:0', 0.52), ('2830:desc:0', 0.5)] （重排分 0.40 / 0.05）
    巴西表重排后: [('105:desc:0', 0.31)] （重排分 0.95）
[3] 模块按手上的 score 合并: ['2811:desc:0', '2830:desc:0', '105:desc:0']
    按重排分本应是: ['105:desc:0', '2811:desc:0', '2830:desc:0']
```

[1]：除 `restrict_ids` 外没有限定参数。[2]：重排后命中的 `score` 仍是向量分数。[3]：巴西那张单重排分最高（0.95），合并后却排在最后；国内那张「外壳刮伤」与问句无关（重排分 0.05），仍排在它前面。重排模型是假的，分数只为示意；结论（重排分数不带回）来自平台源码 `rerank_candidates` 返回原候选对象。

| `restrict_ids` 按业务记录编号匹配 | `search(restrict_column="record_id")`；不传时仍按向量行 `id`，老用法不变 | 满足 |
| 返回 `top_n` 条不同记录 | `search(group_by="record_id")`；带 `restrict_ids` 时精确，不带时近邻多取 4 倍再折叠、只能尽量凑满 | 满足；不带候选时是近似 |
| 命中带回业务记录编号 | `h.metadata["record_id"]` | 满足 |
| 5,000 上限按记录编号个数计 | 上限仍按 `restrict_ids` 去重后的个数，按记录编号传即按记录数计 | 满足（文档未单独写明） |
| 按字段限定（`field_column` + `fields`） | `search(filters={"field": [...]})`，等值 / IN；引用未声明的列报 `RetrievalColumnNotDeclared`，不静默忽略 | 满足，采用了本文提的通用写法 |
| 命中带回重排分数 | `VectorHit.rerank_score`；按权限分表后合并按它排，`None` 时才退回 `score` | 满足 |
| 一次调用检索多张表并统一重排 | 未做，仍由模块按 `rerank_score` 合并 | 本文列为可选，不要求 |
| 附：文档示例 `issue_no` 改为 `id_column` | 02、04 已改为 `issue_id`，注释写明不是业务单号 | 满足 |

文档另提醒：向量表建成后再加 `metadata_columns` 不会自动补列（DDL 都是 `IF NOT EXISTS`），需手工 `ALTER TABLE` 并重跑回填。本仓的 mart 尚未建库，`metadata_columns` 会在建库前写进声明。
