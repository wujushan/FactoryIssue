# 平台反馈：表上整个行 / 列声明缺失时，SDK 的处理与协议 v1.3 不一致

| 项 | 内容 |
|---|---|
| 提出方 | 制程问题查询助手（模块编码 `FACTORY_ISSUE`）业务仓 |
| 日期 | 2026-10-18 |
| 类型 | SDK 行为与协议描述不一致；`docs/dev/04` 未写明该情形 |
| 涉及版本 | `paxsz-forge-data` 0.3.0、`paxsz-forge-core` 0.3.4 |
| 涉及代码 | `forge_data/scopefilter/compiler.py`：`_ScopeCompiler.row()`、`_partition_columns()` |
| 验证方式 | 读源码 + 本地脚本实测（不连数据库，脚本与输出见文末） |
| 期望答复 | 采用下文方案 1 或方案 2，并写进 `docs/dev/04` |

## 一句话

`defaultEffect = DENY` 时，一张表**整个不写** `row`，SDK 放行全部行；**写了 `row` 但不给 `mode`**，SDK 拒绝全部行。协议对这两种情形的字面要求都是「按 `defaultEffect`」，即都应拒绝。`column` 同理。差异只在 `DENY` 下出现，方向是放开，而且不报错。

## 为什么这件事现在冒出来

- 制程问题查询助手管国内、巴西、海外三个域的制程问题单。业务方要求与原有管理系统一致：**每个域申请通过才能看，没配置就看不到**。因此本助手计划让 INFO 权限平台下发 `defaultEffect = DENY`，按用户已申请的域列出可访问的表（共约 29 张）。
- 目前平台上的助手大多用 `defaultEffect = ALLOW`（例如客诉助手）。`ALLOW` 下「缺失 = 放行」与「按 defaultEffect = 放行」结果相同，所以这个差异一直没暴露。
- INFO 生成权限配置时，是否给每张表都写出 `row`、`column`，由它的生成规则决定。客诉助手的真实下发里每张表都写了，但没有任何约定保证一定会写。

## 协议原文（权限信息传递协议 v1.3，字段描述文档）

- **§15.3 默认规则表**，相邻的三行：
  - 「某个 `table.row.mode` 不存在、为空或取值不合法 → 按 `defaultEffect` 决定该表行级默认权限。」
  - 「子表 `inherit_parent = true` 且整个 `table.row` 字段缺失 → 该子表自身不增加行级限制……`row` 存在但 `row.mode` 缺失、为空或非法时，仍按上一行处理。」
  - 「某个 `table.column.mode` 不存在、为空或取值不合法 → 按 `defaultEffect` 决定该表列级默认权限。」
- **§20.5 第 7 条**与 **§21** 重复同一例外：「子表 `inherit_parent = true` 且整个 `row` 字段缺失时例外。」
- **§22**：「如果 `table.column.mode` 不存在、为空或取值不合法，应按 `defaultEffect` 决定该表列级默认权限。」没有例外。

**我们的理解**：协议单独为「继承父表的子表 + 整个 `row` 缺失」开了「不加限制」的例外。如果「整个 `row` 缺失」对所有表都等于不加限制，这个例外就没有必要写。所以按字面理解，**非继承父表的表整个缺 `row` 属于「`row.mode` 不存在」，应按 `defaultEffect` 处理**；`column` 没有任何例外，整个缺失也应按 `defaultEffect` 处理。

## SDK 当前行为

`forge_data/scopefilter/compiler.py`：

```python
# _ScopeCompiler.row()
if row is None:                       # 整个 row 缺失
    return SQLFragment.ALLOW_ALL_TEXT # → "1 = 1"，不看 defaultEffect、不看 inherit_parent
if row.mode is None:                  # row 写了但缺 mode
    return DENY_ALL_TEXT if self._default is Effect.DENY else ALLOW_ALL_TEXT

# _partition_columns()（resolve_columns / require_columns 共用）
if column_scope is None:              # 整个 column 缺失
    return list(requested), [], False # → 不裁剪
if column_scope.mode is None:         # column 写了但缺 mode
    if default_effect is Effect.DENY:
        raise PermissionDenied(...)   # → 整个查询拒绝
```

`docs/dev/04` 的写法是「`row` 缺 `mode`、`column` 缺 `mode` 时用 `defaultEffect`」，没有提整个 `row` / `column` 缺失的情形。

## 实测结果（`defaultEffect = DENY`，表级 `mode = ALLOW`）

| 该表的写法 | 行（编译出的 WHERE） | 列 | 协议字面要求 |
|---|---|---|---|
| `row`、`column` 都不写 | `1 = 1`（全部行） | 不裁剪 | 按 DENY |
| `"row": {"rules": []}`（无 mode） | `1 = 0`（无行） | — | 按 DENY ✔ |
| `"column": {"rules": []}`（无 mode） | — | 抛 `PermissionDenied` | 按 DENY ✔ |
| `"row": {"mode": "DENY", "rules": []}`、`"column": {"mode": "DENY", "rules": []}` | `1 = 1` | 不裁剪 | 不限行、不屏蔽列 ✔ |
| 同第一行，但 `defaultEffect = ALLOW` | `1 = 1` | 不裁剪 | 按 ALLOW ✔ |

第一行与第二、三行的差别只是「整个不写」与「写了空对象」，SDK 给出相反的结论。

## 期望（二选一，并写进 `docs/dev/04`）

1. **SDK 向协议对齐**：非继承父表的表整个缺 `row`，按 `defaultEffect` 处理；任何表整个缺 `column`，按 `defaultEffect` 处理。继承父表的子表整个缺 `row` 仍不加限制（协议例外）。
2. **保留 SDK 现行为**：与权限协议制定方确认「整个 `row` / `column` 缺失 = 不加限制」，修订协议 §15.3、§21、§22 的措辞，消除字面歧义，并在 `docs/dev/04` 明写。

**倾向方案 1**，理由：

- SDK 现行为在 `DENY` 下比协议宽松，方向是放开；权限代码里两边理解不一致时，应取拒绝的一边。
- 现行为与 SDK 自己对「写了但缺 mode」的处理不对称，配置方很难预料。

方案 1 对存量助手的影响：只有 `defaultEffect = DENY` 且省略了 `row` / `column` 的表会从「放行」变成「拒绝」。上线前可按助手扫一遍 INFO 实际下发的权限，看有没有这种写法。

## 影响范围

- `defaultEffect = DENY`、且 INFO 对某些表省略 `row` 或 `column` 的助手：协议本意是拒绝，SDK 实际放行，不报错，事后也难察觉。
- `defaultEffect = ALLOW` 的助手：不受影响。

## 本仓在结论出来前的做法

请 INFO 对本助手的每张表都显式写出 `"row": {"mode": "DENY", "logic": "OR", "rules": []}`、`"column": {"mode": "DENY", "rules": []}`（与客诉助手的真实下发同一写法），只有继承父表的子表省略 `row`。这样两种理解结果一致，本仓不依赖本反馈的结论即可推进。

## 附：复现脚本（在任一装了上述版本的业务仓执行 `uv run python probe.py`）

```python
from forge_core.permissions.agentnode import AgentNode
from forge_data.access.scoped import _resolve_table_scope
from forge_data.scopefilter.compiler import FieldResolver, compile_table_scope, resolve_columns

MAIN = "CoreINFO.dbo.ZCTracking_ProblemList"

def case(title, table_scope, default="DENY"):
    priv = {"version": "1.3", "defaultEffect": default, "level": {"code": "A"},
            "dataScope": [{"type": "DB", "table": table_scope}]}
    node = AgentNode.model_validate({"agent": "FACTORY_ISSUE", "privileges": priv})
    row, col, eff, denied, path = _resolve_table_scope(node, MAIN)
    frag = compile_table_scope(row, table=MAIN, fields=FieldResolver.fixed({}), path=path, default_effect=eff)
    try:
        cols = resolve_columns(["Numbers", "ProblemType"], col, mapping={}, default_effect=eff)
    except Exception as exc:
        cols = type(exc).__name__
    print(f"[{title}] defaultEffect={default} row_where={frag.text!r} columns={cols}")

case("row、column 都不写", {"name": f"info.{MAIN}", "mode": "ALLOW"})
case("row、column 都不写", {"name": f"info.{MAIN}", "mode": "ALLOW"}, default="ALLOW")
case("row 写了、缺 mode", {"name": f"info.{MAIN}", "mode": "ALLOW", "row": {"rules": []}})
case("column 写了、缺 mode", {"name": f"info.{MAIN}", "mode": "ALLOW", "column": {"rules": []}})
case("显式 DENY 空规则", {"name": f"info.{MAIN}", "mode": "ALLOW",
     "row": {"mode": "DENY", "logic": "OR", "rules": []}, "column": {"mode": "DENY", "rules": []}})
```

2026-10-18 实测输出：

```text
[row、column 都不写] defaultEffect=DENY row_where='1 = 1' columns=['Numbers', 'ProblemType']
[row、column 都不写] defaultEffect=ALLOW row_where='1 = 1' columns=['Numbers', 'ProblemType']
[row 写了、缺 mode] defaultEffect=DENY row_where='1 = 0' columns=['Numbers', 'ProblemType']
[column 写了、缺 mode] defaultEffect=DENY row_where='1 = 1' columns=PermissionDenied
[显式 DENY 空规则] defaultEffect=DENY row_where='1 = 1' columns=['Numbers', 'ProblemType']
```

脚本调用了 `_resolve_table_scope` 这个内部函数，只用于复现；它与 `ctx.data.fetch()` / `query()` 走的是同一段选表与编译逻辑。
