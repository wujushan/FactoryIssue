## 一句话

Qwen3-Embedding 与 Qwen3-Reranker 都要求「查询侧带一句任务说明、文档侧不带」，模型说明里写明不带会让检索效果下降约 1%–5%。平台现在把用户问句原样发给两个服务；而且向量化与重排共用同一个 `query`，模块即使自己在问句前拼上说明，拼出来的文字也会原样进 rerank，两侧没法分开处理。

## 业务场景

- 「类似问题」「涉及某现象的问题」：用户的问句往往很短，常是一个行业简称，如「非接」（非接触式读卡）、「音频」；被检索的是一两百字到上千字的问题描述、原因分析、改善措施。
- 这正是「短问句找长文档」的非对称检索，模型的任务说明就是为这种场景设计的。说明也能告诉模型「这是工厂制程缺陷记录、按缺陷现象匹配」，比裸问句更不容易匹配到格式相近但内容无关的文本。
- 被检索的文字里混着大量行业缩写（NFC、LCD、PCB、USB 等）与中文简称，问句与文档的说法常常不同，更依赖模型按任务理解「这是在找缺陷现象」。

## 模型方的说明（Qwen 官方模型卡）

[Qwen3-Embedding-8B 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-8B)与 [Qwen3-Reranker-8B 模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-8B)（内容经转述）：

- 两个模型都标为「Instruction Aware」：可以按任务自定义输入的任务说明。
- 多数下游任务里，加任务说明比不加通常提升 1%–5%；不加查询侧说明，检索效果约下降 1%–5%。官方建议按场景写专门的说明；多语言场景建议用英文写。
- 向量化：查询写成 `Instruct: {任务说明}\nQuery:{问句}`，文档不加说明。
- 重排：输入写成 `<Instruct>: {任务说明}\n<Query>: {问句}\n<Document>: {文档}`，外面再包一层固定的系统提示；不给说明时，示例代码用默认的「Given a web search query, retrieve relevant passages that answer the query」。

## SDK 当前行为

1. `EmbeddingClient.embed(texts)` 把文本原样放进 `/embeddings` 请求的 `input`，问句与文档走同一个方法，没有区分（输出 [3]）。
2. `RerankClient.rerank(query, documents, top_n=)` 把问句原样放进 `/rerank` 请求的 `query`（输出 [3]）。
3. `retrieve()` 用**同一个** `query` 先调 `embedder.embed([query])`、再调 `rerank_candidates(reranker, query, ...)`；`ScopedRetrieval.search` 与 `RetrievalPort.search` 只有一个 `query` 参数。
4. 结果：模块如果在问句前拼 `Instruct: ...\nQuery:`，这段文字会原样进 rerank 的 `query`，与重排模型要求的格式不符。

## 需要平台先确认的一点

`/rerank` 背后的推理服务（如 vLLM）可能已经按 Qwen3-Reranker 的模板自动包上系统提示与默认任务说明；`/embeddings` 一般不会替查询加说明。业务仓看不到服务端配置，请平台确认：

- `/embeddings` 是否对输入做任何处理（预期：不做）；
- `/rerank` 是否套用 Qwen3-Reranker 的模板、用的是哪句默认任务说明、能否按请求传入自定义说明。

## 期望

**方案 1（倾向）：`search()` 增加可选的任务说明参数，两侧分别处理**

```python
hits = await ctx.retrieval.search(
    "非接触式读卡相关的问题，如刷卡无反应、读卡失败",
    source="forge_mart_factory_issue", table="domestic_issue_vec",
    instruction="Given a defect phenomenon from factory process quality reports, "
                "retrieve report passages describing the same or related defect",
    restrict_ids=[...],
)
```

- 向量化侧：平台把查询写成 `Instruct: {instruction}\nQuery:{query}`；文档回填不变。
- 重排侧：平台按服务端支持的方式传入同一句说明（服务端支持自定义说明时传说明，问句保持原样）；服务端不支持时只传原问句，不把说明拼进问句。
- `instruction=None` 时与现在逐字节相同，现有模块不受影响。
- 审计照常记录问句原文；说明可记可不记。

**方案 2：平台按向量表配一句默认说明**

在 `VectorizeSpec` 上增加 `query_instruction`，检索这张表时平台自动带上。好处是模块不必每次传；缺点是同一张表上不同问法（找现象、找做法）只能用一句。可以与方案 1 并存：调用时传的优先。

## 影响范围

- 所有用 `ctx.retrieval` 的模块都受影响，短问句、跨语言、领域术语多的场景更明显。
- 效果差别不会报错，只表现为召回与排序变差，需要用评测集比较才看得出来。

## 业务仓的临时做法（平台实现前）

- 不在问句里拼任务说明（避免污染 rerank 输入）。
- 检索用的问句是一句不看上下文也能懂的现象描述：对话里的指代先消解成具体现象（「那个问题以前有过吗」→「刷卡时读卡无反应」）；问「有没有涉及非接」这类话题时，用本模块话题清单里该话题的一句说明（如「非接触式读卡相关的问题，如刷卡无反应、读卡失败」）。
- 不把同义说法串成一串拼进问句（「非接 非接触 NFC 射频 感应」）：有研究发现，把扩写后的查询直接交给神经重排模型，效果可能下降。同义说法只用在关键词匹配那一路。
- 关键词与语义两路合并：带同义说法的关键词匹配保证完整，语义检索补上换了说法的记录。
- 评测集按上面这种问句记录召回，平台实现后对比加说明前后的差别。

## 复现

不连任何服务。在装有 `paxsz-forge-core` 0.3.6、`paxsz-forge-data` 0.3.1 的环境执行：

```python
"""复现：检索时问句原样做 embedding 与 rerank，无查询侧任务说明，且两侧共用同一个 query（不连任何服务）。"""

import asyncio
import inspect
from importlib.metadata import version

import httpx

from forge_core.llm import EmbeddingClient, RerankClient
from forge_data.retrieval.index import VectorHit
from forge_data.retrieval.pipeline import retrieve

for pkg in ("paxsz-forge-core", "paxsz-forge-data"):
    print(f"{pkg} {version(pkg)}", flush=True)

sent = []


def handler(request: httpx.Request) -> httpx.Response:
    import json as _json

    body = _json.loads(request.content)
    endpoint = request.url.path.rsplit("/", 1)[-1]
    sent.append((endpoint, body))
    if endpoint == "embeddings":
        return httpx.Response(200, json={"data": [{"index": i, "embedding": [0.0] * 4}
                                                  for i, _ in enumerate(body["input"])]})
    return httpx.Response(200, json={"results": [{"index": i, "relevance_score": 0.5}
                                                 for i, _ in enumerate(body["documents"])]})


_orig_init = httpx.AsyncClient.__init__


def _patched_init(self, *args, **kwargs):
    kwargs["transport"] = httpx.MockTransport(handler)
    _orig_init(self, *args, **kwargs)


httpx.AsyncClient.__init__ = _patched_init


class FakeIndex:
    def search(self, embedding, top_k, *, scope_where="", scope_params=None, restrict_ids=None):
        return [VectorHit(id="2811#desc#0", text="问题描述：刷卡区感应无反应", score=0.3, metadata={})]


async def main():
    emb = EmbeddingClient("http://embed.invalid/v1", "Qwen3-Embedding-8B")
    rr = RerankClient("http://rerank.invalid/v1", "Qwen3-Reranker-8B")
    await retrieve("非接", embedder=emb, index=FakeIndex(), reranker=rr, top_k=50, top_n=10)


print("\n[1] EmbeddingClient.embed 签名:", inspect.signature(EmbeddingClient.embed))
print("[2] RerankClient.rerank 签名:", inspect.signature(RerankClient.rerank))
asyncio.run(main())
print("\n[3] 检索「非接」时实际发出的请求体:")
for endpoint, body in sent:
    print(f"    /{endpoint}:", body)
```

[1] EmbeddingClient.embed 签名: (self, texts: 'list[str]') -> 'list[list[float]]'
[2] RerankClient.rerank 签名: (self, query: 'str', documents: 'list[str]', *, top_n: 'int | None' = None) -> 'list[tuple[int, float]]'
