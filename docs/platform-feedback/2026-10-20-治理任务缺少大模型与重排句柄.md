# 平台反馈：治理任务里拿不到大模型与重排模型，没法在入库时给文字打标签

| 项 | 内容 |
|---|---|
| 提出方 | 制程问题查询助手（模块编码 `FACTORY_ISSUE`）业务仓 |
| 日期 | 2026-10-20 |
| 类型 | SDK 能力缺口（需求）。不阻塞上线：实现前在查询时做有限判断（见「业务仓的临时做法」） |
| 涉及版本 | `paxsz-forge-core` 0.3.6、`paxsz-forge-data` 0.3.1 |
| 涉及代码 | `forge_core/jobs.py`：`JobContext`；对照 `forge_core/module.py`：`ModuleContext.llm`；重排客户端 `forge_core/llm.py`：`RerankClient` |
| 验证方式 | 读源码 + 本地脚本实测（不连任何服务，脚本与输出见文末） |
| 期望答复 | 是否采纳下文方案 1（或方案 2）及预计版本 |

## 一句话

`handle()` 里有 `ctx.llm`，治理任务（`jobs()` 注册的定时任务）的 `JobContext` 里只有 `embedder`、`etl`、`config` 和进度回调，没有大模型，也没有重排模型。按平台红线，模块又不能自己创建客户端、不能读环境变量。所以「入库时让模型给每段文字打一次标签、查询时直接按标签筛」这类做法在模块里做不了，只能每次提问时临时判断，又慢又不稳定。

## 业务场景

- 本助手管国内、巴西、海外三个域的制程问题单，约 3,000 张。治理任务把每张单的问题描述、原因分析、改善措施剥净格式后按字段分段，落进 mart 的分段表（约 1 万段），再由声明式向量化生成向量。
- 用户常问「最近一年有没有涉及非接的问题」「音频相关的问题有哪些」，期望得到**完整清单**。做法是按业务方维护的同义词表（「非接」= NFC、非接触……）在剥净的文字上按词找，再用语义检索补上说法不同的单。
- 按词找有两类噪音，必须逐张判断才能去掉：
  - **只是提到**：「NFC、打印、显示测试均正常」「排除非接问题」，文字里出现了词，但这张单的问题不是它。
  - **说法有歧义**：「射频」「RF」在终端产品里也可能指 4G、WiFi 模块。
- 一个概念常命中上百张单。在查询时逐张调本地大模型判断，要几分钟，而且同一张单两次判断可能给出不同结论，用户看到的计数会变。
- 更合适的做法是**入库时判断一次**：治理任务对每段文字判断「涉及同义词表里的哪些概念、是真涉及还是只是提到」，把结果存成分段表的标签列；查询时按标签筛选，结果完整、计数确定、响应快。词表或文字变了，只重判变化的段。业界称这种做法为入库时用大模型富化元数据。

## SDK 当前行为

- `JobContext` 的字段只有 `module_code`、`embedder`、`etl`、`config`、`on_progress`（文末输出 [2]）。它的文档字符串明确写了「这里没有 Settings，是故意的」：平台不把配置整袋交给任务，任务需要什么句柄由平台注入。
- `handle()` 的 `ModuleContext` 有 `llm`（输出 [1]）；重排模型只在 `ctx.retrieval.search()` 内部使用，模块拿不到单独的重排句柄，两种上下文里都没有。
- 所以治理任务里没有任何合规途径调用大模型或重排模型。

## 期望

**方案 1（倾向）：`JobContext` 注入 `llm` 与 `reranker`**

- `llm`：与 `handle()` 的 `ctx.llm` 同一个客户端、同一套平台配置；平台策略里与「回答用户」有关的部分（如数字红线的前置提示）在任务里可不加。
- `reranker`：平台已有的 `RerankClient`，返回每条候选的分数（`rerank(query, documents, top_n=) -> [(下标, 分数)]`）。如果平台同时实现「查询侧任务说明」那份反馈里的说明参数，这里也一并支持。
- 未配置对应服务时为 `None`，与 `embedder` 一致；任务自己处理降级。
- 审计：任务里的调用照常记录模块编码与任务名，不涉及用户。

**方案 2：只注入 `reranker`**

本助手的判断本质是「这段文字是否满足这个概念」的是 / 否判断，Qwen3-Reranker 本身就是按这个方式训练的（按「是」的概率打分），比大模型便宜。只注入重排句柄也能满足需求，代价是阈值要靠评测集调。

## 影响范围

- 任何要在入库时做分类、抽取、摘要的模块都需要这项能力；没有它，这些工作只能挪到每次提问时做，延迟与稳定性都受影响。
- 只是新增可选字段，现有任务不受影响。

## 业务仓的临时做法（平台实现前）

- 强词命中直接计入；「只是提到」用确定的规则标注（提示词表，如「正常」「排除」），排到清单后面，不删除。
- 只对弱词命中与语义检索补充的单，在查询时调 `ctx.llm` 判断，每次最多约 30 张，其余标「未逐张判断」并计数。
- 平台实现后，把判断挪到治理任务，在分段表加标签列，查询改为按标签筛选。

## 复现

不连任何服务。在装有 `paxsz-forge-core` 0.3.6、`paxsz-forge-data` 0.3.1 的环境执行：

```python
"""复现：handle() 的 ModuleContext 有 llm，治理任务的 JobContext 没有 llm 与重排句柄（不连任何服务）。"""

from importlib.metadata import version

from forge_core.jobs import JobContext
from forge_core.module import ModuleContext

for pkg in ("paxsz-forge-core", "paxsz-forge-data"):
    print(f"{pkg} {version(pkg)}")

print("\n[1] ModuleContext（handle() 里的 ctx）字段:", list(ModuleContext.model_fields))
print("[2] JobContext（治理任务里的 ctx）字段:", list(JobContext.model_fields))

job_fields = set(JobContext.model_fields)
print("\n[3] JobContext 有 llm 吗:", "llm" in job_fields)
print("    JobContext 有重排句柄吗:", any(k in job_fields for k in ("reranker", "rerank", "retrieval")))
```
