## 一句话

本助手要在三个域（国内、巴西、海外）的制程问题单上按文字找单：按词找，也按意思找相近的单。为此要一个 PostgreSQL 产物库，存剥净后的叙述文字、分段和向量。请平台运维建库并登记别名，权限平台把其中 9 张表按域授权，DBA 确认正式库的两项元数据。

## 业务场景

- 本助手只读查询三个域的制程问题单，结构化取数直连 INFO（别名 `info`）和 ERP（别名 `erp`）的只读副本，不经产物库。
- 用户常问「有没有涉及非接的问题」「以前有没有出现过开机花屏，当时怎么处理的」。答这类问题要在问题描述、原因分析、改善措施等叙述文字里找。原文是 HTML，还内嵌 base64 图片（三域叙述文字合计约 1.15 亿字符，98% 是图片），直接在源库上按词匹配会大量误命中，也没法按意思找。
- 所以由本模块的治理任务定时把叙述文字剥净、分段，写进产物库；平台按本模块的向量化声明生成向量表并回填。产物库只当文字索引用，单上的状态、责任人等事实仍实时回源查。
- 域权限只有表级（每个域的主表允许或拒绝），所以产物库按域分表，没有任何权限承载列。

## 产物库里有什么

| 表（每域一套，`<域>` 为 `domestic`、`brazil`、`overseas`） | 谁建 | 内容 | 预计行数（三域合计） |
|---|---|---|---|
| `<域>_issue_text` | 本模块治理任务首轮跑时建 | 一单一行，剥净的叙述文字与指纹 | 约 2,700 |
| `<域>_issue_seg` | 同上 | 一段一行，按词找用 | 不超过约 1.1 万 |
| `<域>_issue_vseg` | 同上 | 一段一行，向量化的来源 | 不超过约 1 万 |
| `<域>_issue_vec` | 平台装配时由 `forge vectorize apply` 建（DDL 见附录） | 向量（1024 维），平台回填 | 不超过约 1 万 |

整个库预计在 100 MB 量级。

## 请做的事（测试、正式两套环境各做一遍）

### 平台运维

1. **确认 `config/data_sources.json` 已登记 `info`、`erp`**，并告知两件事：
   - 测试环境的 `info` 指向 INFO 开发库，还是正式库的副本。这决定我们在测试环境上的验收结果能代表什么。
   - `info` 连接默认进哪个库。建议设为 `CoreINFO`：INFO 实例上 `info` 库的兼容级别是 100，`CoreINFO` 是 150；以 `info` 为当前库时 `TRY_CONVERT`、`STRING_SPLIT` 不可用（开发库实测）。本助手的表名都写成三段，换默认库不影响取数。不便调整也不阻塞，告诉我们即可，本模块会避开这两个函数。
2. **建库并登记别名**：

   ```bash
   uv run forge data provision-mart --module FACTORY_ISSUE --host <PG主机> --vector --apply --write-config
   ```

   - 建出 `forge_mart_factory_issue` 库、一对专属账号（只读取数账号与写账号），装 pgvector，并写回 `data_sources.json` 的 `forge_mart_factory_issue` 别名。
   - 请确认 pgvector ≥ 0.8.0，并配好写账号（`write_user` / `write_password_env`）：建向量表、治理任务建表和落数都走它，缺了会 fail-closed。
   - 请确认只读取数账号能看到写账号建的表（默认权限授予了写账号建的对象）。看不到时平台启动期会报向量表不存在。
3. **确认 embedding 与 rerank 服务已配置**：`FORGE_EMBEDDING_BASE_URL`（向量维度 1024）与 `FORGE_RERANKER_BASE_URL`。本模块排序与初筛依赖重排分，缺 rerank 能跑但效果差。
4. **jobs worker 的环境**：本模块的治理任务要读 INFO 的叙述文字，所以 jobs worker 上要有 `info` 别名的口令，以及产物库的写账号口令。

### 权限平台

5. 在本助手（`FACTORY_ISSUE`）的权限里加 9 张表，放最外层，写法同其他最外层表（显式写不限行、不屏蔽列：`"row": {"mode": "DENY", "logic": "OR", "rules": []}`、`"column": {"mode": "DENY", "rules": []}`），随所属域给「允许」：

   | 表（四段名） | 何时给「允许」 |
   |---|---|
   | `mart.forge_mart_factory_issue.public.domestic_issue_text`、`domestic_issue_seg`、`domestic_issue_vec` | 申请了国内 |
   | `mart.forge_mart_factory_issue.public.brazil_issue_text`、`brazil_issue_seg`、`brazil_issue_vec` | 申请了巴西 |
   | `mart.forge_mart_factory_issue.public.overseas_issue_text`、`overseas_issue_seg`、`overseas_issue_vec` | 申请了海外 |

   - 实例段我们建议写 `mart`。平台匹配时只看库、架构、表名，实例段不能为空；如有统一约定，请告诉我们，以约定为准。
   - 三张 `<域>_issue_vseg` 只由后台任务读写，本助手不读，不用列。
   - 本助手的权限默认效果是「拒绝」。漏列一张时，按词找会被拒；按意思找不报错，只是什么都找不到。本助手每轮开头会检查，这种情况回答「暂不可用」，但请配置时逐张核对。

### DBA

6. 请书面确认正式库（INFO 实例）的三项，与开发库一致即可：
   - SQL Server 版本 ≥ 2016（开发库是 2019）。治理任务用 `HASHBYTES` 给超过 8000 字节的长文本算指纹，需要 2016 及以上。
   - `CoreINFO`、`info` 两个库的兼容级别（开发库分别是 150、100）。
   - 两张全公司大表的索引：`info.dbo.tbTask` 上有 `frecID` 单列索引，以及（`ftable`, `fstat`）INCLUDE `frecID` 的复合索引；`info.dbo.DocumentList` 上有 `ID` 聚集主键，以及（`frecid`, `BusinessType`）复合索引。本助手按单直连这两张表，靠这些索引。
   - 这一项不挡建库，但要在首轮跑数之前有。

### 定时任务与对 INFO 只读副本的压力

| 任务 | cron | 对 INFO 的读取 |
|---|---|---|
| `FACTORY_ISSUE.sync_issue_text` | `*/30 * * * *` | 每轮在 INFO 上按单算一次文字指纹（三张主表与子表的叙述列，约 3,000 张单），只返回「单 ID + 指纹」；再只拉指纹变了的单的全文 |

## 预期会看到、不用处理的现象

- `forge vectorize ddl` 打出的「权限承载列」一行是「（无）」。本模块的产物库不需要权限承载列，`field_mappings` 不给这个别名填映射，平台启动期的权限承载列校验对它整体跳过。开发者文档 `docs/dev/11` 阶段 1 的自检说那行为空就是没配对，与 `07`、`04` 的说法相反，另有一份反馈「mart 别名不配 `field_mappings` 时，`11` 的向量化自检会把正常配置说成『没配对』」。
- 装配后、首轮跑数前：文字表与两张段表还不存在（治理任务首轮跑时才建），按词找会报表不存在；向量表已建但为空，按意思找什么都找不到。属正常中间态，首轮跑数后消失。平台启动不会因此被拒。

## 附录：三张向量表的 DDL

本模块的向量化声明（三域同形，以国内为例）：

```python
VectorizeSpec(source="forge_mart_factory_issue", vector_table="domestic_issue_vec",
              origin_table="domestic_issue_vseg", id_column="seg_id",
              text_columns=["seg_text"], default_cron="10,40 * * * *",
              metadata_columns=["issue_id", "field"])
```

本仓 2026-10-26 在 `paxsz-forge-core` 0.3.7 / `paxsz-forge-data` 0.3.2 上，用 `forge vectorize ddl` / `apply` 共用的生成函数（`forge_data.etl.declarative.vector_table_ddl`，`field_mappings` 为空）打印出的 DDL，不连库：

```sql
-- domestic_issue_vseg -> domestic_issue_vec；权限承载列：（无）
CREATE TABLE IF NOT EXISTS domestic_issue_vec (
    id text PRIMARY KEY,
    content text NOT NULL DEFAULT '',
    embedding vector(1024) NOT NULL,
    metadata jsonb NOT NULL DEFAULT '{}'::jsonb,
    issue_id text,
    field text,
    content_hash text
);
CREATE INDEX IF NOT EXISTS domestic_issue_vec_embedding_hnsw ON domestic_issue_vec USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX IF NOT EXISTS domestic_issue_vec_issue_id_idx ON domestic_issue_vec (issue_id);
CREATE INDEX IF NOT EXISTS domestic_issue_vec_field_idx ON domestic_issue_vec (field);
```

`brazil_issue_vec`、`overseas_issue_vec` 只是表名与索引名前缀不同。`issue_id`、`field` 两列来自 `metadata_columns`，检索时按单限定、按单去重、按字段过滤都靠它们。DDL 是 `IF NOT EXISTS`，建成后再改声明不会补列，所以这两列在第一次建表前就已定死。
