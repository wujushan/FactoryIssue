# 2026-11-10 AI 润色技术设计（G4a）评审

> 评审对象：决策 2026-11-09「AI 润色技术设计」（`docs/decisions/2026-11-09-AI润色技术设计.md`，草稿待评审）。
> 评审依据：`docs/1_user_input/domestic/国内制程问题_填单内容AI润色需求.md`、决策 2026-11-09「AI 润色任务接口设计」（已定稿）、决策 2026-11-09「AI 润色放在本助手」、`2_landed/domestic/ai_polish.md`、`2_landed/domestic/ai_polish_api.md`、现有 `src/factory_issue_module/` 代码、`scripts/polish_spike/` 实测工具、已装 paxsz-forge-core 0.3.9 / paxsz-forge-platform 0.3.9 / paxsz-forge-data 0.3.2 源码。
> 结论按严重程度分三级：🔴 需修改、🟡 建议改进、🟢 小问题 / 文档一致性。

## 总体评价

整体质量很高：接口设计定稿清晰、`2_landed` 口径完整、实测数据扎实（r1/r2 两轮、81 次一次通过）、包结构合理、对查询助手的改动面控制得很好（仅四处）。以下按严重程度分级列出需要改进的地方。

## 🔴 需要修改（设计缺口或自相矛盾）

### 1. §4 模型调用与心跳进度事件不可兼得（最重要）

§4 表格写的是：

> `asyncio.wait_for(llm.chat(messages, …), timeout=CALL_TIMEOUT)`；等待期间每 `HEARTBEAT` 秒发一个同样的 `progress`

`asyncio.wait_for` 是对一个 `await` 的包装——生成器阻塞在那一个 `await` 上，**无法在等待期间 `yield` 进度事件**。平台停止机制是在「事件之间」检查 `stop_status`（`forge_platform/gateway/pipeline.py` 的 `_stop_requested()`），如果模型调用期间没有事件产出，停止要等到模型返回或 `turn_max_seconds`（900 秒）才会生效；反代读超时（R1 待确认项）也保不住。

需要改成「任务 + 周期等待 + 交替 yield」的模式，大致是：

```python
task = asyncio.create_task(llm.chat(messages, **kwargs))
try:
    deadline = loop.time() + CALL_TIMEOUT
    while True:
        remaining = deadline - loop.time()
        if remaining <= 0:
            task.cancel()
            raise asyncio.TimeoutError
        done, _ = await asyncio.wait({task}, timeout=min(HEARTBEAT, remaining))
        if done:
            return task.result()
        yield Event.progress("polish", "正在润色")
except asyncio.CancelledError:
    task.cancel()
    raise
```

这个模式同时解决三个问题：SSE 保活（每 10 秒有事件）、停止响应（10 秒内收住）、超时控制（`deadline` 到点取消任务）。§4 的伪代码和 §1.1 的流程图都要改成这个形状，§12.1 的单测「超时（把 `CALL_TIMEOUT`、`HEARTBEAT` 调小，同时核对心跳的进度事件）」也依赖这个模式。

### 2. `POLISH_PROMPT_VERSION` 的值写错了

§8.1 写 `POLISH_PROMPT_VERSION = "r1"`，但同节紧接着说「以上是 `r2`（2026-11-10 按 r1 实测改…）」，spike 代码里（`scripts/polish_spike/polish_core.py`）也是 `PROMPT_VERSION = "r2"`。设计稿的常量值应改为 `"r2"`，否则 G4b 照抄会写错。

### 3. `max_length` 取 `min(页面值, 栏目默认)` 与接口口径矛盾

§5 写「`max_length` 与栏目默认取较小的一个：页面给的是这一栏真正的存储上限，栏目默认只是没给时的兜底」。但接口设计 §4.2 和 `ai_polish_api.md` 的口径是「页面应当传；**没传时**用配置里这一栏的默认值」——默认值是**兜底**，不是**上界**。

场景：`measures` 的栏目默认是 2000（取自库列宽），但页面实际列宽 3000 并正确传了 `max_length=3000`。取 `min` 后有效上限是 2000，润色结果被不必要地压缩；用户把结果粘回编辑器后发现字数远没到列宽上限，体验是「润色把我的内容砍了」。

建议：页面传了就用页面的，没传才用栏目默认（`raw_max or fld.default_max`）。如果担心页面传错（比如传了个 999999），可以另设一个硬上限（如 `MAX_RESULT_CEILING`），但不要拿「库列宽默认值」当上界。spike 代码的 `min(limits)`（`polish_core.py` `parse_request`）也要同步改。

### 4. §13.3 对话框引导语的插入位置描述与代码实际顺序不符

§13.3 说引导语插在「判空之后、判『三域都无权』之前」。但看 `orchestrator.run_turn` 的实际顺序（`turn/orchestrator.py:125-140`）：

```
gate.resolve → access is None → 判空 → access.none（三域都无权）→ 读历史/规划…
```

`access is None`（「没拿到权限」，答 `ACCESS_UNAVAILABLE`）的分支在判空**之前**就 return 了。所以「判空之后、判三域都无权之前」这个描述与实际代码顺序对不上：`access is None` 分支已经先行返回，引导语实际只能插在 `access is None` 分支**之后**、判空之前（或判空之后、`access.none` 之前，两者都在 `access is None` 之后）。

交互本身没问题（润色不查域权限，G105 已定；对所有有本助手使用权的人引导语都成立），但 §13.3 的插入位置描述要改成「`gate.resolve` 之后、判空之前」（即 `access is None` 分支之后），与代码实际顺序对齐，避免 G4b 照文字描述插错位置。

## 🟡 建议改进（不影响正确性，但值得在 G4b 前明确）

### 5. §7.2 5Why 子表排序列 `AddDate`/`ID` 未进 `select`，需确认列级权限

§7.2 写 5Why 子表取 `Question`、`Reason`、`Status`，`order_by` 提问时间（`AddDate`）、ID。`AddDate` 和 `ID` 都不在 `select` 里。核对 paxsz-forge-core 0.3.9 的 `QuerySpec` 编译：`order_by` 引用非 `select` 列是合法的（`GroupByIncomplete` 只查分组查询；非分组查询的 `order_by` 列只过列级白名单，不过投影完备性）。**但前提是 `AddDate` 和 `ID` 在列级权限白名单内**。国内 5Why 子表（`ZCTracking_ProblemFiveWhy`）的列级权限如果只开放了 `Question`/`Reason`/`Status`，`order_by` 引用 `AddDate`/`ID` 会抛 `ColumnNotPermitted`。

建议：要么把 `AddDate`、`ID` 也放进 `select`（单张单的 5Why 行数很少，多取两列无妨），要么在 §7.2 明确「`AddDate`/`ID` 需已在列级授权内，否则 5Why 排序失败按取数出错处理」。前者更稳。

### 6. §9 第 5 项长度检查的比例门槛（一半到两倍）对分条场景可能过严

§9 第 5 项：「正文字数在原文的一半到两倍之间（原文不足 50 字时上限放宽为原文加 20 字）」。当原文是一段 200 字的连续叙述、模型按提示「内容较多时分条」把它拆成 5 条带序号的短句时，总字数可能从 200 变成 150（去掉了「首先」「其次」之类的连接词，换成「1. 2. 3.」），比例 0.75 还在范围内。但如果原文是 80 字的短段落、模型分条后变成 40 字（每条只保留核心），比例 0.5 刚好卡线。

r2 实测 81 次全部通过，说明当前样例集没撞上这个边界。但 D53 业务试用用真实单据时，短原文 + 分条的组合可能出现。建议：在 §12.3 的「检查漏了的」观察项里加一条「分条后字数比是否触碰 0.5 下界」，业务试用时留意；如果确实过严，把下界从 0.5 放宽到 0.4（配置化或代码常量都行）。

### 7. §6.2 `K` 的「段落标记的估计长度」对纯文字栏的口径缺失

§6.2 的公式：`段落标记的估计长度 = 7（"<p></p>"）×（原文段落数 + 2）`。这个公式只对富文本栏成立（拼回后每段包 `<p></p>`）。纯文字栏拼回是 `"\n".join(lines)`，段落标记是 1 字符的 `\n`，不是 7 字符的 `<p></p>`。

spike 代码已经处理了（`polish_core.py` `budget()`：`if split.rich: … else: overhead = split.paragraphs`），但设计文档 §6.2 的公式没有区分两种格式，G4b 照设计写会出错。建议 §6.2 补一句：「纯文字栏的段落标记估计长度 = 1 ×（原文段落数），因为拼回用单个换行连接」。

### 8. §8.2 参考内容为空时的行为宜明确

§8.2 说「没有字数上限、没有额外要求、没有参考内容时，对应那一段不写」。如果参考内容为空（没传 `context`、没传 `issue_no`），`【同一张单的其他内容】` 这一整段（标题 + JSON）都不写——这没问题，system 第 6 条已经说了「只用来让这一栏与其他栏前后一致」，没有就不一致。

但有一个边界：`field` 为 `five_why_answer` 时，`context.current_question` 是**必传**的（§5 校验），所以参考内容至少会有「这一答对应的问」一项，不会是空。其他栏目可能真的没有参考内容。这个行为是正确的，不需要改，但建议在 §8.2 明确一句：「`five_why_answer` 的参考内容恒非空（至少含 `current_question`），其他栏目可能为空」。

### 9. §12.2 回归断言 `answer_preserves` 对富文本栏的匹配口径

§12.2 说新断言 `answer_preserves`（结果里必须原样出现的串：数字、型号、图片地址、表格原文）。但富文本栏的结果是拼回后的 HTML（`<p>…</p>` 包裹、`html.escape` 过的文字），`answer_preserves` 里如果放的是纯文字串（如 `A999`），在 HTML 结果里是 `A999`（字母数字不会被 escape），可以直接匹配。但如果放的是含 `&` 的文字（如 `A&B`），结果里是 `A&amp;B`，直接匹配会失败。

样例集（`docs/testcases/polish/cases.json`）里 `answer_preserves` 的值都是数字、字母、URL、HTML 片段，没有 `&`，所以当前不会踩到。但建议在 `qa_test.py` 的断言实现里明确：对富文本栏，`answer_preserves` 的串在**拼回后的 HTML 全文**里做子串匹配（不做 HTML 解析），并在文档里注明「断言串不要包含 `&`、`<`、`>` 等会被 escape 的字符，除非你要断言的就是 escape 后的形态」。

### 10. §14 日志 `input_chars` 的定义与 §6.1 判长的口径应统一

§14 说 `input_chars`（去掉占位后的文字数），§6.1 判长用的是「`text` 去掉占位标记后的字数」。spike 代码里 `text_chars` 是「去掉占位标记与**空白**后的字数」（`re.sub(r"\s+", "", strip_marks(text))`）。判长和日志的 `input_chars` 应该用同一个口径（去空白），否则日志里的 `input_chars` 和判长用的字数对不上，排查时 confusing。建议 §14 明确 `input_chars` = 去掉占位标记与空白后的字符数（同 `text_chars`）。

## 🟢 小问题 / 文档一致性

### 11. §8.1 `POLISH_PROMPT_VERSION` 常量名与 spike 代码不一致

设计写 `POLISH_PROMPT_VERSION`，spike 代码（`polish_core.py`）写 `PROMPT_VERSION`。G4b 移进 `src` 时用哪个名字？建议设计稿统一为 `POLISH_PROMPT_VERSION`（带模块前缀，避免与查询助手的其他版本常量混淆），spike 在 P6 改 import 时同步改。

### 12. §1.2 包结构里 `polish/` 依赖 `plan.schema.parse_reply`

§1.2 说 `polish/` 不 import `plan`（`plan.schema.parse_reply` 除外）。但 `parse_reply` 是查询助手规划器的 JSON 解析工具（去 `
`、取第一个 `{` 到最后一个 `}``），它本身与规划无关，放在 `plan/schema.py` 里只是因为历史原因。建议 G4b 时把 `parse_reply` 提到一个更通用的位置（如 `textnorm.py` 或新建 `text/json_parse.py`），让 `polish/` 的依赖声明干净一些。不改也能跑，但 `polish/` 依赖 `plan/` 的例外会一直在。

### 13. §2.1 `ext_param_schema` 里 `five_why` 的 `items` 没有 `required`

`five_why` 的 `items` 是 `{"type": "object", "properties": {"question": …, "answer": …}}`，没有 `"required": ["question", "answer"]`。§5 说「某项不是 `{question, answer}`」时丢掉那一项，所以 schema 不标 required 是合理的（schema 只作文档）。但 Console 展示时，管理员可能以为 `question`/`answer` 是可选的。建议 `description` 里补一句「每项须含 `question` 与 `answer`（待答复的 `answer` 为空串）」。

### 14. §6.3 结果例里 `<img src="https://…"/>` 的自闭合写法

设计 §6.3 的结果例：`<p>2. 永久措施：如图<img src="https://…"/>更换夹具。</p>`。TinyMCE 的 `setContent` 能处理 `<img …/>` 自闭合，但原始 `<img>` 标签在拆的时候是「整个 `<img …>` 标签」原样保留（§6.1），拼回时也是原样放回。如果原文是 `<img src="…">`（无 `/`），拼回后也是 `<img src="…">`（无 `/`），设计例子里的 `/` 只是示意。不影响实现，但例子里最好与「原样放回」的口径一致，避免 INFO 前端对着例子做格式比对。

### 15. §16 R3 状态措辞

R3 状态列写「2026-11-10 已回填：3000 字、110 秒、系数不变；截断长度与比例门槛按初值，实测里没有因它们不过的，保持不变」。严格说这不是「回填」（回填 = 用实测数据改了初值），而是「实测验证了初值合理，不改」。建议措辞改为「3000 字、110 秒、系数不变为实测回填；截断长度与比例门槛经实测验证无需调整，维持初值」。不影响实现，只是表述精确性。

### 16. 接口设计 §2 约束表里「`require_privileges=True` 只在取数时检查」的引用

接口设计 §2 写「`require_privileges=True` 只在取数时检查（`forge_data` 的 `ScopedDataAccess`），不取数的分支不受影响」。核对 paxsz-forge-data 0.3.2 的源码：`require_privileges` 的检查在 `_resolve_table_scope()` 里，由 `fetch()`/`query()`/`raw()`/`row_scope_sql()` 触发，`describe()` **也会**触发（`describe` 调 `_resolve_table_scope`）。所以「只在取数时检查」的表述不够精确——`describe()` 也检查。

对本设计的影响：§0 说润色分支「不判域（不调 `describe()`）」，所以不会触发 `require_privileges` 检查，润色本身确实不受影响。但如果将来有人想在润色分支里调 `describe()`（比如做权限预检），会踩到 `PrivilegesRequiredError`。建议接口设计 §2 的表述改为「`require_privileges=True` 在 `fetch`/`query`/`raw`/`describe` 时检查，不取数也不调 `describe()` 的分支不受影响」，与源码一致。

## 汇总

| 级别 | 数量 | 关键项 |
|---|---|---|
| 🔴 需修改 | 4 | 模型调用与心跳不可兼得（§4）、`PROMPT_VERSION` 值错（§8.1）、`max_length` 取 min 矛盾（§5）、§13.3 插入位置描述 |
| 🟡 建议 | 6 | 5Why 排序列权限（§7.2）、长度比例门槛（§9.5）、纯文字栏 K 公式（§6.2）、参考内容为空的说明（§8.2）、`answer_preserves` 匹配口径（§12.2）、日志 `input_chars` 口径（§14） |

第 1 项（模型调用模式）是唯一的架构级缺口，必须在 G4b 前改设计；第 3 项（`max_length` 取 min）是业务逻辑错误，会影响用户看到的结果质量；其余都是文档精确性或防御性改进。
