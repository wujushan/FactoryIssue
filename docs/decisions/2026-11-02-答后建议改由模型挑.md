# 2026-11-02 答后建议改由模型挑

## 背景

开发者 2026-11-02 在 INFO 网页端实测：

1. 问「ZC2604012 的详情」，答后推荐「ZC2604012 的完整处理过程」「ZC2604012 的原因与措施」，点了前一个。
2. 答后推荐「ZC2604012 的原因与措施」，点了它。
3. 答后又推荐「ZC2604012 的完整处理过程」：第 1 轮推荐过、第 2 轮问过。

原因在规则本身（设计 §9.5 原先的写法）：

- 只看本轮问了哪几项：没看处理过程就推处理过程，没看原因就推原因与措施；问过的、推荐过的都不记。会话历史剥掉了按钮数据块，模型也看不到推荐过什么。
- 候选太少：单张单详情后永远只有这两个，与单上有什么（CAR、驳回、机型、供应商）无关，两轮就用完，只能来回推。
- 不看对话往哪个方向走，措辞每次一样。

开发者要的是不机械、紧贴对话、不重复、有意义。

## 结论（开发者 2026-11-02 定）

1. **代码出候选，模型挑与写，代码核对**：
   - 候选不按场景写模板，改为对本轮实际执行的计划套几种「走一步」：下钻、换角度、收窄、换时间、比较、换域、导出、看另一面、上卷、找类似、下一张。参数取自计划格式与本轮沙箱产物，不另取数，所以规划器能做的事都覆盖得到，以后加了可看项、维度动作照样用得上。
   - 模型读最近几轮对话、本轮回答的开头与候选，挑至多 3 条、写问句；同一个底的两条可以合成一条（「只看惠州百富的，按问题类型统计」）。模型只能用候选，不能另出候选之外的问题。
   - 代码逐条核对：问句必须写出改动的那个取值（单号、机型、工厂、维度名、时间说法），里面的数与单号要在这条候选里出现过，不露表名字段名，不与问过推荐过的相同。不合格的丢掉。
   - 模型出错、超时（5 秒）、关掉时按代码的默认顺序取；模型挑了 0 条时不给接着问，不凑数。
   - 纠偏类按钮（其他理解、按上月同期比、改按结案时间算、放宽时间、文字查找那几个）照旧由代码直出，排在前面，不交模型：这些问句是代码要认的。
2. **不重复的范围**：同一会话里问过的、推荐过的都不再推。意图键按计划算（单号、条件、分组），与用户怎么说无关；换了单、换了条件不算重复。推荐过没点的也不再推。
3. **看过整张详情后不推「原因与措施」**：整张详情已在各环节里给了原因分析与改善措施。例外：单上有 CAR 报告内容时照推（详情里只给了 CAR 编号）。「完整处理过程」是全部操作记录，详情里没有，照推。
4. **每个取数轮多一次模型调用**：在最后一步算完、还没发它的事件时就开始，与正文分段发出重叠；按钮可能比正文晚一点出来。点了接着问按钮的那一轮不调规划，直接执行存下的计划，大致抵掉多出的这一次。
5. **点了之后直接执行存下的计划**：问句由模型写、措辞自由，点了也不会被规划器理解错。用户自己打字时照常规划。

管理员可在模块配置 `answer_params.toml` 关掉模型（`suggest_model = false`，按代码的默认顺序）、改等待秒数（`suggest_seconds`，1–30，默认 5）。
