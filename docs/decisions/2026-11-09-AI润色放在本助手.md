# 2026-11-09 AI 润色放在本助手

## 背景

业务方提出：在 INFO 管理页面的国内制程问题单上，给问题描述、原因分析、5WHY分析过程、改善措施、预防对策五栏加【AI润色】按钮，初步规划在本助手内扩展，供 INFO 前端经平台的业务任务接口 `POST /v2/tasks` 调用。开发者先要求评估放在本助手是否合适。

平台只按助手授权，不按任务授权：用户要能调用本助手的任务，就得有本助手的使用权；有了使用权，也就能在对话框里查制程问题（查到什么仍按他的数据权限）。

## 比较

| | 放在本助手 | 另起一个润色助手 |
|---|---|---|
| 权限 | 能用润色与能用查询绑在一起 | 可以只给填单人开通润色 |
| 起步工作量 | manifest 声明任务，`handle()` 开头加分支 | 新建业务仓、平台装配、INFO 登记 |
| 发版 | 改润色也要整包发版、跑查询回归；本助手装不起来时润色一起不可用 | 各发各的 |
| 业务说法 | 直接复用 `2_landed` 的术语与各栏含义 | 复制一份，日后两边不一致 |
| 日后参考历史单的原因与措施 | 本助手已有按意思找，内部扩展 | 要跨助手调用本助手 |
| 推广到其他单据 | 每加一种都改查询助手 | 适合做成通用填单助手 |

决定性的一条是权限：会用润色的人若有不宜开通查询助手的（如外部加工厂人员），就该另起助手，或请平台做按任务授权。日后要拆出去，INFO 页面只需改 `target` 一个常量，任务码与参数可以不变，现在的选择可逆。

## 结论

开发者 2026-11-09 确认：会用国内制程问题 AI 润色的人员，就是开通了国内制程问题权限的人员，都是内部人员，开通本助手没有问题（关闭 G103）。据此**放在本助手内实现**。

实现上的约束（G4a 设计时细化）：

- 润色是 `handle()` 开头按 `ext_param.task` 分出的独立分支，不进查询编排；与查询共用的只有业务说法（术语表、各栏含义）。
- 默认 `data_scope="user"`，不声明 `system`。

## 补记：开发者答复与 D43 的接口核实（同日）

开发者 2026-11-09 答复：D42、D45、D49、G105 同意建议；D43 暂定同意，要求核实平台接口能否把提示与正文分开返回；D44 暂定同意，要点业务方后续补充，并要求各栏的要点与提示词能灵活组合、可配置，哪些可配置另列 D50；D47 问能否只给单号、由本助手去查同单其他栏，改写为「两种都支持」的建议待确认。D48、G104 未答。

**D43 核实**（对照 `docs/dev/02`「任务面」与 paxsz-forge-core 0.3.9 的事件类型）：`/v2/tasks` 与 `/v2/chat` 是同一套 SSE 事件，即 delta、tool_call、tool_result_meta、table、chart、citation、progress、clarify、suggestions、error、end，没有专门承载「结构化结果」的事件。可选的载体：

| 载体 | 怎么放 | 问题 |
|---|---|---|
| `delta` 正文后接分隔标记 | 润色正文后接一段提示 | 页面要按文字标记切开，模型漏写或改写标记就切错，正文不能保证直接替换 |
| `delta` 整段 JSON | 正文与提示放进一个 JSON | 没有逐字显示；模型生成的 JSON 可能不合法 |
| `suggestions` | 每条提示一个按钮 | 语义不符：按钮点了就把 `query` 当新一轮发出去，提示不是能发送的问题 |
| `table` | 单列表格，标题固定，每行一条提示 | 用表格装列表，语义稍弱；回读任务会话历史时它会以 Markdown 表格出现在正文里 |

结论：润色正文走 `delta`（逐字流式，拼起来即可直接替换原文），提示走一个单列 `table`，标题与列名定为常量写进 INFO 对接说明；页面按事件类型分开取，不靠文字切分。现有协议即可满足，不需要平台改动。「任务面缺少结构化结果事件」可作为改进建议向平台提出，不阻塞本需求。

**已改**：`2_landed/domestic/ai_polish.md` 补「改到什么程度」「还可以补充的提示」「各栏的写法要点」「图片、表格和格式」「原文为空或很短」；`2_landed/privileges.md`「国内填单内容润色」补「润色前不另查国内域权限」；`open-questions.md` 关闭 D42–D45、D49、G105，改写 D47，新增 D50。
