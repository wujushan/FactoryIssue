## 结论先行

1. **结构化取数直连 `info` / `erp`，不治理。** 32 张原始表的筛选、关联、统计、展示都直接查只读副本，脏数据按 `2_landed/dirty_data.md` 在查询期处理。
2. **文字查找建 `forge_mart_factory_issue`，启用 `governance-etl` + `semantic-retrieval`。** mart 只当文字索引，回答「哪些单的文字命中 / 相近」；单上的事实一律回源取，展示、统计、条件筛选都不读 mart。
3. **每域 4 张表，共 12 张，不设权限承载列**：文字表、分段表（按词找）、按意思找的段表（向量化来源）、向量表（平台生成），见「产物设计」。域权限只有表级，按域分表后由权限平台逐表授权；`field_mappings` 不给 mart 别名填映射。
4. **向量按段，不按单**：一单按字段分段，长字段再按段落切。理由是检索粒度：用户常用很短的说法找单（「非接」「音频」），这件事可能只是整单里的一句，整单一个向量会被其余内容稀释。分段规则放 `ctx.config`，不发版即可切换，用评测定（见「检索评测」）。预设的问题现象和剥净后不超过 10 个字的内容不进向量，靠另落一张表做到（见「按意思找的段表」）。
5. **「涉及某个话题」走按词与按意思两路，合成一张清单**（决策 2026-10-22「涉及某个话题的找法与呈现」）：按词一路给前两组，完整、计数确定；按意思一路与有歧义的说法只补第三组「可能相关」，经判断后最多 10 张。按哪些说法找、怎么分组，见总述「涉及某个话题怎么找」。不做「只是提到」标注：按提示词就近标注会把「更换喇叭后测试正常」这类修好的真问题标错。
6. **CAR 报告文字、附件、PN 不进 mart。**
7. **从 profiles 移除 `analysis-report`**：本助手不调用其他模块，用不到它的多步编排与 `ctx.bus`。
8. **同步不依赖数据量，也不依赖修改时间**：每轮在源库按单算文字指纹，只拉指纹变了的单；每天凌晨全量重建兜底（见「同步策略」）。
9. **叙述原文按需回源**：清单、汇总不取叙述原文，按文字找单只读 mart，单张详情才回源取原文并剔除内嵌图片（见「叙述原文的取数」）。

### 为什么结构化部分不治理

- 量小：三张主表合计 3,019 行，子表最多 1.8 万行，单次查询拉回的明细在平台行数上限与沙箱承受范围内。
- 脏数据都是确定规则（按段拆分、文本转日期、JSON 展平、剥内嵌图片），查询期在沙箱里处理即可，不需要预先落一份。
- 两张大表只按单关联取很少几行，取法都有可用索引（F6）。

### 为什么文字部分必须进 mart

- **类似问题要按意思找**，只能靠向量。`VectorizeSpec` 的来源表与向量表须在同一个 mart 库里，原始表在 SQL Server 上，所以先由治理任务把文字落进 mart。
- **向量化前的文字要加工**：剥标签、实体与内嵌图片，展平两种现象 JSON，巴西只取最新一条处理过程，分段，挑出参与按意思找的段。声明式向量化只做「单表 + 列拼接」，这些是治理任务的活。
- **按词找必须在剥净的文字上做**：原文是 HTML（F1：三域问题描述全部带标签），关键词会误命中标签、实体与外链图片地址；含内嵌图片的行在原文上按 usb、lcd、pcb、nfc 匹配几乎全部命中，去掉图片后基本归零（F2）。在源库原文上匹配还要把动辄几百万字的值整段拉回来复核。剥净的文字反正要落进 mart，按词找直接在上面做。

### 为什么按段向量化、为什么要两路

把「非接找不到」拆开看，有四个原因，分段只解决其中一个：

| 原因 | 说明 | 对策 |
|---|---|---|
| 稀释 | 一单一个向量时，只占一句的现象被其余内容冲淡，相关单排不进向量召回的前列 | 按字段分段，长字段再切（结论 4） |
| 术语缺口 | 「非接」是行业简称，模型未必把它与 NFC、非接触、射频、感应等放在一起；与文档长短无关 | 管理员维护的说法清单 + 按词一路（结论 5） |
| 短问句缺任务说明 | Qwen3 的两个模型都要求查询侧带任务说明；平台现在原样发问句，模块也没法只给向量化一侧加 | 平台反馈「语义检索查询侧缺少任务说明」；实现前用扩写弥补 |
| 问法要完整清单 | 「有没有涉及 X」「X 相关问题」用户期望看到全部，语义检索只给最相近的若干张 | 按词一路给完整的前两组 |

不切到句子级，因为另有两点降低了稀释的影响：

- 重排把问句与段落放在一起读，一句话里提到的内容它判断得准；稀释主要伤「进不进向量召回前列」这一步。切得太碎，重排只看到片段，丢上下文，「一句顺带提到」的误命中反而增加。
- 带条件检索时，候选段数不超过召回条数，每段都直接进重排，与向量相似度高低无关。

### 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 不建 mart：关键词搜索在源库上模糊匹配 + 沙箱复核；类似问题由模型把现象扩写成一组关键词再搜 | 类似问题退化成关键词搜索，做不到「按意思相近」；源库匹配受标签、图片干扰 |
| 三域合进一套表，按「所属域」列过滤 | 域权限只有表级，同表内无法按域授权；只能取回后再按域筛，等于模块自己做权限过滤，违反「权限经平台取数前阻断」 |
| 一单一个向量（整单拼成一段） | 见上表「稀释」。保留为评测里的对照组（分段规则 `whole`），不作默认 |
| 每个叙述字段各建一张向量表 | 约 35 张向量表，权限平台要逐张授权。每段带字段代号，检索时按字段过滤即可，不必分表 |
| 向量化整张分段表，检索时再过滤掉不该按意思找的段 | 每次检索都要带过滤，漏带一次，预设现象就静默混进结果。巴西、海外的标准现象与手填现象同为 `phen`，要另加标记列，且须在第一次建向量表前写进 `metadata_columns`。处理步骤一段里长短条目混在一起，按行过滤去不掉其中的短条目 |
| 分段表加一列向量用文字，不该按意思找的段置空 | 平台回填只挑内容非空、且未嵌过或内容哈希变了的行，回填结束时只删来源表里已不存在的段的向量（本仓 2026-10-26 打印 data 0.3.2 生成的回填 SQL 核对）。一段嵌过之后改到不超过 10 个字，编号不变、内容为空，回填跳过它、清理也不删它，旧内容的向量照样能被找到 |
| 等平台给 `VectorizeSpec` 加行过滤 | `VectorizeSpec` 只有来源表、主键、拼哪几列，没有行过滤；平台文档对这条表达力边界的说法是「声明表达不了的，加一步治理 ETL，不加声明字段」。另落一张表已能做到 |

## 产物设计

### 文字表 `<域>_issue_text`（一单一行，只含未删除的单）

| 列 | 内容 |
|---|---|
| `issue_id` | 源主表主键，转文字；主键 |
| `issue_no` | 问题编号（仅便于排查，回答不从这里取） |
| 各叙述字段列 | 每个叙述字段一列，剥净后**归一化**（小写、全角转半角、连续空白压成一个空格），供按词找比对范围以外的字段与处理步骤的某一列。国内另有问题现象列：已选现象与可能原因表 → 问题现象表的现象文字，按现象去重后用「；」连接 |
| 子表汇总列 | 国内 / 海外处理步骤的结论、意见、内容（措施列；每个环节只取最新一条），巴西处理过程各叙述列、费用备注：按记录先后拼成一段，每列一段，同样归一化 |
| 巴西最新处理过程两列 | 最新一条（ID 最大）处理过程的原因分析、改善措施 |
| `text_fingerprint` | 源库算出的本单文字指纹，增量同步时比较用（见「同步策略」） |
| `synced_at` | 本行同步时间 |

### 分段表 `<域>_issue_seg`（一段一行，按词找用）

| 列 | 内容 |
|---|---|
| `seg_id` | 段编号，主键：`<issue_id>:<字段代号>:<序号>`，如 `2811:desc:0` |
| `issue_id` | 所属单 |
| `field` | 字段代号：`phen`（问题现象，三域；国内为建单时选的现象）、`desc`（问题描述）、`reason`（原因分析）、`measure`（改善措施）、`improve`（改善建议）、`prev`（预防对策）、`sqe`（SQE 跟进结果，巴西）、`step`（整理后的处理步骤，国内、海外） |
| `seq` | 字段内序号，从 0 起 |
| `seg_text` | 段落文字，剥净但**不做大小写归一**，开头带字段名（如「问题描述：…」），供清单摘要与命中处的上下文 |
| `seg_norm` | 同一段文字的归一化版本（同文字表，不带字段名前缀），供按词匹配 |

- 收总述「比对范围」内的全部栏目，含预设的问题现象、剥净后不超过 10 个字的字段值与处理步骤条目：它们不参与按意思找，按词找照常比对（决策 2026-10-26「预设问题现象不参与按意思找」）。比对范围以外的叙述字段只进文字表。
- 每个字段一段，不按长度切：按词找只需知道命中在哪一栏，上下文按命中位置截取。分段规则不作用于这张表，所以评测切到 `whole` 也不会让分组失效。
- 不向量化。

### 按意思找的段表 `<域>_issue_vseg`（一段一行，向量化的来源）

| 列 | 内容 |
|---|---|
| `seg_id` | 段编号，主键，格式同分段表。两张表各自编号，同一个编号不一定是同一段文字；按词、按意思两路的结果按单（`issue_id`）合并，不按段编号对应 |
| `issue_id` | 所属单（`metadata_columns`） |
| `field` | 字段代号，同分段表（`metadata_columns`） |
| `seq` | 字段内序号，从 0 起 |
| `seg_text` | 段落文字，剥净但不做大小写归一，开头带字段名，供向量化 |

- 只收参与按意思找的内容（总述「比对范围」）：国内问题现象不收（含建单时手填的「其他」现象，本助手不区分）；巴西、海外现象只收手填的（现象数组里编号小于 0 的元素，含补充说明，按各域展平规则）；剥净后不超过 10 个字的字段值不收，手填现象同样适用；处理步骤去掉不超过 10 个字的条目后再整理（见「整理规则」）。
- 按分段规则切段，一段一个向量。为什么另落一张表，见「备选方案」后三行。
- 段怎么消失：单被删除、某个字段改到不超过 10 个字、分段规则改了，治理任务都把对应的段从这张表删掉，平台回填结束时随之删掉对应向量。
- 本助手不经 `ctx.data` 读这张表（按词找读分段表，按意思找读向量表）。它只由治理任务写、由平台向量化任务读（系统级，不经权限过滤），所以不写进 `manifest.data_sources[].tables`，也不进权限清单。

### 整理规则（文字表与两张段表共用）

- 字段代号决定命中归「涉及某个话题」的哪一组：`phen`、`desc`、`reason`（巴西为最新一条处理过程的原因分析）归第一组「问题本身涉及」；`improve`、`measure`、`prev`、`sqe`、`step` 归第二组「处理中提到」。按词命中看分段表的 `field`，按意思命中看 `h.metadata["field"]`。分组规则随分段规则放 `ctx.config`，内置默认值即此。
- 处理步骤由治理任务整理成每单一个 `step` 字段：
  - 每个环节只取最新一条（国内按 `Step`、海外按 `StepStr` 分环节，取 ID 最大的一条），只取分析类环节的意见与内容（措施列；工厂制程分析另取结论）。怎么认环节、纳入哪些环节，见总述「比对范围」。
  - 环节清单放 `ctx.config`（与分段规则同一份配置，内置默认值 = 总述的国内编码清单、海外名称清单）；清单外的环节不纳入，治理任务每轮在统计行里报出。
  - 每条前带环节名称；同单内完全相同的条目只留一条。进分段表每条都留，进按意思找的段表去掉剥净后不超过 10 个字的条目。
  - 不做「与主表重复」的去重：E4 显示 1.65 万条里只有 24 条与主表相同或被包含，不值得维护去重规则。
  - 内容列是系统拼的「操作人姓名 + 这一步的结果与所填各项」（见各域处理步骤表「内容」）：清洗时去掉人名前缀，内容包含意见时只留内容，具体写法 G4a 用平台测试环境的样本定。责任人确认这一步的内容会把主表原因分析、改善措施、预防对策再写一遍，是否在比对与「原因与措施」里去重，G4a 定。
- 分段规则从 `ctx.config` 读（文件名与格式 G4a 定），只作用于按意思找的段表；读不到或写错时用默认值：
  - `whole`：整单比对文字拼成一段（评测对照组）；
  - `field`：每个字段一段；
  - `field_split`（默认）：每个字段一段，剥净后超过约 500 字的按段落切成约 300–500 字的段，相邻段重叠一句。
  - 规则改了要跑一次全量重建（`rebuild_issue_text`）；段编号会变，平台回填删掉旧段的向量。
- 估算规模（正式镜像 F3、E1、E2，按 `field_split`）：三域合计约 1.1 万段，其中国内约 9,000（问题描述 2,474、原因分析 468、改善措施 881、改善建议约 1,100、预防对策约 500、处理步骤约 2,000–2,500、问题现象约 966，另有少量长字段切段）、巴西约 1,000、海外不到 100。
  - 分段表：每字段一段、不切，不超过约 1.1 万段。
  - 按意思找的段表，即回填规模：去掉国内约 966 段问题现象、巴西与海外的标准现象和短值，不超过约 1 万段，分钟级回填。探测没有单独数过短值，精确段数看上线首轮统计行。
- 清洗按 `2_landed/dirty_data.md`「富文本」：剥净内嵌图片、全部标签与实体，只留文字；现象 JSON 按各域主表文件的展平规则。
- 只含未删除的单（国内是否删除为 0 或空；巴西状态不为 -1；海外是否删除为 0），与管理页面一样查不到已删除的单（决策 2026-10-22「按编号查单」）。三域删除标记都没有空值，国内、海外只有 0 和 1（探测 U1，2026-10-26），这几种写法与「不为 1」「空按 0」结果相同。单被删除后，治理任务把它从文字表与两张段表删掉，平台回填随之删掉对应向量；查询结果仍以回源为准。
- 建表语句写在治理任务开头（`CREATE TABLE IF NOT EXISTS`）。本助手要读的 9 张表（三域各文字表、分段表、向量表）写进 `manifest.data_sources[].tables`：向量表靠它出现在 `ctx.data.describe()` 里，供域闸门判断；以后若加权限承载列，启动期校验只查这里声明的表。

### 向量表 `<域>_issue_vec`（平台生成）

```python
VectorizeSpec(source="forge_mart_factory_issue", vector_table="domestic_issue_vec",
              origin_table="domestic_issue_vseg", id_column="seg_id",
              text_columns=["seg_text"], default_cron="10,40 * * * *",
              metadata_columns=["issue_id", "field"])
# brazil_issue_vec / overseas_issue_vec 同形，origin_table 分别为 brazil_issue_vseg / overseas_issue_vseg
```

- 来源是按意思找的段表，进不进向量全由治理任务往这张表写什么决定（平台怎么挑行，见「备选方案」）。
- 向量行 `id` 是段编号，不是单号。`issue_id`、`field` 是 `metadata_columns`，平台把它们抄进向量表（text 列 + btree 索引），按单限定（`restrict_column="issue_id"`）、按单去重（`group_by="issue_id"`）、按字段找（`filters={"field": [...]}`）都靠它们，命中从 `h.metadata["issue_id"]` 取单。
- 版本：需 `paxsz-forge-core ≥ 0.3.7`、`paxsz-forge-data ≥ 0.3.2`、`paxsz-forge-platform ≥ 0.3.7`，本仓 `pyproject.toml` 下界已是这些版本；低于它们时 `metadata_columns` 被静默丢弃，检索参数即 `TypeError`。`metadata_columns` 不能用 `id_column`（`seg_id`）与平台保留名 `id`、`content`、`embedding`、`metadata`、`content_hash`。
- **必须在建向量表前声明**：向量表 DDL 是 `IF NOT EXISTS`，建成后再加 `metadata_columns` 不会补列，平台拒绝启动，只能手工 `ALTER TABLE` 并重跑回填。所以 `metadata_columns` 随本稿一起评审、一起申请建库。文字表与两张段表由治理任务自己建，不受这条限制。来源表以后要换时，段编号与文字不变则内容哈希不变、不会重嵌，新来源表里没有的段由平台清理，向量表结构不用动。

### 查询期怎么用（G4a 细化）

业务规则以 `2_landed` 为准，本节不重写：问法怎么分（关键词搜索、涉及某个话题、类似问题、点名字段）、按哪些说法找、怎么分组与呈现，见总述「关键词搜索与类似问题」整节；说法怎么匹配、不算的说法怎么屏蔽，见 `topic_terms.md`「怎么读」。本节只写每一步读哪张表、用哪些检索参数，与总述冲突时以总述为准。下面按「涉及某个话题」写；关键词搜索、点名字段按词找用其中的 ②，类似问题用 ③。

**配置**（`ctx.config`，读不到或写错时用内置默认值）：

- 说法清单按话题组织：每个话题有一句说明（给重排与判断用）、算的说法（有歧义的加 ＊）、不算的说法；内置默认值 = `2_landed/topic_terms.md`。
- 维护的业务侧流程见 `topic_terms.md`「上线后怎么维护」，以下由 G4a 落实：
  - 槽位：`manifest.config_files` 声明一个文件（文件名与格式 G4a 定），`description` 写清是「涉及某个话题」的说法清单；平台只存不解析，管理员在 Console「模块配置」页上传、预览、回滚。
  - 没上传时 `ctx.config.text()` 为 `None`，用代码内置的清单；单元测试比对内置清单与 `topic_terms.md`，防两边漂移。
  - `validate_config()` 只做快速检查、不读库（它在网关进程同步执行、没有超时保护）：能解析；每个话题有说明和至少一个算的说法；中文说法至少 2 个字；同一话题内不重复、不同时算又不算；＊ 写法正确。
  - 解析结果按 `ctx.config.version()` 缓存。
  - 只在提问时用，改了下一轮生效，不触发重建或重嵌；分段规则是另一份配置，改了才要全量重建。
  - 每轮用的配置版本进审计归档 `configs.json`、测试通道 `trace.configs`，G3 / G5 用例的结果受它影响时据此核对。
  - 发版前把 Console 当前版本回写 `topic_terms.md` 与内置默认值，在 `docs/decisions/` 记一句。
  - 怎么让管理员看到常用的临时说法（如在审计日志里检索），G4a 定。

**流程**：

- **① 定说法**：先把问句消解成自足的说法（多轮里「那上个月呢」不能直接拿去检索）。再按总述「按哪些说法找」判断用户说的是话题本身、比话题小的说法，还是清单外的组合说法，从说法清单取对应的说法；清单里没有时由模型临时提说法。这一步不读库；模型只挑说法，不改清单。
- **② 按词一路**（结果完整、计数确定）：
  - 比对范围内的栏目在本域分段表的 `seg_norm` 上逐段匹配；用户点名比对范围以外的字段时，改在文字表的该列上匹配（这些字段没有向量，不参与 ④ 的重排）。
  - 实现匹配与屏蔽时注意三点：纯英文缩写的前后边界不用数据库正则的词边界（它把汉字也当作词的一部分，「刷卡NFC失效」会匹配不上）；纯英文缩写不在去掉空格的文字上匹配（「use NFC card」去掉空格后 NFC 前后都是字母）；屏蔽不算的说法时，先把出现处换成去空格时不会被删掉的占位，再去空格做包含匹配，免得屏蔽处两侧粘成新说法。
  - 有附加条件时，经 `ctx.data` 在原始表上取候选单的主表 ID，只在这些单的段里匹配。
  - 分组看命中段的 `field`，按单去重、由数据库计数（N1、N2；2026-10-28 补记改为沙箱计数）。带 ＊ 的说法只在第一组栏目里命中、且该单不在前两组的，作 ④⑤ 的候选。
- **③ 按意思一路**：
  - 只检索本域向量表，来源表里本就没有预设现象与短值，检索时不用再过滤。
  - 问句是 ① 定下的话题说明，或用户原话消解后的一句现象描述；不把说法串拼进去（有研究发现，把查询扩写直接交给神经重排模型，效果可能下降）。
  - 有附加条件时，经 `ctx.data` 取候选单的主表 ID，传 `restrict_ids=候选单, restrict_column="issue_id"`，不展开成段编号；限定时平台走精确近邻，候选内召回完整。没有条件时直接检索。
  - 只在某些字段里找时加 `filters={"field": [...]}`：点名比对范围内的字段只给该字段（总述「点名字段时怎么找」）；问做法只给 `improve`、`measure`、`prev`、`sqe`、`step`（总述「按问法分工」）。`filters` 与 `restrict_ids`、行级权限都是 AND，只收窄。
  - 候选上限 5,000 按单数算，三域未删除单最多是国内的 2,474 张，正常撞不上。仍接住 `RetrievalRestrictTooLarge`：改用不限定检索、加大 `top_k`、取回后按候选单过滤，并说明结果不保证完整。
  - 按单去重用 `group_by="issue_id"`，同一单只占一个结果位，`top_n` 数的是单数。带候选时结果精确；不带候选时平台近邻多取 4 倍再折叠，只能尽量凑满 10 张。
  - 三域都查时各域分别做 ①–⑤，按域分组呈现（总述「跨域规则」）。`rerank_score` 同一问句下跨表可比，需要跨域比较时按它比、为 `None` 时退回 `score`；不因此改成跨域混排。
- **④ 第三组的候选排序**：前两组不重排。第三组的候选单 = ③ 找到的单 + ② 里带 ＊ 说法在第一组栏目命中的单，去掉已在前两组的单。以这些单再检索一次（`restrict_ids=候选单, restrict_column="issue_id", group_by="issue_id"`，`top_k` 设成候选单的段数、`top_n` 设成候选单数，问句同 ③）：平台对候选单的段逐段精确比对、重排后每单留最相关的一段，带回 `rerank_score`（2026-10-28 补记改正：平台是先按向量距离每单留一段、再重排）。候选超过上限（约 500 段，放配置）时只取 ③ 的结果重排（2026-10-28 补记改为按单数设上限）。② 来的候选单在按意思找的段表里没有段时（例如带 ＊ 的说法只命中国内的预设现象），再检索拿不到它，就带着按词命中处的上下文直接进 ⑤，排在有重排分的候选之后。
- **⑤ 第三组的判断**：先按 `rerank_score` 初筛，低于阈值的不交模型、视为不相关（阈值放配置，由检索评测定；评测前不启用，`rerank_score` 为 `None` 时也不筛）。再按 ④ 的顺序把剩下的候选交给模型判断「X 是不是这张单的问题现象或原因」，最多约 30 张（放配置）；判断为相关的列入第三组，最多 10 张。判断为不相关、来不及判断的不列出，也不对用户计数。每张候选带命中处前后约 80 字的上下文，供判断与展示。
- **⑥ 呈现**：三组怎么列、怎么排、回答开头给什么、哪些组请用户看命中的文字，见总述「涉及某个话题怎么找」与「统计口径说明」的「文字查找」。数据侧要备好：每行的命中方式（命中了哪个说法、在哪一栏，或按意思相近）和上下文（同 ⑤）；本次用了哪些说法；N1、N2 由数据库计数（2026-10-28 补记改为沙箱计数），S 由执行器按标签计数，模型不报数。清单上百张时按呈现规范导出全量。之后回源取展示字段。
- **⑦ 后续演进**：
  - 入库时打标签：治理任务给每段标「涉及哪些话题」，查询变成结构化筛选，完整、确定、更快，第三组也能给全。前提是平台在治理任务里提供大模型或重排句柄（平台前置第 7 项）；实现后只需在分段表加标签列。
  - 评测显示重排分可靠时，⑤ 可改为只按分数阈值判断，不再受约 30 张的上限约束，不改库表。
- **域闸门**：每轮开头用 `ctx.data.describe()` 同时看三张主表与本域要读的三张 mart 表（文字表、分段表、向量表）。主表有权而 mart 表无权（权限平台漏配）时，该域的文字查找明说「暂不可用」，不说成「没有找到」；其余查询照常。

## 叙述原文的取数（G4a 细化）

叙述列里有内嵌图片，单个值最长约 4,845 万字（见「涉及数据与数据量」）。结构化取数只要把这些列带进 `select`，一次查询就可能拉回几十 MB，而有用的文字不到 1%。所以：

- **清单、汇总、统计不取叙述原文**，只取标识、枚举、数量、日期这类列；清单要展示描述摘要时，从分段表取剥净后的文字（时效同按文字找单）。
- **按文字找单只读 mart**，不在源库原文上匹配（F2）。
- **单张单的详情回源取原文**，在沙箱里剔除内嵌图片后再展示或交给模型；一次只取一张单，最坏约 48 MB。G4a 要核对平台取数行数上限之外的两道限制：沙箱数据帧通道的单次上限、单轮预算。超限时改从 mart 取一份去图、保留格式的展示副本（文字表加列，治理任务顺带生成），详情的叙述文字随之晚约半小时。业务方同意约半小时时效（G22）的前提是单上内容实时查，所以 G4a 若确需改走副本，须另向业务方确认。
- **治理任务读原文时按单分批**：含图的长值集中在少数单上，一批读太多单会一次拉回上亿字。只有指纹变了的单才拉全文（见「同步策略」）。

## 检索评测（决定分段规则与两路的取舍）

分段该多细、扩写帮多大忙，靠推理定不了，要在真实数据上比较。

- **评测集**（G3 准备）：一组主题问句（如非接、音频、花屏、通信、USB / 打印、按键失灵），每句配上应该命中的单，三域都要有，单号从正式数据取。做法：内网用本地大模型把全部未删除的单标一遍话题，与说法清单按词的结果对照，业务方只抽查分歧与少量一致的单；人工判定过的单才进评测集与 golden，模型标签只用来找分歧、估准确率（工具 `scripts/topic_labeling/`，探测 T4 已判的单作标尺）。
- **对比组**：分段规则 `whole` / `field` / `field_split` × 扩写与否；平台支持查询侧任务说明后再加一组。
- **指标**：
  - 按意思一路：前 10、前 50 的命中率；带窄条件（某机型、某工厂）的命中率。
  - 按词一路：按话题、按每个说法统计准确率与召回率。误命中多的说法改加 ＊ 或挪到不算的说法，只改配置。
  - 分组与模型判断：第一组里有多少其实只是处理中提到、第二组里有多少其实是问题本身；第三组判断相关与否对不对。
  - 重排分阈值（⑤ 初筛）：在第三组候选上看 `rerank_score` 与业务方判断的对应，定一个几乎不误删相关单的阈值；被阈值筛掉的并入下条的漏判抽样。
  - **漏判抽样**（借鉴电子取证审查）：从「第二组」「判断为不相关」「未逐张判断」三堆里各随机抽一批请业务方核对，估计每堆里还有多少其实是问题本身涉及或相关；比例偏高就调分组字段、说法清单或判断上限。G5 验收前做一次，上线后清单大改时再做。
  - 两路合并后的漏检与误命中。
- **在哪跑**：平台测试环境（有 embedding 与重排服务、能连库）。切换分段规则只改配置，跑一次全量重建与回填，分钟级。
- **怎么用结果**：默认 `field_split`；评测显示 `field` 不差时改用 `field`（段更少、上下文更完整）；`whole` 明显更好时也可切回。结果记入本决策的后续记录。

| `brazil_issue_text` / `_seg` / `_vseg` / `_vec` | 无（域权限 = 表级） | — | 是：只含巴西单 |
| `overseas_issue_text` / `_seg` / `_vseg` / `_vec` | 无（域权限 = 表级） | — | 是：只含海外单 |

- 域权限怎么落到 mart：权限平台把本助手要读的 9 张 mart 表列进本助手的权限，随所属域给「允许」，写法同其他最外层表（显式写不限行、不屏蔽列）；按意思找的段表本助手不读，不列。默认拒绝下漏列一张时，按词或分段取数抛表级拒绝，向量检索静默返回 0 条，所以靠「域闸门」每轮检查。
- mart 别名不填 `field_mappings` 时，平台向量表、治理后表两道启动期权限列校验都跳过，不会因没有权限承载列拒绝启动；`forge vectorize ddl` 的「权限承载列」一行为「（无）」是预期（本仓 2026-10-26 不连库核对 core 0.3.7 / data 0.3.2 / platform 0.3.7）。`docs/dev/11` 阶段 1 的自检说那行为空就是没配对，与 `07`、`04` 相反；按 `04` 与实际行为办，不为过这条自检去填映射（平台前置第 8 项）。没有行级规则，也就没有 HNSW 后过滤召回塌陷。
- **以后若要按部门或个人限制**（`privileges.md`「权限级别」里的「A + 行级规则」），规则引用的列必须先加进全部 12 张 mart 表（按意思找的段表也要带上，平台回填从它把列透传进向量表），属破坏性变更：改建表语句 → 重建表 → 全量重跑治理与向量化。改权限口径前先改本决策。

## 受列级管控字段的处置

本助手没有列级规则。需要单独处理的是 **CAR 报告**：它单独授权（表级），有国内权限不等于能看报告内容。

- [x] 不向量化该字段：CAR 报告各段文字不进 mart 的任何一张表。物料问题单上的 CAR 编号是问题单字段，不是叙述文字，也不进 mart。
- [ ] 按敏感度分表把列级降维成行级：不适用。

## 同步策略

| 任务 | 做什么 | cron（G22，业务方 2026-10-22 同意） |
|---|---|---|
| `FACTORY_ISSUE.sync_issue_text`（治理任务，业务仓写） | 按指纹增量同步文字表与两张段表，见下 | `*/30 * * * *` |
| `FACTORY_ISSUE.rebuild_issue_text`（治理任务，业务仓写） | 全量重建文字表与两张段表，兜底指纹漏判；改分段规则后手动跑一次 | `30 2 * * *` |
| `FACTORY_ISSUE.vectorize:<域>_issue_vec`（平台生成，3 个） | 只重嵌内容有变化的段，删掉已不存在的段（平台按内容哈希判断） | `10,40 * * * *`（错开治理任务 10 分钟） |

**按指纹增量**（不依赖数据量，也不依赖主表修改时间是否随流转更新；海外主表本来就没有修改时间）：

1. 在源库里算每张单的文字指纹：主表各叙述列与子表叙述列一起参与（子表按单汇总），用 `HASHBYTES` 在库里算完，只把「单 ID + 指纹」拉回来，几千行、每行几十字节，内嵌图片不出库。
2. 与 mart 里上次保存的指纹比较，只对新增和指纹变了的单拉全文、清洗、写入文字表，并在两张段表里删掉该单的旧段、写入新段；源上已不存在或已删除的单从这三张表删掉（指纹比较只拿未删除的单）。
3. 指纹存进文字表，下轮比较用。分段规则不进指纹，改规则靠全量重建。
4. 凌晨全量重建一次，指纹有漏判（如某个子表叙述列没纳入）时最多影响一天。

`HASHBYTES` 对超过 8000 字节的文本需要 SQL Server 2016 及以上（F7 确认开发库，正式库待 DBA 告知）；正式库低于 2016 时退回每轮全量重建，cron 按上线首轮核对的耗时再定。治理任务里调 `ctx.progress(...)` 上报进度；上线首轮的跑法见「平台 / 运维侧前置」第 4 项。

### 上线首轮核对（正式环境）

开发库代表不了正式环境的数据量与压力，以下几项在正式环境首轮跑数时由治理任务自报，业务仓据此复核，不需要任何人连正式库：

- 治理任务每轮结束输出一行统计（只含计数与耗时，不含文字）：每域单数、拉全文的单数、分段表段数、按意思找的段数、清洗前后字符数合计、含内嵌图片的单数、比对文字全空的单数、没有按意思找的段的单数、各步骤耗时。走任务执行记录与日志，平台 Console 任务页可见。
- 复核规则：增量一轮超过 1 分钟或全量重建超过 10 分钟，拉长 cron 或与平台运维商量低峰时段；比对文字全空的单占比明显时，在「类似问题」的说明里写明这些单按文字找不到；没有按意思找的段的单占比明显时，按决策 2026-10-26「预设问题现象不参与按意思找」的「风险」一节处理。
- 大表取数：G5 在平台测试环境验收时看取数日志里待办任务、文档清单查询的耗时，单次超过 2 秒即回到「两张大表能否直连」一项处理。平台测试环境连的是开发库还是正式库副本，先向平台确认（平台前置第 1 项），否则 G5 的耗时同样代表不了正式环境。

## 结论

- `manifest.data_sources` 别名：`info`（INFO 实例）、`erp`（ERP 实例）、`forge_mart_factory_issue`（mart，`tables` 列本助手要读的 9 张：三域各文字表、分段表、向量表）。

- profiles：`structured-query`、`stats-sandbox`、`governance-etl`、`semantic-retrieval`；移除 `analysis-report`。
- `manifest.vectorize`：3 条，每域一张向量表，读本域按意思找的段表；`id_column="seg_id"`、`text_columns=["seg_text"]`、`metadata_columns=["issue_id", "field"]`、cron `10,40 * * * *`。
- 权限承载列：无，mart 别名不填 `field_mappings`。
- `manifest.config_files`：分段规则（含各字段归哪一组、处理步骤环节清单）、说法清单（内置默认值 = `2_landed/topic_terms.md`）；判断上限、重排上限与重排分阈值可并入其中一份（重排上限按单数计，见文末补记）。文件名与格式 G4a 定。

## 补记（2026-10-28，G4a 设计与其独立评审之后）

模块技术设计（决策 2026-10-27「模块技术设计」§7.2）细化了本决策的两处，独立评审（`docs/reviews/2026-10-28-G4a模块技术设计独立评审.md` I5）又指出一处对平台行为的误读。三处都不动向量表、按意思找的段表与已申请的建库。

1. **分段表加一列 `seg_compact`**（`seg_norm` 去掉全部空白），只作按词找的 SQL 预筛。中文说法按业务规则忽略空格匹配，在 `seg_norm` 上预筛会漏掉「非 接触」这类写法。分段表由治理任务自建，首轮建表前加列没有代价。
2. **N1、N2 改由沙箱计数**，不由数据库计数。屏蔽不算的说法、纯英文缩写的前后边界写不进取数条件，只能取回候选段后在沙箱里判；沙箱与 SQL 同属确定性执行器。
3. **改正「查询期怎么用」④**：带 `group_by="issue_id"` 检索时，平台在 SQL 里按向量距离每单只留最近的一段，然后才重排（`forge_data` 0.3.2 `retrieval/index.py`、`retrieval/pipeline.py`）；`top_k`、`top_n` 数的都是单数。所以 ④ 不能做到「逐段重排后每单留最相关的一段」。改为：`top_k`、`top_n` 都设成候选单数，但不超过一个按单数计的上限（起点 100 张，放配置），不再数候选单的段数，也没有「超过约 500 段」那个分支；超过上限时按向量距离只留最近的这些单。上限仍要有：重排是一次请求把全部候选交过去，候选多时可能超时，平台退回向量顺序、`rerank_score` 为空，第三组的排序就悄悄变成了纯向量顺序（同一评审稿「复评」R8）。⑤ 交给模型判断的上下文是「向量最近的那一段」。要逐段重排，得去掉 `group_by`、在 500 段以内取回各段的重排分、在沙箱里每单取最高的一段；是否值得，看检索评测。
