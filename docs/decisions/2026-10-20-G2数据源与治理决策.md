## 结论先行

1. **结构化取数直连 `info` / `erp`，不治理。** 29 张原始表的筛选、关联、统计、展示都直接查只读副本；脏数据（文本日期、逗号多值、JSON、富文本展示）按 `2_landed/dirty_data.md` 在查询期处理。
2. **文字查找建 `forge_mart_factory_issue`，启用 `governance-etl` + `semantic-retrieval`。** mart 只当「文字索引」：存剥净后的叙述文字、分段与向量，用来回答「哪些单的文字命中 / 相近」；**单上的事实一律回源取**（展示、统计、条件筛选都不读 mart）。
3. **每域 3 张表，共 9 张**：文字表（一单一行，供关键词匹配）、分段表（一段一行，供向量化）、向量表（平台生成）。域权限在本助手里只有表级，按域分表后由权限平台逐表授权；**不设权限承载列**，`field_mappings` 不给 mart 别名填映射。
4. **向量按段，不按单**：一单按字段分段（问题描述 / 现象、原因分析、改善措施各一段），单个字段过长再按段落切。理由是检索粒度而不是长度上限：用户常用很短的说法找单（「非接」「音频」），这件事可能只是整单里的一句，整单压成一个向量会被其余内容稀释。分段规则放 `ctx.config`，可以不发版切换，用评测定（见「检索评测」）。
5. **「涉及某现象」的问法走关键词与语义两路**：先把用户的说法扩成一组同义说法（模型扩写 + 术语表 + 同义词配置），在文字表上做关键词匹配（完整），同时在分段向量上做语义检索（补上换了说法的单），合并、重排、逐张判断相关性。呈现方式待业务方确认（G24）。
6. **CAR 报告文字、附件、PN 不进 mart。**
7. **`analysis-report` 建议从 profiles 移除**：本助手不调用其他模块，用不到它的多步编排与 `ctx.bus`。
8. **同步不依赖数据量，也不依赖修改时间**：每轮在源库里给每张单的文字算指纹，只拉指纹变了的单的全文；每天凌晨全量重建一次兜底（见「同步策略」）。

9. **叙述原文按需回源**：清单、汇总不取叙述原文，按文字找单只读 mart，单张详情才回源取原文并剔除内嵌图片（正式数据里单个叙述值最长约 4,845 万字，见「叙述原文的取数」）。

画像已确认：富文本与内嵌图片普遍，清洗必要；三域文字都是中文；每张单都有比对文字（正式镜像库 F1–F5）；两张大表的取法都有索引，直连（开发库 F6）。`info` 库兼容级别只有 100：指纹与平台分页不受影响，只是以它为当前库时 `TRY_CONVERT`、`STRING_SPLIT` 不可用（F8），属 G4a 的写法约束，不影响本决策的取舍。

### 为什么结构化部分不治理

- 量小：三张主表合计 2,974 行，子表最多 1.8 万行，单次查询拉回来的明细在平台行数上限与沙箱承受范围内。
- 脏数据都是确定规则（按段拆分、文本转日期、JSON 展平、剥内嵌图片），查询期在沙箱里处理即可，不需要预先落一份。
- 两张大表只按单关联取很少几行，前提是有可用索引，由 F6 确认。

### 为什么文字部分必须进 mart

- **类似问题要按意思找**，只能靠向量。平台的声明式向量化只读与向量表**同一个库**里的表（`VectorizeSpec` 的 `origin_table` 与 `vector_table` 同在 `source` 库），原始表在 SQL Server 上，所以必须先由治理任务把文字落进 mart。
- **向量化前的文字要加工**：剥标签、实体与内嵌图片，展平两种现象 JSON，巴西只取最新一条处理过程，再分段。这超出了声明式向量化「单表 + 列拼接」的表达力，正好是治理任务的活。
- **关键词搜索必须在剥净的文字上做**：原文是 HTML（F1：三域问题描述全部带标签），关键词会误命中标签、实体与外链图片地址；更严重的是内嵌图片——F2 显示，含内嵌图片的行在原文上按 usb、lcd、pcb、nfc 匹配几乎全部命中，去掉图片后基本归零。在源库原文上匹配还要把这些动辄几百万字的值整段拉回来复核。剥净后的文字反正要为向量化落进 mart，关键词搜索直接在上面做。

### 为什么按段向量化、为什么要两路

把「非接找不到」拆开看，有四个原因，分段只解决其中一个：

| 原因 | 说明 | 对策 |
|---|---|---|
| 稀释 | 一单一个向量时，只占一句的现象被其余内容冲淡，相关单排不进向量召回的前列 | 按字段分段，长字段再切（结论 4） |
| 术语缺口 | 「非接」是行业简称，模型未必把它与 NFC、非接触、射频、感应等放在一起；与文档长短无关 | 扩写同义说法 + 关键词一路（结论 5） |
| 短问句缺任务说明 | Qwen3 的两个模型都要求查询侧带任务说明；平台现在原样发问句，模块也没法只给向量化一侧加 | 平台反馈「语义检索查询侧缺少任务说明」；实现前用扩写弥补 |
| 问法要完整清单 | 「有没有涉及 X」「X 相关问题」用户期望看到全部，语义检索只给最相近的若干张 | 关键词一路保证完整（G24） |

另有两点降低了稀释的影响，所以不切到句子级：

- 重排是把问句与段落放在一起读的，一句话里提到的内容它判断得准；稀释主要伤的是「进不进向量召回前列」这一步。切得太碎，重排只看到片段，丢上下文，「一句顺带提到」的误命中反而增加。
- 带条件检索时，候选段数不超过召回条数，每段都直接进重排，向量相似度高低无关。

### 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 不建 mart：关键词搜索在源库上模糊匹配 + 沙箱复核；类似问题由模型把现象扩写成一组关键词再搜 | 类似问题退化成关键词搜索，做不到「按意思相近」；源库匹配受标签、图片干扰 |
| 三域合进一套表，按「所属域」列过滤 | 域权限只有表级，同表内无法按域授权；只能取回后再按域筛，等于模块自己做权限过滤，违反「权限经平台取数前阻断」 |
| 一单一个向量（整单拼成一段） | 见上表「稀释」。保留为评测里的对照组（分段规则 `whole`），不作默认 |
| 每个叙述字段各建一张向量表 | 约 35 张向量表，权限平台要逐张授权。分段表里每段带字段标记，限定检索时只取某个字段的段即可达到同样效果，不必分表 |

## 产物设计

### 文字表 `<域>_issue_text`（一单一行，含已删除的单）

| 列 | 内容 |
|---|---|
| `issue_id` | 源主表主键，转文字；主键 |
| `issue_no` | 问题编号（仅便于排查，回答不从这里取） |
| `deleted` | 是否已删除（国内是否删除为 1；巴西状态 -1；海外是否删除不为 0） |
| 各叙述字段列 | 每个叙述字段一列，剥净后**归一化**（小写、全角转半角、连续空白压成一个空格），专供关键词匹配 |
| 子表汇总列 | 国内 / 海外处理步骤的结论、意见、措施，巴西处理过程各叙述列、费用备注：按记录先后拼成一段，每列一段，同样归一化 |
| 巴西最新处理过程两列 | 最新一条（ID 最大）处理过程的原因分析、改善措施 |
| `text_fingerprint` | 源库算出的本单文字指纹，增量同步时比较用（见「同步策略」） |
| `synced_at` | 本行同步时间 |

### 分段表 `<域>_issue_seg`（一段一行，向量化的来源）

| 列 | 内容 |
|---|---|
| `seg_id` | 段编号，主键：`<issue_id>:<字段代号>:<序号>`，如 `2811:desc:0` |
| `issue_id` | 所属单 |
| `field` | 字段代号：`phen`（现象，巴西、海外）、`desc`（问题描述）、`reason`（原因分析）、`measure`（改善措施） |
| `seq` | 字段内序号，从 0 起 |
| `seg_text` | 段落文字，剥净但**不做大小写归一**，开头带字段名（如「问题描述：…」），供向量化 |
| `deleted` | 同文字表 |

- 分段只覆盖比对范围（`2_landed/business_description.md`「比对范围」）：国内为问题描述、原因分析、改善措施；巴西为问题现象（展平后）、问题描述、最新一条处理过程的原因分析与改善措施；海外为已选问题现象（展平后）、问题描述、问题原因。其余叙述字段只进文字表，按词找。
- 分段规则从 `ctx.config` 读（G4a 定配置文件名与格式），三种：
  - `whole`：整单比对文字拼成一段（评测对照组）；
  - `field`：每个字段一段；
  - `field_split`（默认）：每个字段一段，剥净后超过约 500 字的按段落切成约 300–500 字的段，相邻段重叠一句。
  - 配置读不到或写错时用默认值。规则改了要跑一次全量重建（`rebuild_issue_text`），段编号会变，平台回填会删掉旧段的向量。
- 估算规模：约 3,000 张单，每单 2–3 段，约 1 万段。
- 清洗按 `2_landed/dirty_data.md`「富文本」：剥净内嵌图片、全部标签与实体，只留文字；现象 JSON 按各域主表文件的展平规则。
- 含已删除的单，是为了国内「用户明确要求已删除单」时仍能按文字找；默认查询按 `deleted` 排除，并始终以回源结果为准。
- 建表语句写在治理任务开头（`CREATE TABLE IF NOT EXISTS`）。9 张表都写进 `manifest.data_sources[].tables`：文字表、分段表靠它进启动期校验，向量表靠它出现在 `ctx.data.describe()` 里，供域闸门判断。

### 向量表 `<域>_issue_vec`（平台生成）

```python
VectorizeSpec(source="forge_mart_factory_issue", vector_table="domestic_issue_vec",
              origin_table="domestic_issue_seg", id_column="seg_id",
              text_columns=["seg_text"], default_cron="10,40 * * * *")
# brazil_issue_vec / overseas_issue_vec 同形
```

- 向量行 `id` 是段编号，不是单号。平台尚不支持「按业务记录编号限定与去重」（平台反馈「语义检索切块后按业务记录限定与去重」），所以候选展开与结果归并由模块做，见下。
- 比对文字全为空的单没有段，类似问题找不到它们（关键词一路同样找不到）。F3（正式镜像）显示目前没有这样的未删除单。

### 查询期怎么用（G4a 细化）

- **扩写**：先把问句消解成自足的说法（多轮里「那上个月呢」不能直接拿去检索），再由模型参照术语表与同义词配置扩成：一句完整的现象描述（给语义一路）和一组同义说法（给关键词一路，回答里列出用了哪些说法）。同义词表放 `ctx.config`，业务方可在 Console 增补，不必发版；`glossary.md` 里的规范词与别称是它的起点。
- **关键词一路**：有附加条件时先经 `ctx.data` 在原始表上取候选单；在本域文字表上对比对范围的列（用户点名字段时只对该列）做包含匹配，同义说法任一命中即算，关键词同样归一化；与候选单求交。这一路的结果是完整的。
- **语义一路**：
  - 有附加条件时，经 `ctx.data` 取候选单的主表 ID，再在分段表上取这些单的段编号（用户点名的是比对范围内的字段时，只取该字段的段），传给 `restrict_ids`。候选段数不超过 `top_k` 时把 `top_k` 设成候选段数，全部进重排。
  - 候选段超过 5,000 时（约占国内全表一半以上），平台报 `RetrievalRestrictTooLarge`，改用不限定检索、加大 `top_k`，取回后按候选单过滤；候选占全表大半时，这样的后过滤不会明显少召回，但不再保证候选内完整，回答里要如实说明「结果不保证完整」，统计口径「文字查找」一项同样写明。
  - 不带条件时直接检索。
  - 结果按 `issue_id` 归并，同一单只留得分最高的段；为凑够 10 张不同的单，`top_n` 放大到约 30。
  - 三域都查时，各域分别检索后再合并。平台目前不把重排分数带回，合并只能按向量分数排，重排只在域内起作用；平台带回重排分数前，三域合并后的结果统一交给合并判断那一步（见下）逐张判断相关性，不按跨域先后截断。
- **合并与判断**：两路的单合并去重；语义一路独有的单交给模型逐张判断是否真的相关，不相关的不列；回答区分「文字里出现了这些说法的」与「说法不同但相近的」（呈现方式待 G24）。之后回源取展示字段。
- **域闸门**：每轮开头用 `ctx.data.describe()` 同时看三张主表与本域三张 mart 表。主表有权而 mart 表无权（权限平台漏配）时，该域的文字查找明说「暂不可用」，不说成「没有找到」；其余查询照常。

## 叙述原文的取数（F1 新发现，G4a 细化）

F1 显示叙述列里有内嵌图片，单个值最长约 4,845 万字（约 48 MB）；巴西问题描述 44 行含图，合计约 8,400 万字。结构化取数只要把这些列带进 `select`，一次查询就可能拉回几十 MB，而真正有用的文字不到 1%。所以：

- **清单、汇总、统计不取叙述原文**。只要标识、枚举、数量、日期这类列；清单需要展示描述摘要时，从 mart 的分段表取剥净后的文字（与「类似问题」结果的摘要同一来源，时效同 G22）。
- **关键词搜索、类似问题只读 mart**，不在源库原文上匹配（F2）。
- **单张单的详情回源取原文**，在沙箱里剔除内嵌图片后再展示或交给模型；一次只取一张单，最坏约 48 MB。G4a 要核对它在平台取数行数上限之外的两道限制：沙箱数据帧通道的单次上限、单轮预算。超限时改从 mart 取一份「去图保留格式」的展示用副本（文字表加列，治理任务顺带生成），叙述文字的时效随之变成 G22 的延迟，须在 G22 里一并告知业务方。
- **治理任务读原文时按单分批**：含图的长值集中在少数单上，一批读太多单会一次拉回上亿字。指纹在 SQL Server 上算，只有指纹变了的单才拉全文（见「同步策略」）。

## 检索评测（决定分段规则与两路的取舍）

分段该多细、扩写帮多大忙，靠推理定不了，要在真实数据上比较。

- **评测集**（G3 准备）：一组主题问句，如非接、音频（喇叭、蜂鸣器）、花屏、通信、USB / 打印、按键失灵；每句配上「应该命中的单」。应命中的单先用关键词在正式镜像库的剥净文字上初筛，再由业务方逐张确认，三域都要有；具体单号从正式数据取（开发库里有测试单）。
- **对比组**：分段规则 `whole` / `field` / `field_split` × 扩写与否；平台支持查询侧任务说明后再加一组。
- **指标**：语义一路前 10、前 50 的命中率；带窄条件（某机型、某工厂）的命中率；两路合并后的漏检与误命中。
- **在哪跑**：平台测试环境（有 embedding 与重排服务、能连库）。切换分段规则只改配置、跑一次全量重建与回填（约 1 万段，分钟级）。
- **怎么用结果**：默认用 `field_split`；评测显示 `field` 不差时改用 `field`（段更少、上下文更完整）；`whole` 明显更好时也可切回。结果记入本决策的后续记录。

## 权限承载列清单（建 mart 必填）

**无。** 理由：本助手只有表级权限（三个域各自的主表允许 / 拒绝、CAR 报告表单独允许 / 拒绝），没有按人变化的行级、列级规则（`2_landed/privileges.md`「行级、列级」）；唯一的固定行规则在待办任务表上，该表不进 mart。

| 产物表 | 权限承载列 | 来自源表哪一列 | 是否已确认不跨权限维度预聚合 |
|---|---|---|---|
| `domestic_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含国内单，一单一行或一段一行 |
| `brazil_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含巴西单 |
| `overseas_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含海外单 |

- 域权限怎么落到 mart：权限平台把 9 张 mart 表列进本助手的权限，随所属域给「允许」，写法同其他最外层表（显式写不限行、不屏蔽列）。默认拒绝下漏列一张：关键词或分段取数抛表级拒绝，向量检索静默返回 0 条，所以靠上文「域闸门」每轮检查。
- 平台对无 `field_mappings` 的 mart 别名跳过权限承载列校验；向量表上没有行级规则，也就没有「HNSW 后过滤召回塌陷」的问题。
- **以后若要按部门或个人限制**（`privileges.md`「权限级别」里的「A + 行级规则」），规则引用的列必须先加进 9 张 mart 表，属破坏性变更：改建表语句 → 重建表 → 全量重跑治理与向量化。改权限口径前先改本决策。

## 受列级管控字段的处置

本助手没有列级规则。需要单独处理的是 **CAR 报告**：它单独授权（表级），有国内权限不等于能看报告内容。

- [x] 不向量化该字段：CAR 报告各段文字不进文字表、分段表、向量表。物料问题单上的 CAR 编号照常是问题单字段，但它不是叙述文字，也不进 mart。
- [ ] 按敏感度分表把列级降维成行级：不适用。

## 同步策略

| 任务 | 做什么 | cron（待 G22 定） |
|---|---|---|
| `FACTORY_ISSUE.sync_issue_text`（治理任务，业务仓写） | 按指纹增量同步文字表与分段表，见下 | `*/30 * * * *` |
| `FACTORY_ISSUE.rebuild_issue_text`（治理任务，业务仓写） | 全量重建文字表与分段表，兜底指纹漏判；改分段规则后手动跑一次 | `30 2 * * *` |
| `FACTORY_ISSUE.vectorize:<域>_issue_vec`（平台生成，3 个） | 只重嵌内容有变化的段，删掉已不存在的段（平台按内容哈希判断） | `10,40 * * * *`（错开治理任务 10 分钟） |

**按指纹增量**（不依赖数据量，也不依赖主表修改时间是否随流转更新；海外主表本来就没有修改时间）：

1. 在源库里算每张单的文字指纹：主表各叙述列与子表叙述列一起参与（子表按单汇总），用 `HASHBYTES` 在库里算完，只把「单 ID + 指纹」拉回来，几千行、每行几十字节。内嵌图片不出库。
2. 与 mart 里上次保存的指纹比较，只对新增和指纹变了的单拉全文、清洗、写入文字表，并删掉该单的旧段、写入新段；源上已不存在的单从两张表删掉。
3. 指纹存进文字表，下轮比较用。分段规则不进指纹：改规则靠全量重建。
4. 凌晨全量重建一次，指纹算法有漏判（如某个子表叙述列没纳入）时最多影响一天。

依赖：`HASHBYTES` 对超过 8000 字节的文本需要 SQL Server 2016 及以上（画像 F7 确认开发库，正式库请 DBA 告知版本）。正式库低于 2016 时退回「每轮全量重建」，cron 按上线首轮核对的耗时再定。

- 治理任务里调 `ctx.progress(...)` 上报进度。
- 上线首轮由平台运维手动跑：先全量重建任务，再 3 个向量化任务，跑完重启一次平台（见 `docs/dev/11` 阶段 8）。

### 上线首轮核对（正式环境）

开发库代表不了正式环境的数据量与压力，以下几项在正式环境首轮跑数时由治理任务自报，业务仓据此复核，不需要任何人连正式库：

- 治理任务每轮结束输出一行统计（只含计数与耗时，不含文字）：每域单数、拉全文的单数、段数、清洗前后字符数合计、含内嵌图片的单数、比对文字全空的单数、各步骤耗时。走任务执行记录与日志，平台 Console 任务页可见。
- 复核规则：增量一轮超过 1 分钟或全量重建超过 10 分钟，拉长 cron 或与平台运维商量低峰时段；比对文字全空的单占比明显时，在「类似问题」的说明里写明这些单按文字找不到。
- 大表取数：G5 在平台测试环境验收时看取数日志里待办任务、文档清单查询的耗时；单次超过 2 秒即回到「两张大表能否直连」一项处理。平台测试环境连的是开发库还是正式库副本，要先向平台确认，否则 G5 的耗时同样代表不了正式环境。
