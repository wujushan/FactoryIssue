## 结论先行

1. **结构化取数直连 `info` / `erp`，不治理。** 32 张原始表的筛选、关联、统计、展示都直接查只读副本；脏数据（文本日期、逗号多值、JSON、富文本展示）按 `2_landed/dirty_data.md` 在查询期处理。
2. **文字查找建 `forge_mart_factory_issue`，启用 `governance-etl` + `semantic-retrieval`。** mart 只当「文字索引」：存剥净后的叙述文字、分段与向量，用来回答「哪些单的文字命中 / 相近」；**单上的事实一律回源取**（展示、统计、条件筛选都不读 mart）。
3. **每域 3 张表，共 9 张**：文字表（一单一行，供关键词匹配）、分段表（一段一行，供向量化）、向量表（平台生成）。域权限在本助手里只有表级，按域分表后由权限平台逐表授权；**不设权限承载列**，`field_mappings` 不给 mart 别名填映射。
4. **向量按段，不按单**：一单按字段分段（问题描述 / 现象、原因分析、改善措施各一段），单个字段过长再按段落切。理由是检索粒度而不是长度上限：用户常用很短的说法找单（「非接」「音频」），这件事可能只是整单里的一句，整单压成一个向量会被其余内容稀释。分段规则放 `ctx.config`，可以不发版切换，用评测定（见「检索评测」）。
5. **「涉及某个话题」的问法走关键词与语义两路，合成一张清单**（G24，2026-10-22 定）：用户的说法先对到说法清单里的话题（算的说法、不算的说法由管理员维护，有歧义的加 ＊，放 `ctx.config`）；算的说法按词召回，按命中的栏目分「问题本身涉及」「处理中提到」两组，结果完整、计数确定；有歧义的说法与语义检索只作第三组「可能相关」的补充，经判断后最多列 10 张。不做「只是提到」标注。
6. **CAR 报告文字、附件、PN 不进 mart。**
7. **`analysis-report` 建议从 profiles 移除**：本助手不调用其他模块，用不到它的多步编排与 `ctx.bus`。
8. **同步不依赖数据量，也不依赖修改时间**：每轮在源库里给每张单的文字算指纹，只拉指纹变了的单的全文；每天凌晨全量重建一次兜底（见「同步策略」）。

9. **叙述原文按需回源**：清单、汇总不取叙述原文，按文字找单只读 mart，单张详情才回源取原文并剔除内嵌图片（正式数据里单个叙述值最长约 4,845 万字，见「叙述原文的取数」）。

画像已确认：富文本与内嵌图片普遍，清洗必要；三域文字都是中文；每张单都有比对文字（正式镜像库 F1–F5）；两张大表的取法都有索引，直连（开发库 F6）。`info` 库兼容级别只有 100：指纹与平台分页不受影响，只是以它为当前库时 `TRY_CONVERT`、`STRING_SPLIT` 不可用（F8），属 G4a 的写法约束，不影响本决策的取舍。

### 为什么结构化部分不治理

- 量小：三张主表合计 3,019 行，子表最多 1.8 万行，单次查询拉回来的明细在平台行数上限与沙箱承受范围内。
- 脏数据都是确定规则（按段拆分、文本转日期、JSON 展平、剥内嵌图片），查询期在沙箱里处理即可，不需要预先落一份。
- 两张大表只按单关联取很少几行，前提是有可用索引，由 F6 确认。

### 为什么文字部分必须进 mart

- **类似问题要按意思找**，只能靠向量。平台的声明式向量化只读与向量表**同一个库**里的表（`VectorizeSpec` 的 `origin_table` 与 `vector_table` 同在 `source` 库），原始表在 SQL Server 上，所以必须先由治理任务把文字落进 mart。
- **向量化前的文字要加工**：剥标签、实体与内嵌图片，展平两种现象 JSON，巴西只取最新一条处理过程，再分段。这超出了声明式向量化「单表 + 列拼接」的表达力，正好是治理任务的活。
- **关键词搜索必须在剥净的文字上做**：原文是 HTML（F1：三域问题描述全部带标签），关键词会误命中标签、实体与外链图片地址；更严重的是内嵌图片——F2 显示，含内嵌图片的行在原文上按 usb、lcd、pcb、nfc 匹配几乎全部命中，去掉图片后基本归零。在源库原文上匹配还要把这些动辄几百万字的值整段拉回来复核。剥净后的文字反正要为向量化落进 mart，关键词搜索直接在上面做。

### 为什么按段向量化、为什么要两路

把「非接找不到」拆开看，有四个原因，分段只解决其中一个：

| 原因 | 说明 | 对策 |
|---|---|---|
| 稀释 | 一单一个向量时，只占一句的现象被其余内容冲淡，相关单排不进向量召回的前列 | 按字段分段，长字段再切（结论 4） |
| 术语缺口 | 「非接」是行业简称，模型未必把它与 NFC、非接触、射频、感应等放在一起；与文档长短无关 | 管理员维护的说法清单（算的 / 不算的，有歧义的加 ＊）+ 关键词一路（结论 5） |
| 短问句缺任务说明 | Qwen3 的两个模型都要求查询侧带任务说明；平台现在原样发问句，模块也没法只给向量化一侧加 | 平台反馈「语义检索查询侧缺少任务说明」；实现前用扩写弥补 |
| 问法要完整清单 | 「有没有涉及 X」「X 相关问题」用户期望看到全部，语义检索只给最相近的若干张 | 关键词一路按算的说法召回，前两组结果完整（G24） |

另有两点降低了稀释的影响，所以不切到句子级：

- 重排是把问句与段落放在一起读的，一句话里提到的内容它判断得准；稀释主要伤的是「进不进向量召回前列」这一步。切得太碎，重排只看到片段，丢上下文，「一句顺带提到」的误命中反而增加。
- 带条件检索时，候选段数不超过召回条数，每段都直接进重排，向量相似度高低无关。

### 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 不建 mart：关键词搜索在源库上模糊匹配 + 沙箱复核；类似问题由模型把现象扩写成一组关键词再搜 | 类似问题退化成关键词搜索，做不到「按意思相近」；源库匹配受标签、图片干扰 |
| 三域合进一套表，按「所属域」列过滤 | 域权限只有表级，同表内无法按域授权；只能取回后再按域筛，等于模块自己做权限过滤，违反「权限经平台取数前阻断」 |
| 一单一个向量（整单拼成一段） | 见上表「稀释」。保留为评测里的对照组（分段规则 `whole`），不作默认 |
| 每个叙述字段各建一张向量表 | 约 35 张向量表，权限平台要逐张授权。分段表里每段带字段标记，限定检索时只取某个字段的段即可达到同样效果，不必分表 |

## 产物设计

### 文字表 `<域>_issue_text`（一单一行，只含未删除的单）

| 列 | 内容 |
|---|---|
| `issue_id` | 源主表主键，转文字；主键 |
| `issue_no` | 问题编号（仅便于排查，回答不从这里取） |
| 各叙述字段列 | 每个叙述字段一列，剥净后**归一化**（小写、全角转半角、连续空白压成一个空格），专供关键词匹配。国内另有问题现象列：已选现象与可能原因表 → 问题现象表的现象文字，按现象去重后用「；」连接（G24） |
| 子表汇总列 | 国内 / 海外处理步骤的结论、意见、措施（每个环节只取最新一条），巴西处理过程各叙述列、费用备注：按记录先后拼成一段，每列一段，同样归一化 |
| 巴西最新处理过程两列 | 最新一条（ID 最大）处理过程的原因分析、改善措施 |
| `text_fingerprint` | 源库算出的本单文字指纹，增量同步时比较用（见「同步策略」） |
| `synced_at` | 本行同步时间 |

### 分段表 `<域>_issue_seg`（一段一行，向量化的来源）

| 列 | 内容 |
|---|---|
| `seg_id` | 段编号，主键：`<issue_id>:<字段代号>:<序号>`，如 `2811:desc:0` |
| `issue_id` | 所属单 |
| `field` | 字段代号：`phen`（问题现象，三域；国内为建单时选的现象，G24 加入）、`desc`（问题描述）、`reason`（原因分析）、`measure`（改善措施）、`improve`（改善建议）、`prev`（预防对策）、`sqe`（SQE 跟进结果，巴西）、`step`（整理后的处理步骤，国内、海外） |
| `seq` | 字段内序号，从 0 起 |
| `seg_text` | 段落文字，剥净但**不做大小写归一**，开头带字段名（如「问题描述：…」），供向量化 |
| `seg_norm` | 同一段文字的归一化版本（小写、全角转半角、连续空白压成一个空格，不带字段名前缀），供按词匹配。按词匹配在段上做，命中直接得到段编号，可与语义一路合并重排，也便于截取上下文 |

- 分段只覆盖比对范围（`2_landed/business_description.md`「比对范围」，G29 扩充、G24 加国内问题现象后）：国内为问题现象、问题描述、原因分析、改善建议、改善措施、预防对策、处理步骤；巴西为问题现象（展平后）、问题描述，以及最新一条处理过程的原因分析、改善措施、预防对策、SQE 跟进结果；海外为已选问题现象（展平后）、问题描述、原因分析、改善建议、改善措施、预防对策、处理步骤。剥净后不超过 10 字的字段值不进向量、不参与按意思找，问题现象（`phen`）除外：它是选出来的短标签（如「黑屏、白屏」），三域都照常成段。（2026-10-23 G48：短值仍要能按词找，关键词搜索、话题前两组、点名字段按词找都要比对到它；G4a 定做法，例如分段表照收短值、向量化只读超过 10 字的段。）其余叙述字段只进文字表，按词找。
- 每段的字段代号决定它在「涉及某个话题」里归哪一组（G24）：`phen`、`desc`、`reason`（巴西为最新一条处理过程的原因分析）归第一组「问题本身涉及」；`improve`、`measure`、`prev`、`sqe`、`step` 归第二组「处理中提到」。分组规则随分段规则放 `ctx.config`，内置默认值即此。
- 处理步骤由治理任务整理成每单一个 `step` 字段再分段：
  - 每个环节只取最新一条（国内同一环节编码 `Step`、海外同一 `StepStr` 下 ID 最大；国内按编码认环节，见 `2_landed` 总述「比对范围」）；
  - 只取分析类环节的意见、措施（工厂制程分析另取结论），环节清单放 `ctx.config`（与分段规则同一份配置，内置默认值 = 落盘清单）；清单外的环节（国内按编码、海外按名称）不纳入，治理任务每轮在统计行里报出；
  - 每条前带环节名称，剥净后不超过 10 字的不进向量（G48：仍留着供按词找）；同单内完全相同的条目只留一条。
  - 不做「与主表重复」的去重：E4 显示 1.65 万条里只有 24 条与主表相同或被包含，去重规则不值得维护。
  - **G4a 核对**：E5 显示不纳入环节的「措施」常是「人名 + 环节标签 + 意见」的系统拼接（如「【人名】效果确认结果：OK」）。分析类环节若也这样，措施里会带人名、并与意见重复一遍。G4a 用平台测试环境的样本核对，是则清洗时去掉人名前缀、措施包含意见时只留措施。（2026-10-23：海外「操作记录」截图证实，措施列就是页面上的「内容」，是「操作人姓名 + 这一步的结果与所填各项」拼成的一句话，责任人确认这一步还会把主表原因分析、改善措施、预防对策再写一遍；国内同一列含义相同。清洗按上面做；与主表同名字段重复的部分，G4a 再定是否在比对与「原因与措施」里去重。）- 分段规则从 `ctx.config` 读（G4a 定配置文件名与格式），三种：
  - `whole`：整单比对文字拼成一段（评测对照组）；
  - `field`：每个字段一段；
  - `field_split`（默认）：每个字段一段，剥净后超过约 500 字的按段落切成约 300–500 字的段，相邻段重叠一句。
  - 配置读不到或写错时用默认值。规则改了要跑一次全量重建（`rebuild_issue_text`），段编号会变，平台回填会删掉旧段的向量。
- 估算规模（按正式镜像 F3、E1、E2 的实数）：国内原范围约 3,800 段（问题描述 2,474、原因分析 468、改善措施 881，另有少量长字段切段），加改善建议约 1,100、预防对策约 500、处理步骤约 2,000–2,500（分析类环节约 63 万字），国内合计约 8,000 段，G24 再加问题现象约 966 段（966 张单各一段，现象很短），约 9,000 段；巴西约 1,000 段、海外不到 100 段。三域合计约 1.1 万段，仍是分钟级回填。
- 清洗按 `2_landed/dirty_data.md`「富文本」：剥净内嵌图片、全部标签与实体，只留文字；现象 JSON 按各域主表文件的展平规则。
- 只含未删除的单（国内是否删除不为 1；巴西状态不为 -1；海外是否删除为 0）：已删除的单与管理页面一样查不到（决策 2026-10-22「按编号查单」）。单被删除后，治理任务把它从文字表、分段表删掉，平台回填随之删掉对应向量；查询结果仍以回源为准。
- 建表语句写在治理任务开头（`CREATE TABLE IF NOT EXISTS`）。9 张表都写进 `manifest.data_sources[].tables`：文字表、分段表靠它进启动期校验，向量表靠它出现在 `ctx.data.describe()` 里，供域闸门判断。

### 向量表 `<域>_issue_vec`（平台生成）

```python
VectorizeSpec(source="forge_mart_factory_issue", vector_table="domestic_issue_vec",
              origin_table="domestic_issue_seg", id_column="seg_id",
              text_columns=["seg_text"], default_cron="10,40 * * * *",
              metadata_columns=["issue_id", "field"])   # core ≥ 0.3.7 / data ≥ 0.3.2，见下
# brazil_issue_vec / overseas_issue_vec 同形
```

- 向量行 `id` 是段编号，不是单号。`issue_id`、`field` 声明为 `metadata_columns`，平台把它们抄进向量表（text 列 + btree 索引），检索时按单限定（`restrict_column="issue_id"`）、按单去重（`group_by="issue_id"`）、按字段找（`filters={"field": [...]}`）都靠它们，命中从 `h.metadata["issue_id"]` 取单（平台反馈「语义检索切块后按业务记录限定与去重」，平台文档 2026-10-22 已更新）。
- **版本依赖**：需 `paxsz-forge-core ≥ 0.3.7` / `paxsz-forge-data ≥ 0.3.2`（开发依赖 `paxsz-forge-platform ≥ 0.3.7`）。本仓 2026-10-22 已升级并改 `pyproject.toml` 下界，不连库核对与文档一致：
  - `VectorizeSpec.metadata_columns` 可声明，用 `seg_id`、`content`、`metadata` 作列名会被拒；
  - 生成的 DDL 多出 `issue_id text`、`field text` 两列与各自的 btree 索引，回填 SQL 把两列透传进向量表；
  - `search()` 有 `restrict_column`、`filters`、`group_by`。按单限定加按字段过滤编译成同一个 `WHERE`；`group_by` 用 `DISTINCT ON` 每单留最近的一段；
  - 命中的 `metadata` 里有 `issue_id`、`field`（回填时整行附带的列写进向量表的 jsonb），重排成功时带 `rerank_score`；
  - 有 `RetrievalColumnNotDeclared`。
  - 低于这些版本时，`metadata_columns` 声明会被静默丢弃，检索参数即 `TypeError`。
- **必须在建向量表前声明**：向量表的 DDL 都是 `IF NOT EXISTS`，建成后再加 `metadata_columns` 不会补列，平台会拒绝启动，只能手工 `ALTER TABLE` 并重跑回填。所以 `metadata_columns` 随 9 张表一起写进评审稿、一起申请建库。文字表、分段表由治理任务自己建，不受影响。
- 比对文字全为空的单没有段，类似问题找不到它们（关键词一路同样找不到）。F3（正式镜像）显示目前没有这样的未删除单。

### 查询期怎么用（G4a 细化）

「有没有涉及 X」「X 相关问题」按下面 ①–⑦ 走（G24）；「有没有出现过开机花屏，当时怎么处理的」这类找先例的问法，只走 ③④ 的语义一路，给最相近的若干张。用户自己点名要搜某几个词（关键词搜索，如「描述里有『打印』和『USB』的单」）时，只按用户给的词匹配，「和」「或」照用户说的，不套说法清单、不分组，匹配规则同 ②。

**配置**（`ctx.config`，管理员在 Console 维护，读不到或写错时用内置默认值，G4a 定格式；说法清单的内置默认值就是 `2_landed/topic_terms.md` 的清单）：

- **说法清单，按话题组织**（G24）：每个话题有一句简短说明（如「非接触式读卡（挥卡、NFC）相关的问题」，给重排与判断用）、算的说法（出现即命中，如 NFC、非接触；有歧义的加 ＊ 标记，如 ＊射频、＊感应）、不算的说法（如纸张感应）。本仓起草、按探测 L1–L3 修订，业务方 2026-10-22 暂且同意（G45），落盘 `2_landed/topic_terms.md`。
- 不设「只是提到」提示词表（G24 否决提示词就近标注：会把「更换喇叭后测试正常」这类修好的真问题标错）。
- **说法清单的维护**（业务侧流程见 `2_landed/topic_terms.md`「上线后怎么维护」，G4a 落实）：
  - 槽位：`manifest.config_files` 声明一个文件（如 `topic_terms.yaml`，文件名与格式 G4a 定），`description` 写清是「涉及某个话题」的说法清单。平台只存不解析，管理员在 Console「模块配置」页上传、预览、回滚。
  - 内置默认值：平台不提供包内默认文件，没上传时 `ctx.config.text()` 为 `None`。代码内置一份与 `topic_terms.md` 一致的清单兜底，并加单元测试比对代码默认值与 `topic_terms.md`，防止两边漂移。
  - `validate_config()`：能解析；每个话题有说明与至少一个算的说法；中文说法至少 2 个字；同一话题内不重复、不同时算又不算；＊ 标记写法正确。只做快速检查，不读库（它在网关进程同步执行、没有超时保护）。
  - 缓存：解析结果按 `ctx.config.version()` 缓存，版本变了再解析。
  - 生效：清单只在提问时用（按词匹配在 `seg_norm` 上做，话题说明作语义一路的问句），改了下一轮即生效，不触发重建或重嵌；分段规则是另一份配置，改了才要全量重建。
  - 留痕：每轮用的配置版本进审计归档 `configs.json`；测试通道进 `trace.configs`，G3 / G5 的用例对结果有影响时据此核对。
  - 回写：发版前把 Console 当前版本回写 `topic_terms.md` 与代码内置默认值，在 `docs/decisions/` 记一句。
  - 临时说法：清单里没有的话题由模型临时提说法，回答里列出；怎么让管理员看到常用的临时说法（如审计日志里检索），G4a 定。

**流程**：

- **① 定话题**：先把问句消解成自足的说法（多轮里「那上个月呢」不能直接拿去检索），再由模型把用户的说法对到说法清单里的话题，只能从清单里选。清单里没有对应话题时，模型提出几个说法，作临时的算的说法使用，回答里列出用了哪些说法，并给可点的选项让用户增减说法或只看第一组；常用的临时说法由管理员补进清单（怎么让管理员看到，G4a 定）。话题一旦对上，用哪些说法由清单决定，同一个问题每次召回的单一样。
- **② 关键词一路**（结果完整、计数确定）：
  - 在本域分段表的 `seg_norm` 上逐处匹配；用户点名的是比对范围以外的字段时，改在文字表的该列上匹配（这些字段没有向量，不参与 ④ 的重排）。
  - 中文说法（含夹带英文的，如「IC卡」）忽略空格按包含匹配，最短 2 个字；纯英文缩写要求前后都不是英文字母或数字（不用数据库正则的词边界：它把汉字也当作「词的一部分」，「刷卡NFC失效」会匹配不上），且不在去掉空格的文字上匹配（「use NFC card」去掉空格后 NFC 前后都是字母）。
  - 不算的说法只屏蔽它出现的那一处，屏蔽后再看剩下的文字是否命中，不把整张单剔掉。
  - 有附加条件时，经 `ctx.data` 在原始表上取候选单的主表 ID，只在这些单的段里匹配。
  - 算的说法（不带 ＊）命中的单按命中段的字段代号分组：在第一组字段（`phen`、`desc`、`reason`）里命中的归第一组，否则归第二组；按单去重，由数据库计数（N1、N2）。用户点名字段时只在该字段里找、不分组（G23）；问做法时只看措施类字段、也不分组（G24）。
  - 带 ＊ 的说法只在第一组字段里命中、且该单不在前两组的，进入 ⑤ 判断；只在第二组字段里命中的不算。
- **③ 语义一路**：
  - 检索用的问句是 ① 定下的话题说明，或用户原话消解后的一句现象描述；不把说法串拼进去（有研究发现，把查询扩写直接交给神经重排模型，效果可能下降）。
  - 有附加条件时，经 `ctx.data` 取候选单的主表 ID，直接传 `restrict_ids=候选单, restrict_column="issue_id"`，不再展开成段编号。限定时平台走精确近邻，候选内召回完整。
  - 只在某些字段里找时加 `filters={"field": [...]}`：用户点名的是比对范围内的字段（G23）只给该字段；问做法（G29「按问法分工」）只给措施类字段 `improve`、`measure`、`prev`、`sqe`、`step`。`filters` 与 `restrict_ids`、行级权限都是 AND，只收窄。
  - 上限 5,000 按候选单数算，三域未删除单最多是国内的 2,474 张，正常撞不上；仍接住 `RetrievalRestrictTooLarge`（单数将来超过 5,000 时），改用不限定检索、加大 `top_k`、取回后按候选单过滤，并如实说明「结果不保证完整」。
  - 不带条件时直接检索。
  - 按单去重用 `group_by="issue_id"`，同一单只占一个结果位，`top_n` 数的是单数，不再放大。带候选时结果精确；不带候选时平台近邻多取 4 倍再折叠，只能尽量凑满 10 张。
  - 三域都查时，各域分别做 ①–⑤，再按域分组呈现（每域内前两组按建单时间倒序，第三组按 ④ 的顺序），与总述「先给各域小计」、G39「三域按域分开列」一致。命中带回 `rerank_score`（同一问句下跨表可比），需要跨域比较时按它比、`None` 时才退回 `score`；按域分组呈现是业务规则，不因此改为跨域混排。
- **④ 第三组的候选排序**：前两组是完整清单，不重排，按建单时间倒序（G24）。第三组的候选单 = ③ 找到的单与 ② 里带 ＊ 说法在第一组字段命中的单，去掉已在前两组的单；以这些单再检索一次（`restrict_ids=候选单, restrict_column="issue_id", group_by="issue_id"`，`top_k` 设成候选单的段数、`top_n` 设成候选单数），平台对候选单的段逐段精确比对、重排后每单留最相关的一段，问句同 ③，每单带回 `rerank_score`。候选超过上限（约 500 段，G4a 按重排耗时定，放配置）时只取 ③ 的结果重排。
- **⑤ 第三组的判断**：先按 `rerank_score` 初筛，低于阈值的候选不交模型、视为不相关（阈值放配置，由检索评测定；评测前不启用，`rerank_score` 为 `None` 时也不筛）。再按 ④ 的顺序把剩下的候选交给模型判断「X 是不是这张单的问题现象或原因」，最多判断约 30 张（G4a 按耗时定）；判断为相关的列入第三组，最多 10 张。判断为不相关、来不及判断的不列出，也不对用户计数（G24）；来不及判断时，回答建议用户加时间、机型等条件再查。不做「只是提到」标注。每张单带一段命中处前后约 80 字的上下文，供判断与展示。探测 L2、L3（2026-10-22）：初稿清单下不加条件时国内每个话题待判断 1–156 张，多个话题远超上限，靠收紧说法清单（G45）减少；抽查的待判断约一半相关，看错的从上下文分得出。
- **⑥ 呈现**（G24）：一张清单分三组，每行写明命中方式（命中了哪个说法、在哪一栏，或按意思相近）和上下文片段：
  - 问题本身涉及 X 的 N1 张（第一组，完整，按建单时间倒序）；
  - 处理中提到 X 的 N2 张（第二组，完整，按建单时间倒序；注明多是顺带提到，探测 L3 抽查 12 张里 4 张相关）；
  - 说法不同、可能相关的 S 张（第三组，最多 10 张，按 ④ 的顺序，注明不保证找全）。

  回答开头给 N1、N2、S，并列出本次用了哪些说法。N1、N2 由数据库计数，S 由执行器按标签计数，模型不报数；统计口径「文字查找」一项写明前两组按说法清单计、第三组按内容判断可能有误判。清单上百张时按呈现规范导出全量。之后回源取展示字段。
- **⑦ 后续演进**：
  - 入库时打标签：治理任务给每段标「涉及哪些话题」，查询变成结构化筛选，完整、确定、更快，第三组也能给全。需要平台在治理任务里提供大模型或重排模型句柄，见平台反馈「治理任务缺少大模型与重排句柄」。实现后只需在分段表加标签列。
  - 评测显示重排分可靠时，⑤ 可从「初筛 + 模型判断」改为只按分数阈值判断，判断量不再受约 30 张的上限约束，不改库表。
- **域闸门**：每轮开头用 `ctx.data.describe()` 同时看三张主表与本域三张 mart 表。主表有权而 mart 表无权（权限平台漏配）时，该域的文字查找明说「暂不可用」，不说成「没有找到」；其余查询照常。

## 叙述原文的取数（F1 新发现，G4a 细化）

F1 显示叙述列里有内嵌图片，单个值最长约 4,845 万字（约 48 MB）；巴西问题描述 44 行含图，合计约 8,400 万字。结构化取数只要把这些列带进 `select`，一次查询就可能拉回几十 MB，而真正有用的文字不到 1%。所以：

- **清单、汇总、统计不取叙述原文**。只要标识、枚举、数量、日期这类列；清单需要展示描述摘要时，从 mart 的分段表取剥净后的文字（与「类似问题」结果的摘要同一来源，时效同 G22）。
- **关键词搜索、类似问题只读 mart**，不在源库原文上匹配（F2）。
- **单张单的详情回源取原文**，在沙箱里剔除内嵌图片后再展示或交给模型；一次只取一张单，最坏约 48 MB。G4a 要核对它在平台取数行数上限之外的两道限制：沙箱数据帧通道的单次上限、单轮预算。超限时改从 mart 取一份「去图保留格式」的展示用副本（文字表加列，治理任务顺带生成），叙述文字的时效随之变成 G22 的延迟。业务方 2026-10-22 同意 G22 时，前提是「单上内容都实时查」，没有涵盖这一情形；G4a 若确需改走 mart 副本，须另向业务方确认单张单详情的叙述文字可以晚约半小时。
- **治理任务读原文时按单分批**：含图的长值集中在少数单上，一批读太多单会一次拉回上亿字。指纹在 SQL Server 上算，只有指纹变了的单才拉全文（见「同步策略」）。

## 检索评测（决定分段规则与两路的取舍）

分段该多细、扩写帮多大忙，靠推理定不了，要在真实数据上比较。

- **评测集**（G3 准备）：一组主题问句，如非接、音频（喇叭、蜂鸣器）、花屏、通信、USB / 打印、按键失灵；每句配上「应该命中的单」。应命中的单先用关键词在正式镜像库的剥净文字上初筛，再由业务方逐张确认，三域都要有；具体单号从正式数据取（开发库里有测试单）。
- **对比组**：分段规则 `whole` / `field` / `field_split` × 扩写与否；平台支持查询侧任务说明后再加一组。
- **指标**：
  - 语义一路：前 10、前 50 的命中率；带窄条件（某机型、某工厂）的命中率。
  - 关键词一路：按话题、按每个说法分别统计准确率与召回率。误命中多的说法改加 ＊ 或挪到不算的说法，只改配置。
  - 分组与模型判断（G24）：第一组里有多少其实只是处理中提到、第二组里有多少其实是问题本身；第三组模型判断相关与否对不对。
  - 重排分阈值（⑤ 初筛）：在第三组候选上看 `rerank_score` 与业务方判断的对应，定一个几乎不误删相关单的阈值；被阈值筛掉的一堆并入下条的漏判抽样。
  - **漏判抽样**（借鉴电子取证审查的做法）：从「第二组」「判断为不相关」「未逐张判断」三堆里各随机抽一批，请业务方核对，估计每堆里还有多少其实是问题本身涉及或相关。比例偏高就调整分组字段、说法清单或判断上限。G5 验收前做一次，上线后清单大改时再做。
  - 两路合并后的漏检与误命中。
- **在哪跑**：平台测试环境（有 embedding 与重排服务、能连库）。切换分段规则只改配置、跑一次全量重建与回填（约 1 万段，分钟级）。
- **怎么用结果**：默认用 `field_split`；评测显示 `field` 不差时改用 `field`（段更少、上下文更完整）；`whole` 明显更好时也可切回。结果记入本决策的后续记录。

## 权限承载列清单（建 mart 必填）

**无。** 理由：本助手只有表级权限（三个域各自的主表允许 / 拒绝、CAR 报告表单独允许 / 拒绝），没有按人变化的行级、列级规则（`2_landed/privileges.md`「行级、列级」）；唯一的固定行规则在待办任务表上，该表不进 mart。

| 产物表 | 权限承载列 | 来自源表哪一列 | 是否已确认不跨权限维度预聚合 |
|---|---|---|---|
| `domestic_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含国内单，一单一行或一段一行 |
| `brazil_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含巴西单 |
| `overseas_issue_text` / `_seg` / `_vec` | 无（域权限 = 表级） | — | 是：只含海外单 |

- 域权限怎么落到 mart：权限平台把 9 张 mart 表列进本助手的权限，随所属域给「允许」，写法同其他最外层表（显式写不限行、不屏蔽列）。默认拒绝下漏列一张：关键词或分段取数抛表级拒绝，向量检索静默返回 0 条，所以靠上文「域闸门」每轮检查。
- 平台对无 `field_mappings` 的 mart 别名跳过权限承载列校验；向量表上没有行级规则，也就没有「HNSW 后过滤召回塌陷」的问题。
- **以后若要按部门或个人限制**（`privileges.md`「权限级别」里的「A + 行级规则」），规则引用的列必须先加进 9 张 mart 表，属破坏性变更：改建表语句 → 重建表 → 全量重跑治理与向量化。改权限口径前先改本决策。

## 受列级管控字段的处置

本助手没有列级规则。需要单独处理的是 **CAR 报告**：它单独授权（表级），有国内权限不等于能看报告内容。

- [x] 不向量化该字段：CAR 报告各段文字不进文字表、分段表、向量表。物料问题单上的 CAR 编号照常是问题单字段，但它不是叙述文字，也不进 mart。
- [ ] 按敏感度分表把列级降维成行级：不适用。

## 同步策略

| 任务 | 做什么 | cron（G22 已定，业务方 2026-10-22 同意） |
|---|---|---|
| `FACTORY_ISSUE.sync_issue_text`（治理任务，业务仓写） | 按指纹增量同步文字表与分段表，见下 | `*/30 * * * *` |
| `FACTORY_ISSUE.rebuild_issue_text`（治理任务，业务仓写） | 全量重建文字表与分段表，兜底指纹漏判；改分段规则后手动跑一次 | `30 2 * * *` |
| `FACTORY_ISSUE.vectorize:<域>_issue_vec`（平台生成，3 个） | 只重嵌内容有变化的段，删掉已不存在的段（平台按内容哈希判断） | `10,40 * * * *`（错开治理任务 10 分钟） |

**按指纹增量**（不依赖数据量，也不依赖主表修改时间是否随流转更新；海外主表本来就没有修改时间）：

1. 在源库里算每张单的文字指纹：主表各叙述列与子表叙述列一起参与（子表按单汇总），用 `HASHBYTES` 在库里算完，只把「单 ID + 指纹」拉回来，几千行、每行几十字节。内嵌图片不出库。
2. 与 mart 里上次保存的指纹比较，只对新增和指纹变了的单拉全文、清洗、写入文字表，并删掉该单的旧段、写入新段；源上已不存在或已删除的单从两张表删掉（指纹比较只拿未删除的单）。
3. 指纹存进文字表，下轮比较用。分段规则不进指纹：改规则靠全量重建。
4. 凌晨全量重建一次，指纹算法有漏判（如某个子表叙述列没纳入）时最多影响一天。

依赖：`HASHBYTES` 对超过 8000 字节的文本需要 SQL Server 2016 及以上（画像 F7 确认开发库，正式库请 DBA 告知版本）。正式库低于 2016 时退回「每轮全量重建」，cron 按上线首轮核对的耗时再定。

- 治理任务里调 `ctx.progress(...)` 上报进度。
- 上线首轮由平台运维手动跑：先全量重建任务，再 3 个向量化任务，跑完重启一次平台（见 `docs/dev/11` 阶段 8）。

### 上线首轮核对（正式环境）

开发库代表不了正式环境的数据量与压力，以下几项在正式环境首轮跑数时由治理任务自报，业务仓据此复核，不需要任何人连正式库：

- 治理任务每轮结束输出一行统计（只含计数与耗时，不含文字）：每域单数、拉全文的单数、段数、清洗前后字符数合计、含内嵌图片的单数、比对文字全空的单数、各步骤耗时。走任务执行记录与日志，平台 Console 任务页可见。
- 复核规则：增量一轮超过 1 分钟或全量重建超过 10 分钟，拉长 cron 或与平台运维商量低峰时段；比对文字全空的单占比明显时，在「类似问题」的说明里写明这些单按文字找不到。
- 大表取数：G5 在平台测试环境验收时看取数日志里待办任务、文档清单查询的耗时；单次超过 2 秒即回到「两张大表能否直连」一项处理。平台测试环境连的是开发库还是正式库副本，要先向平台确认，否则 G5 的耗时同样代表不了正式环境。

## 结论

- `manifest.data_sources` 别名：`info`（INFO 实例）、`erp`（ERP 实例）、`forge_mart_factory_issue`（mart，tables 列 9 张表）。
