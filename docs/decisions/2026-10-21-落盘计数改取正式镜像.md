# 2026-10-21 落盘计数改取正式镜像

## 背景

G1 的行数统计（2026-10-16、10-19）与探测 C1–C10 在 INFO 开发库上执行。开发库是正式库的副本，另有测试数据（决策 2026-10-20「内网计数来自开发库」）。正式环境的 PostgreSQL 镜像库 `ai-info` 可用之后，两者已有差别（探测 P0b、O4）：未删除的单国内 2,447 → 2,474、巴西 191 → 203、海外 13 → 12；关联了 CAR 的物料问题 1,331 → 1,364。开发库里有海外测试单。那份决策留了一项待业务方决定：要不要把 `2_landed` 的计数整套换成正式镜像的数字。

## 决定

业务方 2026-10-21 同意 G38 建议：

- `2_landed` 的行数、主表按年分布与各处「业务方内网计数」整套换成正式镜像的数字，一次重算，不零散替换。
- 以后落盘计数一律取正式镜像；开发库只用来查索引、执行方式、版本这类 SQL Server 才有的事实。

本仓补充：

- 列类型与长度仍以 SQL Server 的 information_schema 为准。镜像库是 PostgreSQL，类型不同，不用它替换。
- 已经是正式镜像计数的结论（富文本、比对范围、订单号与 CAR 编号、料号与 PN 编码、停线、结案时间、不良率、机型与系列、部门名称）不重跑，保留原日期。
- 镜像库里没有的表（国内工厂表在 ERP 实例，很可能没有）沿用开发库行数，落盘写明。
- 重算后某条规则的前提不再成立时（出现多值、对不上的段、其他写法），不直接改数，另提待确认。

重算用 `docs/probes/2026-10-21-落盘计数重算探测说明.md`（R0–R6）。执行前 `2_landed` 的计数不动。

## 补记：重算执行结果（2026-10-22）

业务方 2026-10-22 在镜像库执行了 R0–R6，数据截至 2026-10-20。29 张表都在镜像库里（国内工厂表也在），没有沿用开发库的行数。已整套替换：总述「数据量声明」（表格、按年分布、业务含义）与统计口径的示例数字，`dirty_data.md` 开头与各条计数，巴西「时间」「数据规模」，国内发现工位写法数，国内主表 IQC 状态、国内生产订单 PN 名称、巴西申请单 PN 编码、海外主表当前责任人、文档清单的字段说明；`privileges.md` 的「现有 1 张」与重算结果相同，不用改。G2 决策草案的数据量表同步改了。

与开发库相比，有几处只在开发库里出现过：IQC 状态有值的单（开发库 2 张）、进行中的退货 / 退库（开发库 3 张单）、巴西测试值 0 与只有雷亚尔的单。正式数据里目前都没有，对应规则照旧保留。

规则前提都成立。只有一处转待确认：巴西关联申请单有 52 条 PN 编码只有 1 位数字（43 张单），对不上 PN 主数据，像是占位值，见 open-questions B17。

补充探测 R4f1 显示这 52 条都是「0」：29 张单另有 15 位 PN，14 张单上只有 0。业务方 2026-10-22 用 R4f2 按这两类到管理页面核对：只有 0 的单 PN 一栏为空；另有 15 位 PN 的单只显示那些 PN；按 PN 搜「0」搜不到。B17 据此关闭：PN 编码为 0 是占位值，不展示、不参与按 PN 查，只有 0 的单 PN 显示「未填」（页面上为空，助手按答案呈现规范写「未填」）。已改巴西业务描述「一行一单」「大机型与 PN」、总述「三域共用的说法」、术语表「PN」、`dirty_data.md`、巴西申请单字段说明。
