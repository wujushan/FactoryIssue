# 脏数据与特殊解析

> 文中「正式镜像计数」取自正式环境的镜像库。各条处理规则不依赖其确切数字（见总述「数据量声明」）。

## 富文本（HTML）

源系统录入界面是富文本编辑器，叙述类长文本在库中常存成 HTML 片段，不是纯文本。

| 标记 | 含义 |
|---|---|
| `<p>…</p>` | 段落 |
| `<strong>…</strong>` | 加粗 |
| `<img src="https://…" />` | 外链图片（常见为 INFO 文件服务器上的库文件地址） |
| `<img src="data:image/…;base64,…" />` | 内嵌 base64 图片 |
| `&nbsp;` | 不换行空格 |

涉及字段：

| 域 | 字段 |
|---|---|
| 国内 | 主表问题描述、原因分析、改善建议、改善措施、预防对策、效果确认、生产确认备注、备注、原因分类说明、重启方案；处理步骤意见、措施、结论；CAR 报告各段文字 |
| 巴西 | 主表问题描述、补料备注、备注；处理过程各叙述列；费用备注 |
| 海外 | 主表问题描述、改善建议；其余叙述列按同样方式对待 |

内嵌 base64 图片只在少数行里，却占了叙述文字的绝大部分（业务方 2026-10-20 正式镜像计数）：

| 域 | 列 | 含内嵌图片的行 |
|---|---|---|
| 国内 | 主表问题描述 | 9 |
| 巴西 | 主表问题描述 | 44 |
| 巴西 | 处理过程原因分析 / 改善措施 / 预防对策 | 9 / 3 / 1 |
| 海外 | 主表问题描述 | 1 |

- 这 67 行合计约 1.12 亿字，占三域叙述文字约 98%；单个值最长约 4,800 万字（巴西问题描述）。去掉内嵌图片后，这 67 行只剩约 2 万字。
- 其余图片都是外链。
- 图片编码由随机字母组成，几乎必然含 usb、lcd、pcb、nfc 这类字母组合：含内嵌图片的行，在原文上按关键词匹配几乎全部误命中，去掉图片后才是真实命中。
- 任何叙述列，展示、按关键词匹配或交给模型解读前，都要先剔除内嵌图片。

处理口径：

- 源值保留 HTML，不改写。
- 展示前剔除内嵌 base64 图片；段落标记、外链图片保留。不保证 100% 清除。
- 做相似问题比对前，base64 图片、全部 HTML 标签与实体都剥净，只留文字。图片内容不参与比对。
- 这些字段不作为筛选、分组、关联条件；用户按现象或做法找单时，用相似问题查找或关键词模糊匹配。

## 自由文本

| 域 | 列 | 情况 |
|---|---|---|
| 国内 | 发现工位 | 约 410 种写法，非原子值，分隔符混乱，同义多种写法；不能当枚举精确筛选，靠模糊匹配或相似查找，同义写法可能漏检 |
| 巴西 | 发现工位 | 自由文本，无固定枚举 |
| 巴西 | 投诉单号 | 自由文本，多数以 `CLAIM` 开头但不绝对，分隔符、日期片段写法多样；展示原值，筛选用模糊匹配 |
| 海外 | 发现工位 | 自由文本 |

## 逗号分隔的多值列

| 域 | 列 | 存什么 |
|---|---|---|
| 国内 | `MemberList` / `MemberListName` | 主状态处理人 ID / 姓名 |
| 国内 | `IQCMemberList` / `IQCMemberListName` | IQC 成员 ID / 姓名 |
| 国内 | `AllReDepartment` | 责任归属部门 ID |
| 国内 | 处理步骤 `MemberList`、`FileUrl` | 步骤责任人 ID（内部字段，不展示）、附件 ID |
| 巴西 | `BrazilFactory` | 巴西工厂名称，如 `CA,TT` |
| 巴西 | `ProductIDAll` | 大机型 ID；逐段去首尾空格。对不上产品主数据的段不显示，全部对不上时显示「未识别机型」，不展示内部编号。业务方 2026-10-22 正式镜像计数：未删除的 203 张单都填了大机型，共 215 段，全部能对上；分隔符都是半角逗号 |
| 海外 | `ProductType` | 大机型 ID；规则同巴西：逐段去首尾空格，对不上产品主数据的段不显示，全部对不上时显示「未识别机型」，不展示内部编号。业务方 2026-10-23 正式镜像计数：未删除的 12 张单都填了大机型，共 12 段，全部能对上 |
| 海外 | `PNList` | PN 编码，逗号分隔；经 PN 主数据得到 PN 名称，展示为「PN 名称 PN 编码」 |
| 海外 | `RUser` | 问题跟进人 ID，如 `4535,4527` |
| 海外 | `MemberList` / `MemberListName` | 当前责任人 ID / 姓名 |
| 海外 | `DocId`、处理步骤 `DocID`、处理步骤 `MemberList` | 附件 ID、步骤成员 ID（内部字段，不展示） |

按段匹配时逐段去首尾空格后精确比较（`12` 不能命中 `112`），不能用整列模糊包含。

## JSON 列

| 域 | 列 | 处理 |
|---|---|---|
| 巴西 | `ProblemPhenomenon` | 问题现象；可能含非法转义，容错后解析；展平规则见巴西主表文件 |
| 海外 | `InvInfo` | 物料数组，逐条列出；规则见海外主表文件 |
| 海外 | `hasCheckedPhenomenon` | 已选现象数组，展平规则见海外主表文件 |

两域的现象展平规则不同：巴西手填现象为 `parentType->Value otherVal`；海外为 `parentType -> Value (otherVal)`。

## 文本存日期

| 域 | 列 |
|---|---|
| 巴西 | 主表停线日期、现场发现日期、统计日期；处理过程计划完成日期、设计更改评估时间 |
| 海外 | 主表现场发现日期、停线日期；发货单发货日期 |

格式统一为 `YYYY-MM-DD`。巴西这 5 列与海外这 3 列经业务方 2026-10-22 正式镜像计数，只有 `YYYY-MM-DD` 与空两种写法。展示用原值；筛选、排序、统计按 `YYYY-MM-DD` 解析成日期，空串或不符合该格式的值按空处理，不猜测填充。同表内文本日期与 datetime 列并存不算数据错误。

## 类型不一致

| 域 | 列 | 处理 |
|---|---|---|
| 国内 | `RUser`、`ReStartExamineUser`、`ReStartSchemeUser` | 文本型员工 ID，关联人员表时转整数，无效值按空。业务方 2026-10-22 正式镜像计数：三列都是单值，非空值全部能对上人员表 |
| 国内 | CAR 报告的检验总数、检查总数、不良数量、不良率 | 文本型（varchar），按原值展示，不参与计算 |
| 国内 | 流程待办任务 `frecID`、`fuserID` | 文本型：`frecID` 存问题单主表 ID，`fuserID` 存员工 ID；关联时转整数，无效值按空 |

## 其他

- 国内物料标识的「空」有 NULL 与空串两种，都按整机问题处理。
- 国内 CAR 编号与 CAR 报告 ID 总是同时有值或同时为空（业务方 2026-10-22 正式镜像计数）。
  - 非物料问题也有 20 张单在库里带 CAR。按源系统管理页面，这些单不展示 CAR、不计入关联 CAR 的单数。
  - 物料问题中有 1 张单的 CAR 报告 ID 在报告表里查不到。这张单照常显示 CAR 编号、生成链接、计入关联数；有 CAR 报告权限的用户问报告内容时，说明该单登记的 CAR 报告查不到内容。
- 结案时间（业务方 2026-10-21 正式镜像计数）：
  - 国内已完成 2,307 张中 21 张没有「结案确认」记录（最后一条步骤多为效果确认），海外已完成 11 张中 1 张没有。这些单定不出结案时间，按结案时间筛选、统计结案周期时不计入，写明张数。
  - 国内另有 195 张单在结案确认之后还有停线重启步骤，结案时间仍取最后一条结案确认的时间。
  - 巴西已结案的单结案日期都有值。
- 停线与重启时间（业务方 2026-10-22 正式镜像计数）：
  - 停线日期三域都齐：国内停过线的 488 张、海外 6 张、巴西 9 张都有。
  - 主表停线重启时间基本没有填：国内已经重启的 480 张单只有 1 张有值，海外已经重启的 6 张都为空；巴西没有这一列。
  - 国内这 480 张单都有「停线重启」这一步。这一步登记的日期就是管理页面详情里的「重启日期」，本助手的重启时间也取它。只有 96 张有「重启审核通过」那一步，重启流程前后不一。
  - 停线重启这一步登记的日期多数早于这一步的发生时间（484 条里 413 条），是事后补登的实际重启日。按重启时间筛用登记的日期，不用发生时间。
- 国内处理结果（业务方 2026-10-22 正式镜像计数，未删除的单）：
  - 跟进人确认为「是」、处理结果却为空的单 13 张（硬件问题 7 张、软件问题 6 张）。管理页面这一项显示为空，本助手写「未填」。
  - 改过问题类型的单，处理结果可能来自改前的环节：物料问题里 5 张单有处理结果、却没有设计变更，结果应是改类型前在责任人确认时填的；资料问题、软件问题、结构问题、制程优化、工厂制程各有 1 张单的处理结果不是本类型对应环节填的。展示时跟着环节走（见国内主表处理结果字段说明）。
- 国内产品在制属性有 3 张未删除的单取值不在管理页面的显示清单里（194 两张、0 一张，业务方 2026-10-23 正式镜像计数）。页面上为空，本助手写「未填」。
- 国内有 5 张未删除的单带「删除问题」处理步骤（2024-08 至 2026-10）。这些单仍在管理页面上，照常查询，完整处理过程里照常列出这一步。
- 巴西 `IsCost = 0` 为删除状态的测试数据，按无效值处理；按是否涉及费用筛选只看 1、2。正式镜像里未删除的单目前没有 0。
- 巴西「是否涉及费用」标记与费用明细个别对不上（业务方 2026-10-22 正式镜像计数，未删除 203 张单）：标「是」的 184 张中 1 张明细合计为 0；标「否」的 19 张中 1 张有费用明细。所以「涉及费用的单」按费用明细认定，不按标记（目前 184 张）。目前没有只有雷亚尔、没有美元明细的单，规则照旧保留。
- 巴西费用明细多为 0 金额占位行，0 金额行上汇率常为 0。
- 巴西同一单的多条关联申请单解析出的 PN 一般相同，但不能排除不同，合并为 PN 列表。
- PN（业务方 2026-10-22 正式镜像计数）：三域 PN 编码都是同一套。
  - 国内生产订单、海外主表与发货单上的 PN 编码都是 15 位数字，全部能对上 PN 主数据；海外发货单上的 PN 都等于本单主表某段 PN。
  - 国内生产订单的 PN 名称有 13 条不是标准的连字符型号码写法（含手填说明文字），按原值展示。
  - 巴西未删除单关联的 307 条申请单中，255 条 PN 编码是 15 位数字、都能对上 PN 主数据；另 52 条（43 张单）PN 编码是「0」，是没选 PN 时的占位值。这 43 张单里 29 张另有 15 位的 PN，14 张单上只有 0。与管理页面一致，0 不展示、不参与按 PN 查，只有 0 的单 PN 显示「未填」（规则见巴西业务描述「大机型与 PN」）。
- 海外不良率为文本，`%` 与 `‰` 混用（`30%`、`6.6667‰`、`0.1‰`），展示按原文；需要比较大小时先统一单位。
- 问题等级的空值有 NULL 与空串两种，都按「未填」处理（业务方 2026-10-22 正式镜像计数）：国内 1,207 张为 NULL，都是 2024-04-17 之前建的单，此后的单都有等级；巴西 14 张为空串；海外目前都有值。三域的值目前只有 A、B、C 三种写法，没有 A+，也没有大小写、空格等变体。
- 国内、巴西供应商编号为空时都不与供应商表关联（避免空串命中空编码的供应商）。
- 显示「未填」、不报错的情形：国内供应商、责任归属部门、CAR 关联不上；巴西供应商关联不上，大机型、发现工位、投诉单号为空（大机型有值但对不上时按上文多值列规则显示「未识别机型」）；海外问题跟进部门、问题跟进人为空，大机型为空，国内工厂关联不上（大机型有值但对不上时同巴西，显示「未识别机型」）。三域 PN 编码对不上 PN 主数据时都只给编码，不写「未填」（巴西 PN 编码为 0 的除外，见上文 PN 一条）。
- 软删：国内看是否删除；巴西看状态 -1；海外看是否删除；文档看删除标志。子表都没有独立删除标记，随主表。
