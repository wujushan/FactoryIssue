# 国内制程问题 业务描述

> 字段定义见 `db_description/`；三域共用口径见上级 `business_description.md`。

## 业务域

围绕国内制程问题主表（CoreINFO.dbo.ZCTracking_ProblemList），查询国内工厂制程质量问题的发现、分类、跟进、责任归属、停线、改善与结案。一张单在主表占一行，单号 `ZC` 开头。

**非核心场景**：退货（在线 / 在库退货单号、其他在线订单的处理方式）与版本修订（版本、是否更改订单版本、修订的订单版本）不做专项口径，问到时按单上原值回答。

## 查询范围

- 默认只查未删除单（是否删除为 0 或空）。用户明确要求「已删除的」才列出已删除单。子表没有删除标记，随主表。
- 本域用 13 张表：主表、机型、处理步骤、生产订单、小板订单、其他在线订单 6 张业务表，加国内工厂、存货档案、供应商、CAR 报告、部门、人员、文档清单 7 张主数据表。

## 口径

### 时间

| 用户说法 | 口径 |
|---|---|
| 给出时间、没说现场发现 | 按建单时间筛 |
| 现场发现、发现日期 | 按现场发现日期筛 |

### 问题类型

硬件问题、软件问题、物料问题、资料问题、工厂制程、结构问题、制程优化。修改过类型的单，问题类型是当前类型，原问题类型保留修改前的值。

### 状态与生命周期

- 主表状态是当前所处环节的快照（18 个取值见主表文件）；处理步骤表是每次流转的留痕。问「进行到哪了」看主表状态，问「完整处理过程」看处理步骤表全部记录。
- 不同问题类型走不同路径，可能被驳回到前序环节后再推进，不能只凭当前状态推断全程。
- 结案完成只有「已完成」。「结案确认」仍算未结案。未结案、进行中、没完成 = 状态不是「已完成」。

### 停线

| 用户说法 | 口径 |
|---|---|
| 停线中、目前停线、正在停线 | 停线状态为停线中、重启审核、审核通过、填写重启方案四者之一。不含已经重启、没有停线。统计口径说明里写明含这几个子状态 |
| 停线、曾经停线、发生过停线（没带「中 / 目前 / 正在」） | 是否停线为「是」，已经重启的仍算 |

停线相关还有停线日期、停线重启时间、重启方案、重启审核人、重启方案制定人。

### 人员与部门

| 用户说法 | 口径 |
|---|---|
| 某部门跟进的、问题跟进部门；只说部门（「品质部的问题」） | 问题跟进部门 |
| 某人跟进的、问题跟进人；只说人名（「张三的问题」） | 问题跟进人 |
| 某部门处理的、某部门负责的、某部门人员处理的 | 同样按问题跟进部门。物料问题、工厂制程、资料问题不指定跟进部门，统计不到；统计口径说明里写明这三类未计入 |
| 当前谁在处理、当前处理人 | 当前处理人（随最新处理节点变化） |
| 责任部门、定责、责任归属 | 结案后的责任归属部门（可多个），不是问题跟进部门；为空表示无需定责。两者可能相同也可能不同 |
| 问题责任人 | 制程问题一般不定责到个人，没有与问题跟进人同义的「问题责任人」。问当前谁在处理，看当前处理人 |

**问题跟进人按问题类型分两种**：

- 硬件、软件、结构问题、制程优化：提交后由固定负责人指定**一名**跟进人，问题跟进人、问题跟进部门有值。
- 物料问题、工厂制程、资料问题：提交后按类型流转到固定处理角色，**不指定**问题跟进人，两列为空；工厂制程默认流转到工厂的三个接口人。

其他人员：填单人、效果确认人、生产确认人、设计变更责任人、IQC 成员、重启审核人、重启方案制定人。

### 物料标识与关联订单

| 物料标识 | 含义 | 看哪些订单 |
|---|---|---|
| 空（NULL 或空串） | 整机问题 | 关联生产订单 |
| 物料 | 磁头、面壳组件等有独立 BOM 的中间产物出的问题 | 小板订单 |

其他在线订单不分物料标识，整机单与「物料」单都可能有，有就展示。

产品在制属性表示该单关联的那次生产处于哪个阶段（首次量产、量产爬坡、物料试产、工程样机等）。

### 数量与不良率

| 字段 | 口径 |
|---|---|
| 不良率 | 不良数量 ÷ 生产数量，单上已存百分数，展示加「%」（46.4 → 46.4%） |
| 影响数量 | 整机问题中，受影响的关联生产订单的订单数量之和 |

### 物料问题专属

- **CAR**：只有物料问题可关联 CAR（纠正预防措施报告），取问题点、围堵对策、根本原因、永久纠正措施、预防措施、有效性确认。
- **设计变更**：只对物料问题有意义；是否设计变更为「是」时才有设计变更责任人、确认结果、预计完成时间。
- **IQC**：IQC 意见（退回仓库 / 继续使用）、IQC 状态、IQC 成员。

资料问题另有资料问题确认结果。

### 原因

- 原因分析：问题发生原因的叙述。
- 原因分类：结案时人为归类，从自维护的原因列表中选取，是有限集合（如「人为工作疏忽」），可做分类统计；原因分类说明是补充。

### 叙述文字

问题描述、原因分析、改善建议、改善措施、预防对策、效果确认、生产确认备注、备注、原因分类说明、重启方案，以及处理步骤的意见、措施、结论，都是人填写的自由文字，是理解「发生了什么、怎么处理的」的主要依据。用户提到某类现象或做法（「外壳开裂」「磁头有异响」「改善措施里提到换料」）时指向这些文字。它们用于理解案情、核对细节，不按固定档位计数或分组。格式见 `dirty_data.md`「富文本」。

发现工位也是自由文本（约 425 种写法），不能当枚举精确筛选。

### 处理步骤

- 完整处理过程：该单全部步骤，按先后顺序给出环节名称、处理人、意见、措施、结论、发生时间。
- 某环节最新一次：同一环节名称只取最新一条（`ID` 最大）。
- 责任人处理结果：取工程确认环节最新一条措施中「处理结果：」之后的文字。
- 步骤附件：附件 ID 可能逗号多值，逐段对应文档；以文档名称打开预览；已删除文档不展示。

## 关联

| 看什么 | 怎么关联 |
|---|---|
| 机型、系列 | `ZCTracking_ProductNames.ProblemId = 主表.ID`，一张单可多机型 |
| 整机生产订单 | 主表物料标识为空时，`ZCTracking_ProblemOrders.ProblemId = 主表.ID` |
| 小板订单 | 主表物料标识为「物料」时，`ZCTracking_XBOrders.ProblemId = 主表.ID`；小板订单工厂按名称对 `PaxFactory.FactoryName`，料号对 `Inventory.cInvCode` |
| 其他在线订单 | 不分物料标识，`ZCTracking_OtherOrder.ProblemId = 主表.ID`；工厂按工厂码对 `PaxFactory.FactoryID` |
| 处理步骤 | `ZCTracking_ProblemSteplog.ProblemId = 主表.ID` |
| 加工厂 | `Factory = PaxFactory.FactoryID` → `FactoryName`；按名称筛时先把名称解析为工厂码。国内工厂表在 ERP 实例，与问题单不在同一实例 |
| 物料 | `CInvCode = Inventory.cInvCode` → 物料名称、规格型号 |
| 供应商 | `VenCode = tbIQCvendor.ferpcode` → 供应商名称 |
| CAR | 物料问题时 `CARID = tbIQCreportOut.fid` |
| 人员 | 各人员 ID 列 `= Employee.ID` → 姓名；文本型的问题跟进人、重启审核人、重启方案制定人需转整数；当前处理人直接用姓名列 |
| 部门 | `RDepartment = Department.ID`；`AllReDepartment` 各段 `= Department.ID` |
| 步骤附件 | `ZCTracking_ProblemSteplog.FileUrl` 各段 `= DocumentList.ID`，且 `EffectFlag = 0` |
| 制程单链接 | 见 `link_rules.md` |

可空关联（供应商、责任归属部门、CAR 等）关联不上时显示「未填」，不报错。

## 常见查询示例

1. 2024 年 Q3 某加工厂 A 类硬件问题有哪些？
2. 单号 ZC2109001 的完整处理过程和当前处理人是谁？
3. 目前停线中的物料问题，涉及哪些订单？
4. 某机型系列在首次量产阶段的不良率趋势？
5. 责任部门为某部门且尚未结案的问题列表？
6. 含 CAR 报告的物料问题及纠正措施内容？
7. 2026 年 1 月由生产工程部负责跟进处理的制程问题单有哪些，列出单号、处理人、问题类型、机型、不良数量、不良率
8. 工程部人员 2026 年第一季度处理的制程问题统计
9. 加工厂为惠州百富的机型名称有哪些？
10. 最近一年的制程问题中，是否有涉及音频（包括喇叭和蜂鸣器）的内容？
11. 最近 14 天出现的制程相关问题有哪些？
12. 搜索所有制程问题中有「打印」和「USB」描述的问题
13. L1400 机器的制程问题中是否有与音频相关的？
