# docs/2_landed —— 落盘产物（业务口径唯一信源，G1 产物，**仅编程助手可编辑**）

已落地的数据描述、业务规则、指标口径、表关联的 Single Source of Truth——业务逻辑与代码的**唯一信源**。
实现代码与本目录冲突时**以本目录为准**（或先修订本目录再改代码，并在 `docs/decisions/` 记录）。

> **编辑权限**：本目录**仅编程助手可编辑**。开发者不直接改本目录，需修订则向编程助手提出，由助手改这里。
> 更新有两条通道，结果一样都是改本目录：
> 1. **直接交代**（内容简单直白）：开发者在对话里说明，编程助手直接改。
> 2. **投递梳理**（内容较复杂）：开发者把材料放进 `docs/1_user_input/<子目录>/`（临时投递区，不是信源），
>    编程助手梳理、把歧义列进 `docs/open-questions.md` 确认后落盘（可直接复制素材再编辑，或另建新文档）。

## 输出文档清单

| 文件 | 必须/可选 | 内容 |
|---|---|---|
| `db_description/db_[database]_[schema]_[table].md` | **必须** | 原始数据的库/表/字段详细描述，**一表一文件**（多表则多文件；同构分库/动态分表按**表族**只写一个文件，规则见 `db_description/README.md`）；每张表**必填 `source`（所属实例/数据源别名，原始表只能是 info/erp）**——模块源数据可横跨两实例（INFO+ERP），别名并集须与 `manifest.data_sources` 一致（G1 guard 硬拦缺 source）。`forge_mart_<code>` 是 G2 治理/向量产物库，不作原始表 source |
| `business_description.md` | **必须** | 库/表/字段在业务场景中的关联关系、用户关注的查询场景、常见查询示例；须**明确声明数据量**（涉及多少张表、每张表约多少行——G2 治理决策与取数/沙箱策略据此判断） |
| `dirty_data.md` | 可选（存在脏数据时） | 历史遗留/不规则/需特殊解析处理的数据描述 |
| `privileges.md` | 可选（有权限管控要求时） | 本业务需要的行级/列级权限管控机制描述 |
| `glossary.md` | 可选（有业务术语时） | 业务术语表，一行一术语：**规范词 / 别称 / 口径定义**（对应 `GlossaryTerm` 的 term/aliases/definition），供线上助手做术语理解与归一。**是 `manifest.glossary` 的唯一信源**，改此文件须同步 manifest（`module.py` 已留槽位）——沿用 `db_description ↔ field_mappings` 的「文档信源 + manifest 机器读」范式。有业务术语时才新建（缺省不建，不占 G1 闸门） |

## 本模块的文件布局

本模块分国内、巴西、海外三个域，`business_description` 按「总述 + 各域」拆开：

| 文件 | 内容 |
|---|---|
| `business_description.md` | 总述：定位、三域边界、跨域规则、共用说法、常用场景、澄清项、分析维度、数据量声明 |
| `domestic/business_description.md` | 国内口径与表关联 |
| `brazil/business_description.md` | 巴西口径与表关联 |
| `overseas/business_description.md` | 海外口径与表关联 |
| `link_rules.md` | 制程单跳转链接、附件预览链接的生成规则 |
| `db_description/` | 27 张表的字段说明（三域共用的基础表只写一份） |
| `dirty_data.md` / `glossary.md` / `privileges.md` | 脏数据与特殊解析 / 术语表 / 权限管控 |

## 原则

- **自包含、不外引**：不得以 `docs/1_user_input/`、未入库的本机参考目录（如某些仓的 `references/`）或其他目录的文档作为信源或出处——**链接与纯文本提及都不行**，表文件也不写「出处」段。有用的信息（字段定义、口径算式、需要逐字遵循的原文，例如本地模型提示词原文）必须**复制落盘**进本目录；复制的是口径、结构与原文，**不复制真实业务数据行**（本目录入库并随 wheel 分发）。日后发现信息有误**直接改本目录**，不回溯原始素材。素材来源需要说明时用文字描述（如「业务方 2026-10-10 书面答复」），不写路径。
- **决策只作依据标注，且以最新结论为准**：`docs/decisions/` 是决策过程与变化历史，可作信源之一，本目录可用纯文本「决策 YYYY-MM-DD」标注依据——**不写成链接**（本目录打进 wheel，`../decisions/` 在平台 Console 里是死链）。决策更新后本目录须及时同步为**最新结论**与原文。
- **只留结论、不留过程**：本目录落盘的是可直接作为口径信源的**最终业务结论**。梳理或后续修正业务逻辑时产生的中间过程——语义修正的来龙去脉、澄清问答、讨论推演、被推翻的旧口径——一律**不入本目录**（原始输入只在梳理期间放在 `1_user_input/`、梳理完成后不再引用；需留痕的决策与推翻理由留 `docs/decisions/`）。修订时直接改写为新结论，不在正文堆叠"原来是…后来改成…"的过程叙述。
- **业务梳理阶段（G1）不做任何技术决策**，只梳理数据字段、业务逻辑；技术选型留到 G2 及之后并落 `decisions/`。
- **持续维护**：仓库升级过程中涉及需落盘的业务信息，必须及时更新本目录对应文件。
