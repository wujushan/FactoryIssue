# ZCTracking_ProblemSteplog（国内制程问题处理步骤）

- **数据源别名（source）**：info
- **物理表名（table）**：CoreINFO.dbo.ZCTracking_ProblemSteplog
- **所属域**：国内
- **用途**：问题单每次节点流转的历史留痕，记录每个环节的处理人、结论、意见、措施与附件。主表 `Status` 是当前状态快照，本表是走过的路径。
- **数据产生方**：INFO 系统制程问题流转时写入。
- **列类型**：按 information_schema（业务方 2026-10-20 内网元数据），字符串长度为声明的字符数。

## 两种读法

| 用户要什么 | 怎么取 |
|---|---|
| 完整处理过程、谁处理过哪些步骤 | 每个环节编码只保留 `ID` 最大的一条，再按 `ID` 升序排（同 `AddDate` 顺序） |
| 某一环节最新一次的结果 | 同一 `ProblemId` + 同一环节编码只保留 `ID` 最大的一条 |

同一环节会多次出现（如驳回后再次「IQC填写意见」，多次任务转移、多次驳回），两种读法都只给每个环节最新的一条，驳回前的旧记录不给（业务方 2026-10-22 答复）。一个编码有两个名称的（见下文「环节编码与名称」）按同一个环节算，名称取保留下来的那一条上的。

按文字找单时只比对分析类环节、每个环节最新一条的意见与措施（工厂制程分析另含结论），环节清单见总述「比对范围」。

## 处理过程怎么展示

照管理页面「操作记录」，给 5 列（决策 2026-10-22「国内管理页面代码对齐」补记「G30 结论」）：

| 列 | 取什么 |
|---|---|
| 操作人 | 做这一步的人，翻成姓名 |
| 操作时间 | 这一步的时间 |
| 类型 | 环节名称 |
| 内容 | 措施列；为空时取意见 |
| 附件 | 以文档名称展示，已删除的不展示 |

- 结论、意见不单列：内容本身已把代码、员工编号、日期写成文字。
- 停线重启（29）、停线重启审核（32，含改名前的「停线重启发起」）、责任人填写重启方案（34）三步不进处理过程，与管理页面一致：页面的操作记录主表把这三步排除，详情页把它们放在停线部分，显示为重启日期、重启备注、重启方案、重启审核意见（见国内业务描述「停线」）。
- 每个环节只留最新一条（见上文「两种读法」）。

## 单张单详情里的结论

单张单详情按环节给（哪些环节显示见国内业务描述「单张单详情各环节怎么显示」），结论与意见按管理页面的标签翻译：

| 环节 | 结论存什么 | 怎么展示 |
|---|---|---|
| 工厂制程分析 | 文字 | 结论显示为「原因分析」，意见显示为「制定对策」 |
| SQE跟进 | 0 / 1 | 「是否设计更改」：0 = 不需要，1 = 需要（需要时附设计变更责任人）。意见显示为「SQE跟进结果」 |
| 设计变更 | 1 / 2 / 3 | 不用结论，显示主表处理结果，叫「确认结果」：改善 / 保持现状 / 挂起；改善时附预计完成时间。意见显示为「原因说明」 |
| 生产角色确认 | 0 / 1 | 「确认结果」：0 = 不同意，其余 = 同意。意见显示为「备注」 |
| 停线重启审核 | 0 / 1 | 放在停线部分的「重启审核意见」：1 = 同意，0 = 不同意，其他值显示为空；附意见、审核人、审核时间。什么时候显示见国内业务描述「停线」 |
| 停线重启 | 日期 | 放在停线部分：结论取日期部分显示为「重启日期」，意见显示为「重启备注」。按重启时间筛、算停线时长都用这个日期（G44） |
| 责任人填写重启方案 | 空 | 放在停线部分：意见显示为「重启方案」，附制定人与填写时间 |
| 任务转移 | 员工 ID | 不展示结论，内容里已写「将任务转移给某某」 |
| 停线重启发起 | 日期 | 「停线重启审核」改名前的旧记录，只有 1 条；作为重启审核意见时结论不是 0 / 1，审核结果显示为空 |
| 其余环节 | 空 | — |

「责任人处理结果」不从本表取，取主表 `DesignConfirmResult`，与管理页面一致（见主表字段说明）。

## 派生：责任人

按主表问题类型取对应环节编码最新一条记录（`AddDate` 最晚，同时间取 `ID` 大的）的 `AddUser`，翻成姓名，显示名「责任人」：
- 问题类型 1、2、6、7 → 编码 3；
- 问题类型 3 → 编码 10；
- 问题类型 4 → 编码 4；
- 问题类型 5 → 编码 6。

本单有「修改问题分类」步骤、且在最后一条编码 31 之后时，改用主表 `OldProblemType`。规则说明见国内业务描述「责任人怎么取」（D25）。

## 派生：结案时间

只对主表状态为「已完成」的单定：取该单环节编码为 31（结案确认）、`ID` 最大的一条记录的 `AddDate`，显示名「结案时间」。按编码认、不按名称认，与管理页面一致（业务方 2026-10-22 同意 D23）。没有这样的记录时定不出结案时间，按结案时间筛选、统计时不计入（见总述「结案时间与结案周期」）。

结案确认之后还可能有停线重启步骤，所以不能拿该单最后一条步骤的时间当结案时间。个别已完成的单没有「结案确认」记录（见 `dirty_data.md`「其他」）。
