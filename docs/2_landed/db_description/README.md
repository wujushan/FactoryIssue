# docs/2_landed/db_description —— 原始数据字段权威源

涉及的 database/schema/table 清单与字段详细描述。查表结构/连接键先读这里，**勿凭字段名臆测**。
必须与 `information_schema` 机器对账（对账脚本产出的差异需归零或说明）。

## 文件规则

- **一表一文件**（多个表则多个 md）；**同构的一族表只写一个文件**，见下方「表族」。
- 文件名格式：`db_[database-name]_[schema-name]_[table-name].md`
  （示例：`db_factory_dbo_ProcessIssue.md`）。
- **物理表名**写成一行显式声明（推荐每张表都写；**库名/schema 含下划线时必写**）：
  `- **物理表名（table）**：UFDATA_999_2021.dbo.mom_order`。SQL Server 写三段 `库.schema.表`，
  MySQL 写 `库.表`，PG 写 `schema.表`。`forge data check` 优先按这一行定位表；没有这一行才从文件名拆，
  而文件名拆不准带下划线的库名（`UFDATA_999_2021` 这种只能靠 `dbo` 段猜边界）。

## 表族（同构分库 / 动态分表）

有些表按某个维度**复制出很多份、结构完全相同**：按年份分库（`UFDATA_111_2005` … `UFDATA_999_2021`
里各有一张 `mom_order`）、按产品动态建表（`POS.dbo.POSSN_<pid>`）。这种情况**不做乘法**——一族只写
**一个**文件：

- 文件名用**代表成员**（一张确实存在的成员表，通常取最新/最常用的那张），如
  `db_UFDATA_999_2021_dbo_mom_order.md`、`db_POS_dbo_POSSN_12.md`。
- 文件内除 `source` 外再写两行：
  - `- **物理表名（table）**：<代表成员的完整物理名>`——`forge data check` 校验的就是它；
  - `- **表族（family）**：<成员命名规则与范围>`，例如
    `UFDATA_111_<2005–2012>.dbo.mom_order、UFDATA_999_<2013–2021>.dbo.mom_order（2022 起数据并入 UFDATA_999_2021）`、
    `POS.dbo.POSSN_<pid>（pid = 产品库 id，取自 …）`。
- 字段清单描述**全族共同的结构**。若个别成员有差异（老年份库缺某列、类型不同），在「成员差异」小节逐条写明
  ——代码会拿同一套列去查每个成员，差异不写就是一个只在查老数据时才炸的坑。
- 成员怎么选（哪一年落哪个库、pid 从哪来）是**业务逻辑**，写进 `business_description.md`，本文件只管结构。
- `forge data check` **只校验代表成员**，报告里会标出 `family`，不代表整族都验过。
- `manifest.data_sources[].tables` 仍按物理表逐个声明：`fetch()` 的多表 JOIN 只认声明过的具体表
  （可连接表图的边端必须是某一张真实的表），表族约定只管文档与 G1 冒烟，不改变这条。

## 每个表文件建议内容

- **数据源别名（source）**：**必填**——该表所属的实例/库，对应平台数据源别名。G1 原始表的 source
  **只能是 `info` / `erp`**（原始结构化取数一律直连 info/erp 只读热备副本）。写成一行显式标注：
  `- **数据源别名（source）**：info`。**一个模块的源数据可能横跨两实例**（如物料助手 = INFO + ERP），
  故每张表都要各自声明所属源。这些别名的并集须与 `manifest.data_sources` 一致（G4 编码时对齐）。
  G1 guard 会硬拦缺 source 的表文件。
  （`forge_mart_<code>` 是 G2 治理/向量化的**产物库**，不是 G1 原始数据源，不写在原始表的 source 上。）
- **物理表名（table）**：紧跟 source 写一行 `- **物理表名（table）**：库.schema.表`（见上方「文件规则」）；
  表族文件再加一行 `- **表族（family）**：…`（见「表族」）。
- 库/schema/表名、用途简述、数据产生方（哪个业务系统写入）与更新频率。
  **不写文档「出处」段**：字段定义、口径从哪份数据字典 / 需求文档整理而来不必交代——有用的内容直接写进本文件，
  本文件自身就是信源（见 `../README.md`「自包含、不外引」）。
- 字段清单：字段名、类型、**用户可见显示名**、含义、是否可空、枚举取值、与其它表的连接键。
  - **「用户可见显示名」是必填项**，因为**回给用户的内容里绝不许出现字段名/表名**
    （见 `docs/dev/09-answer-presentation.md`）——显示名就是替换它的那个词，必须有个唯一信源。
    没有的话每处即兴翻译，同一列这轮叫「延期天数」下轮叫「拖期时长」，用户会以为是两个指标。
  - **不该给用户看的列照实标注**：自增 ID / 代理主键 / 软删标记 / 审计列 / 纯连接键写明
    「内部字段，不返回给用户」（它们仍可能要 `select`——取数集 ⊃ 展示集）。
  - **枚举取值要连人话一起记**（`stage_code`：1=立项 / 2=试产 / 3=量产），回答里只出现人话那侧。
- 权限相关字段（若涉及行/列级管控）标注，并在 `../privileges.md` 展开机制。

> 是否需要治理/向量化（是否建 `forge_mart_<code>` 产物库）是 **G2 决策**（据是否需治理向量化判断，落 `docs/decisions/`）；
> G1 只如实记录原始表当前所属实例（info/erp）即可，不做技术选型。
