# 09 · 答案呈现规范（回给用户的东西长什么样）

取数取对了**不等于**答对了。用户看不到你的 `SELECT`、看不到 DataFrame，只看到你 `yield` 出去的
那些 `table` / `chart` / `delta`。这一章定的就是**那一层**的规范：哪些内容不许出现、哪些必须出现。

> **与红线的区别**：红线（权限、沙箱算数、本地模型）越线会被框架**拒掉**；本章各条越线**不会报错**
> ——它直接变成用户看到的东西。所以没人替你兜，写 `handle()` 时逐条对照。
>
> **给 AI 编程助手**：本章是**行为规范**，与 02/04 的 API 契约同等约束力。产出任何回给用户的
> 事件之前先过一遍下面的自检清单，别等人来 review 才发现列名是 `prj_dly_days`。

## 一、只把对用户有意义的东西返回

**取到 ≠ 返回。** 取数集通常**大于**展示集：权限承载列（`dept_id`）、连接键、算延期要用的
`plan_end`/`actual_end`，它们是给权限与沙箱用的，不是给人看的。

> ⚠️ **本文只管「回给用户的东西」**（`Event.*` 与正文），**不管 `ctx.bus.invoke` 的返回**。
> 结构化能力调用是面向机器的通道，那边的要求正好相反：**连接键必须在、类型必须明确、
> 截断必须显式告知**（决策 2026-09-10）。同一份底层取数逻辑两处复用是常态，但**产物形态
> 不该复用**——把本文的裁剪规范套到 `CapabilityResult` 上，调用方做跨域关联时第一步就没有键。
> 见 [02 · 结构化能力调用](02-sdk-reference.md)。

不许出现在回给用户的内容里：

| 不返回 | 为什么 |
|---|---|
| 自增 ID / 代理主键 / GUID / hash 外键 | 对用户零信息量，还会被当成业务编号拿去别处查 |
| 内部状态码、软删标记、建表冗余列、审计列（`created_by`/`row_version`） | 同上；状态码要给就给**状态名** |
| 权限承载列、连接键（除非它本身就是用户关心的业务字段） | 它们进来是为了过滤/关联 |
| `None` / `NaN` / `1970-01-01` / `-1` 这类占位值 | 写「未填」「未开始」，别把内部哨兵值倒给用户 |

必须出现的反面：**业务标识要给全**。工单号、料号、项目编号、机型这类用户认得、能拿去别处查的
标识是答案的一部分，别一并砍掉——「砍掉无意义字段」不是「砍到只剩名称」。

**序号不是主键**：用户要「第几条」，就在**展示层现生成** 1..N（沙箱产物里加一列，或直接作为表格
第一列），不要拿自增 id 冒充序号。这条常被误解成「不能有序号列」——序号照给，只是它跟数据库无关。

枚举/代码值一律翻成人话（`stage_code=3` → 「量产」），口径以
`docs/2_landed/db_description/` 与 `glossary.md` 为准，别就地编一套。

**结果太多时，展示给摘要、全量给文件**（不是二选一，是两件事各就各位）：几百上千条塞进
`table` 事件，用户在对话框里既翻不动也看不出结论。做法是**表格只放前 N 条 + 你的分析结论，
全量走 `ctx.files` 生成 Excel，把链接嵌进正文**：

```python
df = ctx.data.fetch(spec)                                   # 1000 条（取数是同步的，别 await）
yield Event.table(columns, rows[:20], title="按延期天数排序（前 20 项）")
ref = await ctx.files.save_dataframe(df, "延期项目明细.xlsx")
yield Event.delta(f"\n\n完整 {len(df)} 项见 {ref.markdown}（链接 24 小时内有效）")
```

导出文件里的**列名同样要过本章第二节那关**——它和表格一样是给用户看的东西，`dept_id` 出现在
Excel 表头里和出现在对话框里是同一个问题。反过来，导出**可以**比展示多给几列（明细文件本
就是拿去自己筛的），但那几列也得是业务语言。用法见
[02 · 文件导出](02-sdk-reference.md#文件导出-forge_corefilesctxfiles-出站)。

**几十万行以上**（单次取数上限、单轮预算都装不下）改用**后台导出任务**：`handle()` 里
`ref = await ctx.files.submit_export(...)` 立刻拿到链接嵌进正文——说清「数据量较大，已在后台
导出，打开链接后生成完成会自动下载」，别让用户以为链接坏了。用法见
[02 · 后台导出任务](02-sdk-reference.md#后台导出任务ctxfilessubmit_export大批量明细)。

## 二、任何情况下不许把表名、字段名甩给用户

表格列名、正文、图表轴标签、错误提示——**一律业务语言**：

```python
# ✗ 用户看到的是数据库内部标识符
yield Event.table(columns=["prj_no", "prj_dly_days", "stage_code"], rows=rows)
yield Event.delta("t_prj_main 里 delay_days > 30 的有 12 条")

# ✓ 用户看得懂的话
yield Event.table(columns=["项目编号", "延期天数", "所处阶段"], rows=rows, title="延期项目清单")
yield Event.delta("延期超过 30 天的项目有 12 个。")
```

同样不许露出去的还有：数据源别名（`info`/`erp`/`forge_mart_xxx`）、向量表名、SQL 片段、沙箱脚本、
内部异常与堆栈。**用户不需要知道数据存在哪张表里。**

**显示名要有唯一信源**：每个字段的「用户可见显示名」记在
`docs/2_landed/db_description/db_[database]_[schema]_[table].md` 的字段清单里（G1 落盘），
业务术语记在 `glossary.md`。别每处即兴翻译——同一列这轮叫「延期天数」、下轮叫「拖期时长」，
用户会以为是两个不同指标。

**错误提示也是回给用户的答案**：`Event.error(code, message)` 的 `message` 用业务语言
（「这批数据里没有 2026 年的记录」），技术细节留给日志与归档（平台每轮自动落
`runtime/audit/…`）。平台只会把**上游异常**脱敏成 safe_message，**你自己写的 message 它不会
替你翻译**。

> 唯一的例外：用户**自己**用业务术语提到的词（术语表里的那些）当然可以照用——那是业务词汇，
> 不是数据库标识符。

## 三、给了数据，还要给分析

**默认要分析。** 用户问「延期的项目有哪些」，只丢一张 37 行的表回去，等于把「所以呢」全推给他
自己算——这正是要避免的那种苍白冰冷的回答。

一个合格的答案大致是：

1. **精确的目标数据**（该给的列表/明细，一行不多一行不少）——这是底座，分析不能替代它；
2. **总量**（共 37 个）；
3. **分档/分组**：按延期时长分档（≤7 天 / 8–30 天 / >30 天）、按部门或机型分布；
4. **重点**：延期最严重的 Top N（点名，带天数）——「需要关注哪几个」是用户真正要的；
5. **一句结论**：集中在哪个阶段/部门，或建议先看哪一批。

**具体分析什么由上下文决定**，没有一张万能清单——本域该看哪些维度是 **G1 采集的产物**，落在
`manifest.analysis_dimensions`（平台的 `domain_prompt_section` 会把它注入 system 提示，
见 [03](03-events-and-streaming.md) / [07](07-capability-profiles.md)）。**别把维度硬编码进
提示串**：那样换个问法就失效，也没法随业务演进。

硬约束：

- **数字全部走 `ctx.stats` 沙箱**（红线）。分档、计数、排序、Top N 都是数字——不许在 `handle()`
  里用 pandas 直算，更不许让 LLM 心算。`Event.chart` 里的每个数都必须来自 `outcome.result`。
- **不许为了「有分析」而编**：只依据取到的数据说话，缺的数据就说缺（平台 policy 已焊死这条，
  但提示里别引诱它推测）。
- **分析文字走 `delta` 流式**（边生成边发），表格/图表走一等事件，正文里不再抄一遍那张表
  （见 [03](03-events-and-streaming.md#表格与图表产出事件别再往正文里抄一遍)）。

**什么时候别分析**（分析是默认，不是强制）：

- 用户明确说「只要列表 / 只给我数据 / 不用分析 / 我自己看 / 导出」——照办，别硬塞；
- 结果只有一两行（分析就成了复述）；
- 用户在追问某一条记录的细节（这时他要的是那条记录，不是全局分布）。

## 四、放在一起看：一个「延期项目」的形状

```python
from forge_core.dataquery import QuerySpec

async def handle(self, request: ModuleRequest, ctx: ModuleContext) -> AsyncIterator[Event]:
    yield Event.progress("fetch", "正在查延期项目")
    # 取数集 ⊃ 展示集：dept_id 是权限承载列，plan_end/actual_end 供沙箱算延期天数，
    # 三者都不会出现在回给用户的表里；主键 id 压根没取
    df = ctx.data.fetch(QuerySpec.model_validate({
        "source": "erp",
        "from": "ERPDB.dbo.PrjMain",
        "select": ["prj_no", "prj_name", "owner_name", "dept_id", "stage_code",
                   "plan_end", "actual_end"],
        # 跨列比较用 {"$column": ...}：被引用的 plan_end 同样过列级白名单。
        # 写成裸 where="actual_end > plan_end" 也能跑，但那串不过白名单——见 04。
        "filter": {"groups": [{"conditions": [
            {"field": "actual_end", "operator": "GT", "value": {"$column": "plan_end"}},
        ]}]},
    }))

    # 一切数字在沙箱里算：延期天数、分档、Top N、各档计数（脚本可由 LLM 生成）。
    # 脚本回 {"rows": 分档统计, "detail": 明细行, "summary": {...}}——`rows` 是 to_chart 的
    # 约定入口（它只认 list[dict] 或 {"rows": [...]}，见 02），要出图的那组数字就放这儿。
    outcome = await ctx.stats.run(DELAY_SCRIPT, {"prj": df})
    if not outcome.ok:
        # 业务语言，不甩脚本报错；细节已在日志与归档里
        yield Event.error("stats_failed", "延期情况没能统计出来，请稍后重试。")
        return

    # 列名是业务名；序号由展示层生成；阶段码已在脚本里翻成阶段名
    yield Event.table(
        columns=["序号", "项目编号", "项目名称", "负责人", "所处阶段", "延期天数"],
        rows=outcome.result["detail"],
        title="延期项目清单",
    )
    yield Event.chart(**ctx.stats.to_chart(
        outcome, chart_type="bar", x_key="延期区间", series_keys=["项目数"],
        title="延期时长分布",
    ))

    # 分析：只喂沙箱算好的数字，让模型组织语言（数字它一个都不许自己算）
    system = MY_SYSTEM + domain_prompt_section(self.manifest)
    async for piece in ctx.llm.chat_stream([
        {"role": "system", "content": system},
        {"role": "user", "content":
            f"用户问：{request.query}\n统计结果（只准使用这些数字）：{outcome.result['summary']}\n"
            "请给出：总量、按延期时长的分档情况、最需要关注的几个项目、一句结论。"},
    ]):
        yield Event.delta(piece)

    yield Event.suggestions([...])   # 答后引导（可选）；每项 {id,name,label,query}，不是字符串
```

## 五、不是每轮都在查数：寒暄与「你能做什么」

前四节讲的是「用户问了个能取数的问题」。线上第一轮往往不是——「你好」「你是谁」「你能帮我
查什么」占了相当比例，而这些**同样会落进你的 `handle()`**。

**为什么这是你的事、不是平台的事**：平台路由没有闲聊分支。一句「你好」不含任何模块关键词，
分类器多半弃权，接着就是——**用户只有一个模块权限时直通你**、**上一轮路由过谁就粘回谁**
（粘性路由）。只有「多个候选 + 无粘性目标」才会被路由的澄清兜底接住。所以这类问题进模块是
常态而非意外，模板骨架那句 `Event.delta(f"[{MODULE_CODE}] 收到: {query}")` 一旦留着，用户
第一句话得到的就是它。

**该回什么**：介绍**本业务板块**的能力——一句话说明你负责哪个域，然后列举常用场景，
每个场景配一句简短介绍（这个场景能回答什么问题）。

```python
# ✗ 骨架的默认反应：用户看到模块编码和一句回声
yield Event.delta(f"[{MODULE_CODE}] 收到: {request.query}")

# ✗ 空洞客套：说了等于没说，用户还是不知道能问什么
yield Event.delta("您好！有什么可以帮您的吗？")

# ✓ 报能力 + 列场景 + 每个场景一句话
yield Event.delta(
    "您好，我负责**制程问题**相关的查询。常用场景：\n\n"
    "- **问题单查询**：按单号、机型或时间段查制程问题单的处理状态与结论\n"
    "- **责任归属分布**：看一段时间内的问题按部门、责任分类怎么分布\n"
    "- **相似问题排查**：找历史上类似的问题及其处理方式\n"
)
# recommendations 每项是对象（id/name/label/query），不是字符串——形状见 02「事件协议」
yield Event.suggestions([
    {"id": "1", "name": "问题单查询", "label": "查上月问题单", "query": "查一下上个月的制程问题单"},
    {"id": "2", "name": "机型分布", "label": "问题最多的机型", "query": "近三个月制程问题最多的机型"},
])
```

硬约束：

- **只介绍本板块**。别顺带列举其他模块能干什么——用户不一定有那些模块的权限，介绍了就是
  给他一个点不动的预期，也等于把他看不到的权限边界说漏了。跨域引导是平台路由的事（澄清
  兜底只推荐权限内的候选）。
- **场景清单有唯一信源**：`manifest.intents`（G1 采集的示例问题）+
  `docs/2_landed/business_description.md`。**别即兴编**——编出来的场景要么模块压根不支持，
  要么措辞与 `intents` 对不上，用户照着你给的说法问一遍却路由不回来。反过来这也是对
  `intents` 的要求：它得写成**用户认得的说法**，不是内部黑话。
- **不许因为寒暄去取数**。一句「你好」不构成查询意图，别为了「显得有用」先拉一把数据回来。
- **第二节照样管**：能力介绍里不出现表名、字段名、数据源别名——介绍的是**业务场景**，
  不是数据存在哪。
- **配 `Event.suggestions`**：把最常用的两三个场景做成可点按钮，比让用户照着正文重敲一遍强。

**哪些问题算这一类**：问候（你好 / 在吗）、身份（你是谁）、能力（你能做什么 / 能帮我查什么 /
有什么功能），以及**问了个本域够不着的问题**——这时同样是说清「本板块管什么、不管什么」，
别硬答。

## 六、自检清单（写完 `handle()` 逐条过）

- [ ] 回给用户的表格/正文里**没有**自增 ID、代理主键、状态码原值、软删标记、审计列。
- [ ] 需要序号时，序号是展示层生成的 1..N，**不是**数据库 id。
- [ ] 业务标识（工单号/料号/项目编号）该给的都给了，没被「精简」掉。
- [ ] 表格列名、正文、图表轴、`Event.error` 的 message 里**没有任何**表名/字段名/别名/SQL。
- [ ] 每个展示列的显示名来自 `db_description` 的「用户可见显示名」，各轮口径一致。
- [ ] 空值/占位值已换成「未填」一类的人话。
- [ ] 结果上百条时：表格只给前 N 条 + 结论，全量走 `ctx.files` 导出并把链接嵌进正文；
      导出文件的表头同样是业务语言（不是 `dept_id` 这种）。
- [ ] 除用户明说只要数据外，答案在明细之外给了：总量 + 分档/分布 + 重点项 + 一句结论。
- [ ] 上述每一个数字都来自 `ctx.stats` 沙箱产物，`Event.chart` 的数字同样。
- [ ] 分析维度声明在 `manifest.analysis_dimensions`，不是硬编码在提示串里。
- [ ] 「你好 / 你能做什么」这类问题有专门分支：报本板块能力 + 列常用场景 + 每个场景一句
      介绍（不是回声，也不是「有什么可以帮您」），并配 `Event.suggestions` 按钮。
- [ ] 能力介绍**只讲本板块**（不列举其他模块），场景取自 `manifest.intents` /
      `business_description.md`，没有即兴编造，也没有因寒暄去取数。
